# 7. 소스맵 복원

브라우저 에러의 스택은 압축된 번들 기준이라 그대로는 읽을 수 없다. worker가 릴리스에 올라온 소스맵으로 원본 파일, 줄, 함수 이름을 되찾고, 그 결과로 지문을 계산한다. 소스맵 해석기는 Java로 직접 구현한다.

## 7.1 고유 문제

```
TypeError: Cannot read properties of undefined (reading 'nickname')
    at t (https://fanpalive.duckdns.org/assets/index-BxK3a9.js:1:28371)
```

이 스택에는 문제가 두 가지 있다. 사람이 읽을 수 없고, 빌드할 때마다 파일 이름과 열 번호가 바뀌어 지문으로 쓸 수 없다. 복원은 화면 표시뿐 아니라 그룹핑의 전제 조건이다.

## 7.2 올리기

1. 프론트를 빌드할 때 소스맵을 만들되 번들에 소스맵 주소를 적지 않는다(Vite의 `build.sourcemap: 'hidden'`). 소스맵 파일은 웹 서버에 배포하지 않는다. 원본 코드가 공개되지 않는다.
2. 빌드 스크립트가 릴리스 이름(git 커밋 해시)과 함께 소스맵을 api에 올린다. 인증은 프로젝트 토큰으로 한다(15장).
3. api가 파일을 압축해 볼륨에 저장하고, PostgreSQL에 릴리스, 파일 이름, 크기, 해시를 기록한다.
4. 같은 릴리스 이름을 Vue SDK 초기화에 넣는다. 이벤트의 릴리스와 소스맵의 릴리스가 같아야 짝이 맞는다.

파일 저장은 포트 뒤에 둔다. 처음에는 로컬 볼륨 어댑터만 만들고, S3 호환 저장소는 필요할 때 어댑터를 추가한다.

## 7.3 해석

소스맵의 핵심은 `mappings` 문자열이다. 압축된 코드의 위치와 원본 위치의 대응이 Base64 VLQ라는 가변 길이 숫자로 적혀 있다. 줄은 세미콜론으로, 구간은 쉼표로 나뉘고, 각 숫자는 바로 앞 값과의 차이다.

해석 절차는 다음과 같다.

1. `mappings` 를 처음부터 끝까지 한 번 읽어 구간마다 숫자 다섯 개(압축 열, 원본 파일 번호, 원본 줄, 원본 열, 이름 번호)를 얻는다.
2. 차이값을 누적해 실제 값으로 바꾼다.
3. 압축 줄별로 구간을 열 순서대로 배열에 담는다.
4. 조회할 때는 해당 줄의 배열에서 이진 탐색으로 주어진 열보다 작거나 같은 마지막 구간을 찾는다.

메모리 표현이 중요하다. 구간마다 객체를 만들면 수십만 개의 객체 헤더가 힙을 차지한다. 구간은 `int[]` 다섯 개에 나란히 담는다. 압축된 번들은 보통 한 줄이므로, 줄별 시작 위치만 따로 둔다.

앞뒤 코드 몇 줄을 보여 주기 위해 `sourcesContent` 도 읽는다. 다만 원본 코드는 크기가 크므로 캐시에는 넣지 않고, 필요한 프레임의 앞뒤 5줄만 잘라 이벤트에 붙인다.

## 7.4 캐시

소스맵 하나를 해석하는 것은 무겁다. 이벤트마다 다시 하면 안 된다.

| 항목 | 설계 |
| --- | --- |
| 캐시 단위 | (프로젝트, 릴리스, 파일 이름) 하나당 해석된 배열 |
| 크기 제한 | 개수가 아니라 바이트 합계로 제한. 처음 값 128MB |
| 동시 요청 | 같은 소스맵을 여러 스레드가 동시에 찾으면 한 스레드만 해석하고 나머지는 기다림 |
| 내보내기 | 오래 안 쓴 것부터. 새 릴리스가 나오면 옛 릴리스 것은 자연히 밀려남 |

셋째 줄이 폭주와 직접 연결된다. 프론트 배포 직후 새 버그가 터지면 같은 소스맵을 찾는 이벤트가 한꺼번에 온다. 이때 스레드마다 해석을 시작하면 CPU와 힙이 동시에 바닥난다. Caffeine의 로딩 캐시는 키 하나에 대해 계산을 한 번만 실행하므로 이것을 그대로 쓴다.

## 7.5 소스맵보다 이벤트가 먼저 오는 경우

배포 직후에는 소스맵 업로드가 끝나기 전에 새 번들의 에러가 먼저 도착할 수 있다.

- 원칙: 빌드 스크립트에서 업로드를 배포보다 먼저 실행한다. 업로드가 실패하면 배포하지 않는다.
- 그래도 못 찾은 경우: 이벤트를 복원 안 됨으로 표시해 저장하고, 지문은 예외 타입과 값을 지운 메시지로 계산한다(6.3의 마지막 규칙).
- 화면에서는 복원 안 된 이벤트를 볼 때 api가 그 자리에서 복원을 다시 시도한다. 뒤늦게 올라온 소스맵이 있으면 읽을 수 있는 스택이 보인다.

남는 한계는 이렇게 묶인 이슈가 나중에 제대로 복원된 이슈와 따로 존재한다는 점이다. 6.4의 지문 대응 구조 덕분에 둘을 병합하는 비용은 작다. 자동 재처리는 후속 과제로 둔다.

## 7.6 버린 대안과 측정할 값

| 대안 | 버린 이유 |
| --- | --- |
| 브라우저에서 복원 | 소스맵을 공개 경로에 두어야 함. 사용자 브라우저에 수 MB를 내려받게 함 |
| Node 프로세스를 옆에 띄워 기존 라이브러리 사용 | 컨테이너와 메모리 예산이 하나 더 필요. 프로세스 간 호출 지연 |
| 조회할 때만 복원 | 지문 계산에 복원 결과가 필요하므로 처리 시점에 해야 함 |
| 구간을 객체 목록으로 보관 | 힙 사용량과 GC 부담이 큼 |

측정할 값은 소스맵 크기별 해석 시간, 해석된 배열의 힙 사용량, 캐시 적중률, 복원 실패율이다. 검증은 실제 Vite 빌드 결과물을 테스트 자료로 두고, 알려진 위치 수백 개의 복원 결과를 기존 라이브러리의 결과와 비교한다.

## 구현하면서 바뀐 점

13 작업에서 해석기와 캐시를 core 에 만들면서 정한 것이다. 이유는 [CHOICES.md](./CHOICES.md)의 13 절에 있다.

- **캐시는 직접 만들었다**: core 는 JDK 만 쓰므로 7.4의 Caffeine 대신 `SourceMapCache` 를 만들었다. 동시 해석 한 번, 바이트 합계 상한, 오래 안 쓴 것부터 내보내기를 한다. 상한(128MB)은 쓰는 쪽이 넘긴다.
- **조회의 기준**: 줄은 1부터, 열은 0부터 센다. 브라우저 스택의 열은 1부터라 복원 단계가 1을 뺀다.
- **원본 경로**: 소스맵에 적힌 그대로(`sourceRoot` 만 앞에 붙임) 돌려준다.
- **검증**: 실제 Vite 빌드의 5,385개 위치가 source-map 0.7.4 의 답과 모두 같다. 자료를 만드는 스크립트는 `scripts/sourcemap-fixture` 에 있다.
- **실측**(로컬-1, 커밋 3a15631): 소스맵 583KB, 구간 18,835개를 해석하는 데 3.05ms(JSON 읽기 포함), 위치 하나 찾기 61ns, 해석 결과의 어림 크기 약 430KB. 원본 소스맵 크기보다 작다.

15 작업에서 업로드와 복원을 붙이면서 정한 것이다. 이유는 CHOICES 15 절에 있다.

- **업로드**: OWNER 가 콘솔에서 프로젝트 토큰(`edt_...`)을 발급하고, 빌드 스크립트 `scripts/upload-sourcemaps.sh` 가 그 토큰으로 릴리스를 등록하고 dist 아래의 `.map` 을 올린다. 하나라도 실패하면 스크립트가 실패해 배포를 막는다.
- **저장 위치**: (프로젝트, 릴리스, 파일 이름)으로 정해지는 해시 경로. worker 는 DB를 묻지 않는다.
- **복원**: worker 의 계산 단계가 지문을 만들기 전에 한다. 소스맵의 원래 이름이 없으면 함수 이름을 비운다. 복원하지 못한 번들 프레임은 앱 프레임에서 빼서 대체 지문이 되게 한다.
- **확인**(커밋 3dae764): demo-web 을 릴리스 A, B, C로 세 번 빌드해 올렸다. 번들 이름은 빌드마다 달랐다(`index-CIWJ4U_E.js`, `index-BX3Emfeb.js`, `index-C4cKEFLW.js`). B의 에러는 `src/collab.ts:7` 로 되돌아가 이슈가 되었고, A와 C의 같은 에러도 같은 이슈로 묶였다. B에서 해결로 표시한 뒤 A(옛 번들)의 에러는 해결을 유지했고, C의 에러는 재발로 바꿨다. 화면의 상세에는 원본 코드의 앞뒤 줄이 보였다.
