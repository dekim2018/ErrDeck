# 12. 통합 화면

팬파라이브와 CoPage를 한눈에 보는 화면은 에러, 성능, 업타임을 직접 그리고, 서버 지표는 서비스마다 숫자 6개짜리 요약 카드로만 올린다. 상세 지표는 같은 서비스와 같은 시간대를 가리키는 그라파나 링크로 넘긴다.

## 12.1 지표를 어디에 그릴지에 대한 제안과 이유

고민 중인 두 안과 제안을 비교한다.

| 기준 | 2번: 지표도 화면에 직접 | 3번: 지표는 그라파나로 | 제안: 요약 카드와 연결 |
| --- | --- | --- | --- |
| 한눈에 보기 | 좋음 | 화면을 오가야 함 | 좋음. 판단에 필요한 숫자는 한 화면에 있음 |
| 깊이 있는 분석 | 차트 기능을 직접 만들어야 함 | 좋음 | 좋음. 그라파나가 맡음 |
| 개발량 | 큼. 시계열 차트, 확대, 기간 비교, 변수 선택 | 작음 | 작음. 즉시 값 조회 몇 개 |
| 프로젝트의 초점 | 프론트 차트 작업에 시간이 감 | 백엔드와 인프라에 집중 | 백엔드와 인프라에 집중 |
| 이 서비스만의 가치 | 그라파나와 같은 것을 하나 더 만듦 | 연결 고리가 약함 | 에러와 지표를 시간으로 이어 줌 |

이유를 풀어 쓰면 네 가지다.

1. **그라파나를 다시 만들지 않는다.** 시계열 차트의 확대, 기간 비교, 변수 전환은 그라파나가 이미 잘한다. 같은 것을 Vue로 다시 만들면 몇 주가 들고, 결과는 그라파나보다 못하다. 그 시간은 5장부터 10장의 수집과 처리 설계에 쓰는 편이 낫다.
2. **링크만으로는 한눈에 보이지 않는다.** 서비스가 정상인지 판단하려고 매번 다른 화면으로 넘어가야 한다면 통합 화면이 아니다. 판단에는 추세 그래프가 아니라 지금 값 몇 개면 충분하다.
3. **요약 카드는 구현이 가볍다.** 프로메테우스의 HTTP API에 즉시 값 질의를 보내면 숫자가 온다. api가 대신 질의하고 15초 동안 캐시한다. 브라우저는 프로메테우스에 직접 닿지 않으므로 인증을 한 곳에서만 처리한다.
4. **두 도구를 시간으로 잇는 것이 이 서비스만 할 수 있는 일이다.** 이슈 상세 화면에서 이 에러가 처음 발생한 시각의 앞뒤 15분으로 맞춘 그라파나 링크를 만든다. 에러가 난 순간 커넥션 풀이 가득 찼는지, 힙이 부족했는지를 한 번에 확인한다. 그라파나만으로는 에러가 언제 났는지 모르고, 에러 화면만으로는 서버가 어땠는지 모른다.

## 12.2 요약 카드의 지표 6개

스프링 프로젝트 하나당 카드 하나다. 값은 전부 감시 대상의 Actuator가 내보내는 표준 지표에서 온다.

| 지표 | 프로메테우스 질의 | 주의로 표시하는 기준(처음 값) |
| --- | --- | --- |
| 생존 | `up` | 0이면 장애 |
| CPU 사용률 | `process_cpu_usage` | 80% 초과 |
| 힙 사용률 | `jvm_memory_used_bytes` 와 `jvm_memory_max_bytes` 의 힙 영역 합계 비율 | 85% 초과 |
| 요청 시간 p95 | `histogram_quantile(0.95, ...http_server_requests_seconds_bucket)` 5분 구간 | 프로젝트별 목표 초과 |
| 5xx 비율 | 상태 코드 5xx의 요청 비율, 5분 구간 | 1% 초과 |
| 커넥션 풀 대기 | `hikaricp_connections_pending` | 0보다 큼 |

여섯째를 넣은 이유가 있다. 스프링 서비스가 느려지는 가장 흔한 원인이 커넥션 풀 고갈이고, CPU와 메모리가 멀쩡해도 일어난다. 대기 수가 0보다 크다는 것은 스레드가 커넥션을 못 얻어 서 있다는 뜻이다.

Vue 프로젝트에는 서버 지표가 없다. 카드에는 이 서비스가 직접 수집한 에러 수와 페이지 로딩 시간을 보여 준다.

## 12.3 화면 구성

| 화면 | 내용 | 데이터 출처 |
| --- | --- | --- |
| 전체 보기 | 시스템 카드 4개. 상태 신호, 미해결 이슈 수, 24시간 에러 추이, 가동률, 열린 장애 | PostgreSQL, ClickHouse 집계 |
| 시스템 보기 | 프로젝트별 한 줄. 상태, 새 이슈, 24시간 에러 수, 요약 카드 지표 6개, 최근 릴리스, 그라파나 링크 | 위와 같음, 프로메테우스 |
| 이슈 목록 | 상태, 환경, 릴리스, 기간으로 거르기. 최근 발생, 횟수, 영향 사용자 순 정렬 | PostgreSQL, ClickHouse 집계 |
| 이슈 상세 | 복원된 스택, 앞뒤 코드, 빵부스러기, 요청 정보, 발생 추이, 연결된 추적, 발생 시각의 그라파나 링크 | ClickHouse |
| 성능 | 엔드포인트 표, 느린 요청 목록, 스팬 그림 | 프로메테우스, ClickHouse |
| 업타임 | 모니터 상태, 응답 시간, 장애 기록, 가동률 | PostgreSQL, ClickHouse |
| 릴리스 | 릴리스별 새 이슈와 재발, 소스맵 업로드 상태 | PostgreSQL |
| 알림과 설정 | 규칙, 채널, 구성원, 키, 한도 | PostgreSQL |

전체 보기의 상태 신호는 세 단계다.

| 신호 | 조건 |
| --- | --- |
| 장애 | 모니터가 다운이거나 생존 지표가 0 |
| 주의 | 최근 1시간에 새 이슈나 재발이 있음, 또는 요약 카드 지표 중 하나가 기준 초과 |
| 정상 | 그 밖 |

화면의 색, 배치, 차트 모양은 이 문서에서 정하지 않는다. 구현 전에 시안을 먼저 만들어 고르는 절차를 따른다.

## 12.4 그라파나 연결 방식

그라파나 대시보드는 서비스 이름을 변수로 받게 만든다. 링크에 변수와 시간 범위를 실어 보낸다.

```
/grafana/d/{대시보드ID}/jvm?var-service=fanpa-broadcast&from={시작 밀리초}&to={끝 밀리초}
```

| 링크가 있는 곳 | 넘기는 값 |
| --- | --- |
| 시스템 보기의 프로젝트 줄 | 그 서비스, 최근 1시간 |
| 이슈 상세 | 그 서비스, 최초 발생 시각의 앞뒤 15분 |
| 장애 기록 | 그 서비스, 장애 시작 15분 전부터 종료 15분 뒤까지 |
| 느린 요청 상세 | 그 서비스, 요청 시각의 앞뒤 5분 |

## 12.5 두 서비스에 맞춘 고려

| 서비스 | 고려한 점 | 처리 |
| --- | --- | --- |
| 팬파라이브 | 서비스가 5개라 한 요청의 에러가 여러 프로젝트에 흩어짐 | 시스템 단위로 묶어 보고, trace_id로 프로젝트를 넘나들며 따라감 |
| 팬파라이브 | 결제사 호출 실패는 스택이 달라도 한 문제 | SDK에서 지문을 직접 지정 |
| 팬파라이브 | 서버를 평소 꺼 둠 | 모니터 일시 중지(9.1). 꺼진 동안은 상태 신호를 중지로 표시 |
| 팬파라이브 | 방송, 경기 단위로 문제를 보고 싶음 | 이벤트 태그에 broadcast_id, match_id를 넣어 거르기 |
| CoPage | 에러가 WebSocket 핸들러 안에서 남 | `ErrDeck.capture` 로 직접 보내고 태그에 doc_id를 넣음 |
| CoPage | 변환 충돌, 재동기화는 에러가 아니라 정상 동작의 빈도 | 이슈로 만들지 않음. CoPage가 프로메테우스 카운터로 내보내고 그라파나에서 봄 |
| CoPage | 클라이언트 OT 오류는 브라우저에서 남 | Vue SDK와 소스맵 복원이 필수. 빵부스러기에 최근 연산 종류를 남김 |

마지막에서 둘째 줄이 에러와 지표를 구분하는 기준을 보여 준다. 예외가 던져진 것은 이슈로, 정상 동작이 얼마나 자주 일어나는지는 지표로 본다. 둘을 섞으면 이슈 목록이 잡음으로 찬다.

## 구현하면서 바뀐 점

12 작업에서 콘솔 뼈대와 이슈 화면을 만들면서 정한 것이다. 이유는 [CHOICES.md](./CHOICES.md)의 12 절에 있다.

- **화면 시안**: 왼쪽 사이드바(시스템과 프로젝트)와 표 중심의 본문(A안). 색은 상태 배지에만 쓴다. 밝은 모드와 어두운 모드를 시스템 설정에 따른다.
- **이슈 목록**: 상태, 기간(1시간 ~ 30일), 정렬(최근 발생, 횟수, 영향 사용자), 릴리스로 거른다. 환경으로는 거르지 않는다. 횟수순과 사용자순은 위 25건만 보인다.
- **이슈 상세**: 발생 추이(빈 구간은 0), 30일 안의 가장 최근 원본(예외 사슬, 라이브러리 프레임은 접음, 요청 정보, 태그, 빵부스러기), 상태 변경(MEMBER 이상), 댓글, 최초 발생 앞뒤 15분의 그라파나 링크.
- **전체 보기와 시스템 보기**: 아직 없다. 22 작업에서 만든다.
- **개발 서버**: `web` 에서 `ERRDECK_API=http://localhost:8081 npm run dev`. 배포는 16 작업에서 Caddy가 정적 파일과 `/api` 를 함께 내보낸다.
