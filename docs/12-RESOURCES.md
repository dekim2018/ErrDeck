# 14. 자원 설계: CPU, 스레드 풀, 메모리, 커넥션 풀

자원 설계의 원칙은 셋이다. 일의 성격(CPU를 쓰는 일인가, 기다리는 일인가)에 맞는 스레드를 쓰고, 모든 대기 공간에 상한을 두고, 프로세스마다 CPU와 메모리의 천장을 정한다. 기준 서버는 4코어다(로컬). 2코어인 오라클 서버용 값은 17.4에 따로 적는다. 이 장의 값은 전부 처음 값이고, 13.5의 대시보드와 18장의 실험으로 고친다.

## 14.1 CPU 배분

| 컨테이너 | CPU 상한(코어) | 이유 |
| --- | --- | --- |
| worker | 2.0 | 가장 많이 쓰는 곳. 폭주 때도 절반은 남기기 위한 천장 |
| ClickHouse | 2.0 | 병합과 조회 |
| ingest | 1.0 | 일이 가벼움. 상한보다 worker에게 밀리지 않는 것이 중요 |
| api | 1.0 | 조회 |
| PostgreSQL | 1.0 |  |
| Redis | 1.0 | 명령 실행이 단일 스레드 |
| 그 밖(Caddy, 관측 도구) | 각 0.5 이하 |  |

상한의 합은 4를 넘는다. 상한은 예약이 아니라 천장이므로 넘어도 된다. 평소에는 아무도 천장에 닿지 않는다. 이 표의 핵심은 worker의 2.0이다. 에러 폭주로 worker가 최대로 돌아도 코어 2개는 ingest, Redis, ClickHouse의 몫으로 남는다.

## 14.2 CPU 상한이 JVM에 미치는 영향

컨테이너의 CPU 상한은 운영체제 수준의 제한으로 끝나지 않는다. JVM은 시작할 때 상한을 읽어 사용 가능한 코어 수로 삼고, 여러 기본값을 여기서 계산한다.

| JVM이 코어 수로 정하는 것 | 영향 |
| --- | --- |
| GC 스레드 수와 기본 GC 종류 | 코어가 2개 미만이거나 메모리가 작으면 기본 GC가 단일 스레드 방식으로 바뀜 |
| 가상 스레드를 실어 나르는 스레드 수 | 코어 수와 같음. 동시에 실제로 실행되는 가상 스레드의 수 |
| 공용 포크조인 풀의 크기 | 병렬 스트림과 `CompletableFuture` 기본 실행기의 크기 |
| JIT 컴파일러 스레드 수 | 시작 직후의 속도 |

그래서 코어 수를 JVM의 추측에 맡기지 않고 `-XX:ActiveProcessorCount` 로 명시한다. 설정 파일을 보면 프로세스가 코어 몇 개를 전제로 도는지 알 수 있게 한다.

**CPU 제한 현상**도 알아야 한다. 리눅스는 CPU 상한을 100ms 주기의 할당량으로 구현한다. 상한이 2.0이면 100ms마다 200ms 분량을 쓸 수 있다. 스레드 8개가 동시에 돌면 25ms 만에 할당량을 다 쓰고, 남은 75ms 동안 프로세스 전체가 멈춘다. 평균 CPU 사용률은 낮아 보이는데 응답 시간의 꼬리가 길어지는 원인이다.

대응은 CPU를 쓰는 스레드 수를 상한과 같게 맞추는 것이다. 그리고 컨테이너의 제한 횟수 지표를 13.6의 경보로 본다.

## 14.3 프로세스별 스레드 모델

| 프로세스 | 일 | 스레드 | 동시성 상한 |
| --- | --- | --- | --- |
| ingest | 요청 처리 | 가상 스레드(요청당 하나) | 동시 연결 2,000, 진행 중인 Redis 호출 256 |
| worker | 대기열 읽기 | 일반 스레드 2개(대기열당 하나) | 넘겨주기 큐 2,000건 |
| worker | 해제, 복원, 지문 계산 | 일반 스레드 고정 풀 2개 | CPU 상한과 같음 |
| worker | 이슈 확인, 묶음 쓰기, 확인 처리 | 일반 스레드 1개 | 묶음 5,000행 또는 1초 |
| worker | 업타임 점검 | 가상 스레드 | 세마포어 50 |
| worker | 알림 발송 | 가상 스레드 | 세마포어 10 |
| api | 요청 처리 | 가상 스레드 | ClickHouse 조회 8, DB 접근 10 |

## 14.4 가상 스레드를 쓰는 곳과 쓰지 않는 곳

**쓰는 곳: 기다리는 일.** ingest의 요청, 업타임 점검, 웹훅 발송, api의 조회는 시간 대부분을 네트워크 응답을 기다리며 보낸다. 가상 스레드는 기다리는 동안 실행 스레드를 내놓으므로, 적은 코어로 많은 대기를 감당한다. 스프링에서는 `spring.threads.virtual.enabled=true` 로 켠다.

**쓰지 않는 곳: 계산하는 일.** 압축 해제, 소스맵 해석, 지문 해시는 기다림이 없다. 가상 스레드는 스스로 멈추는 지점(I/O, 잠금 대기)에서만 자리를 양보한다. 계산만 하는 가상 스레드는 끝날 때까지 실행 스레드를 붙잡는다. 수천 개를 만들어도 동시에 도는 것은 코어 수만큼이고, 나머지는 순서 없이 밀린다. 이득은 없고 통제만 잃는다. 그래서 크기가 코어 수와 같은 일반 스레드 고정 풀을 쓴다.

**가상 스레드의 함정: 상한이 사라진다.** 톰캣의 스레드 풀 200개는 의도하지 않은 보호 장치였다. 동시에 201번째 요청은 기다려야 했고, 그 덕분에 뒤쪽의 DB와 Redis로 가는 동시 호출도 200개를 넘지 않았다. 가상 스레드로 바꾸면 이 천장이 없어진다. Redis가 느려지는 순간 요청 수천 개가 동시에 Redis를 부르고, 전부 힙에 쌓인다.

그래서 상한을 직접 만든다. ingest는 진행 중인 Redis 호출을 세마포어 256개로 제한한다. 자리가 없으면 기다리지 않고 바로 503을 응답한다. 기다리게 하면 요청이 쌓이고, 쌓인 요청은 메모리다.

Java 25를 쓰는 이점도 여기에 있다. 이전 버전에서는 `synchronized` 블록 안에서 기다리는 가상 스레드가 실행 스레드를 붙잡는 문제가 있었고, 라이브러리 내부의 `synchronized` 때문에 예상하지 못한 정체가 생겼다. 이 문제는 JDK 24에서 해결되었다. 그래도 붙잡힘 횟수 지표는 대시보드에 올려 확인한다.

## 14.5 worker의 단계 구조와 역압

```
읽기 스레드(2) -> 넘겨주기 큐(2,000) -> 계산 풀(2) -> 쓰기 큐(10,000) -> 쓰기 스레드(1)
```

| 단계 | 하는 일 | 막히면 |
| --- | --- | --- |
| 읽기 | 대기열에서 최대 500건씩 읽어 넘겨주기 큐에 넣음 | 큐가 차면 넣기에서 멈춤. 대기열을 더 읽지 않음 |
| 계산 | 해제, 정규화, 복원, 지문. I/O 없음 | 쓰기 큐가 차면 멈춤 |
| 쓰기 | 새 지문의 이슈를 한 번에 확인, ClickHouse 묶음 쓰기, 이슈 갱신, 확인 처리 | ClickHouse가 느리면 여기서 늦어짐 |

계산 단계에서 I/O를 전부 뺀 것이 핵심이다. 이슈 확인(PostgreSQL)을 계산 스레드가 이벤트마다 하면, DB가 느려질 때 계산 스레드 2개가 전부 대기에 묶인다. 대신 쓰기 단계가 묶음 안의 처음 보는 지문을 모아 쿼리 한 번으로 확인한다. 계산 스레드는 항상 계산만 한다.

에러와 트랜잭션은 넘겨주기 큐를 따로 쓴다. 계산 풀은 에러 큐를 먼저 비우고, 에러 3건마다 트랜잭션 1건을 처리한다. 트랜잭션이 밀려도 에러는 제때 보인다.

모든 큐에 길이가 있으므로 막힘이 뒤에서 앞으로 전해진다.

1. ClickHouse가 느려진다.
2. 쓰기 스레드가 늦어지고 쓰기 큐가 찬다.
3. 계산 풀이 멈추고 넘겨주기 큐가 찬다.
4. 읽기 스레드가 멈추고 Redis 대기열이 길어진다.
5. 대기열이 상한에 닿고 ingest가 503을 응답한다.
6. SDK가 전송을 쉬고 버린 건수를 센다.

이 사슬 어디에도 길이 제한 없는 공간이 없다. ClickHouse가 10분 동안 멈춰도 어느 프로세스의 메모리도 계속 늘지 않는다. 대신 그동안의 원본은 잃고 건수는 남는다. 이것이 의도한 동작이다.

## 14.6 커넥션 풀

| 풀 | 크기 | 근거 |
| --- | --- | --- |
| ingest의 PostgreSQL | 2 | 키 캐시가 비었을 때만 조회 |
| worker의 PostgreSQL | 4 | 쓰기 스레드 1개와 업타임, 알림의 상태 갱신 |
| api의 PostgreSQL | 10 | 화면 조회 |
| worker의 ClickHouse | 2 | 쓰기 스레드 1개 |
| api의 ClickHouse | 8 | 동시 조회 상한과 같음 |

PostgreSQL 연결의 합은 16이다. PostgreSQL의 최대 연결 수는 30으로 두어 관측 도구와 수동 접속의 여유를 남긴다.

풀을 크게 잡지 않는 이유는 PostgreSQL의 CPU 상한이 1코어이기 때문이다. 연결이 30개여도 동시에 실행되는 쿼리는 하나다. 풀을 키우면 처리량은 그대로이고 DB 안의 대기와 메모리만 는다.

가상 스레드와 커넥션 풀을 함께 쓸 때의 설정은 다음과 같다.

- 커넥션 획득 제한 시간을 2초로 줄인다. 기본값은 30초다. DB에 문제가 생기면 요청이 30초씩 매달려 쌓인다.
- DB에 들어가는 구간을 풀 크기와 같은 세마포어로 감싼다. 가상 스레드 수천 개가 풀 앞에 줄 서는 대신, 세마포어에서 걸러진다.
- 풀의 대기 수를 지표로 본다(12.2의 여섯째 지표).

Redis 연결은 둘로 나눈다. 일반 명령은 연결 하나를 공유한다. 대기열 읽기는 응답이 올 때까지 연결을 붙잡는 명령이므로 전용 연결을 쓴다. 같은 연결을 쓰면 읽기가 기다리는 동안 다른 명령이 전부 막힌다.

## 14.7 메모리 예산

컨테이너 14개, 합계 5,632MB다.

| 컨테이너 | 메모리 상한(MB) | 내부 배분 |
| --- | --- | --- |
| ClickHouse | 2,048 | 서버 메모리 상한과 캐시를 이 안에 맞춤 |
| worker | 768 | 힙 448(그중 소스맵 캐시 128) |
| api | 512 | 힙 256 |
| PostgreSQL | 512 | shared_buffers 128 |
| Prometheus | 512 |  |
| ingest | 384 | 힙 160 |
| Redis | 320 | 데이터 상한 256 |
| Grafana | 192 |  |
| cAdvisor | 128 |  |
| Caddy | 64 |  |
| Alertmanager | 64 |  |
| postgres exporter | 64 |  |
| node exporter | 32 |  |
| redis exporter | 32 |  |

JVM 컨테이너의 힙을 상한의 절반 안팎으로 잡은 이유는 힙 밖에서도 메모리를 쓰기 때문이다. 클래스 정보, 컴파일된 코드, 스레드 스택, 네트워크 버퍼, GC 자체의 자료구조가 여기에 든다. 힙을 상한 가까이 잡으면 힙은 남는데 컨테이너가 메모리 초과로 죽는다.

가상 스레드의 스택은 힙에 저장된다. 일반 스레드의 스택이 힙 밖에 잡히는 것과 다르다. 대기 중인 가상 스레드가 많을수록 힙을 쓴다. ingest의 동시 연결 상한이 메모리 설계이기도 한 이유다.

## 14.8 GC 선택

| 프로세스 | GC | 이유 |
| --- | --- | --- |
| ingest | Serial | 코어 1개, 힙 160MB. 힙이 작아 멈춤이 짧고, GC 스레드가 요청과 코어를 다투지 않음 |
| worker | Parallel | 처리량이 목표. 사용자가 응답을 기다리지 않으므로 멈춤 시간은 중요하지 않음 |
| api | G1 | 응답 시간이 목표. 큰 조회 결과를 다루므로 멈춤 시간을 고르게 유지 |

세 프로세스가 같은 코드 저장소에서 나오지만 GC는 역할에 따라 다르게 고른다. 프로세스를 나눈 4.2의 결정이 여기서 다시 쓰인다. 선택이 맞는지는 GC 멈춤 시간 지표와 처리량을 GC 종류를 바꿔 가며 비교해 확인한다.

공통으로 메모리 부족 시 즉시 종료하는 옵션을 켠다. 메모리가 부족한 채로 반쯤 살아 있는 프로세스보다, 죽고 다시 뜨는 프로세스가 낫다. worker에는 Java 25의 압축 객체 헤더 옵션을 시험한다. 소스맵 배열과 이벤트 객체처럼 작은 객체가 많은 힙에서 사용량이 줄어드는지 잰다.

## 14.9 제한 시간

제한 시간이 없는 외부 호출은 하나도 두지 않는다.

| 호출 | 제한 시간 | 넘으면 |
| --- | --- | --- |
| SDK에서 ingest | 3초 | 버리고 건수 기록 |
| ingest에서 Redis | 200ms | 503 응답 |
| worker에서 PostgreSQL | 2초 | 묶음 재시도 |
| worker에서 ClickHouse 쓰기 | 10초 | 묶음 재시도. 확인 처리하지 않음 |
| api에서 ClickHouse 조회 | 10초 | 오류 응답 |
| api에서 프로메테우스 | 2초 | 요약 카드를 비워서 표시 |
| 업타임 점검 | 5초 | 실패로 기록 |
| 알림 웹훅 | 5초 | 재시도 3회 |

## 14.10 버린 대안

| 대안 | 버린 이유 |
| --- | --- |
| 모든 일을 가상 스레드로 | 계산 작업에는 이득이 없고 동시 실행 수를 통제할 수 없음 |
| 공용 포크조인 풀과 병렬 스트림 | 풀 하나를 모든 코드가 나눠 써서 누가 얼마나 쓰는지 알 수 없음. 크기가 코어 수에서 자동으로 정해짐 |
| 길이 제한 없는 큐 | 뒤 단계가 느려지면 메모리가 끝없이 늚. 역압이 전해지지 않음 |
| 큰 스레드 풀 하나를 여러 용도로 공유 | 느린 일(웹훅)이 빠른 일(점검)의 자리를 차지함 |
| 커넥션 풀을 넉넉하게 | DB의 코어 수를 넘는 연결은 대기만 늘림 |
