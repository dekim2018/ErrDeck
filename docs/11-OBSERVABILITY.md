# 13. 관측: 프로메테우스와 그라파나

프로메테우스와 그라파나는 두 가지 일을 한다. 감시 대상(팬파라이브, CoPage)의 서버 지표를 모아 12장의 요약 카드와 상세 화면에 공급하고, 이 서비스 자신의 파이프라인이 건강한지 지켜본다. 14장의 자원 설계가 맞는지 틀리는지도 여기서 확인한다.

## 13.1 구성 요소

| 구성 요소 | 역할 | 주요 설정 |
| --- | --- | --- |
| Prometheus | 지표 수집과 저장, 경보 규칙 평가 | 수집 주기 15초, 보존 15일 또는 2GB 중 먼저 닿는 쪽 |
| Grafana | 대시보드 | 대시보드와 데이터 소스를 저장소의 파일로 관리 |
| Alertmanager | 경보 묶기와 전달 | api의 웹훅으로 전달 |
| node exporter | 서버의 CPU, 메모리, 디스크, 네트워크 |  |
| cAdvisor | 컨테이너별 CPU, 메모리, CPU 제한 횟수 |  |
| postgres exporter, redis exporter | 저장소 지표 |  |
| ClickHouse | 자체 프로메테우스 엔드포인트 사용 |  |

대시보드를 파일로 관리하는 이유는 재현 때문이다. 그라파나 화면에서 손으로 만든 대시보드는 볼륨을 지우면 사라진다. JSON 파일로 저장소에 두면 `docker compose up` 한 번으로 같은 화면이 뜬다.

## 13.2 수집 대상

| 대상 | 지표 출처 | 수집 방식 |
| --- | --- | --- |
| ingest, worker, api | Actuator의 프로메테우스 엔드포인트(관리 포트) | 같은 도커 네트워크에서 직접 수집 |
| 서버와 컨테이너, 저장소 | 13.1의 exporter | 직접 수집 |
| 팬파라이브 스프링 서비스 5개 | Actuator | 같은 서버면 직접 수집, 다른 서버면 13.3 |
| CoPage app | Actuator | 위와 같음 |

관리 포트는 서비스 포트와 분리하고 Caddy에 연결하지 않는다. 지표 엔드포인트가 인터넷에 노출되지 않는다.

```yaml
management:
  server:
    port: 8091
  endpoints:
    web:
      exposure:
        include: health,prometheus
  metrics:
    distribution:
      percentiles-histogram:
        http.server.requests: true
```

마지막 설정이 12.2의 p95 계산에 필요하다. 이것이 없으면 요청 시간의 합계와 횟수만 나와 평균밖에 구할 수 없다. 히스토그램을 켜면 시계열 수가 늘어나므로 요청 시간 지표에만 켠다.

## 13.3 고유 문제: 감시 대상이 다른 서버에 있다

프로메테우스는 대상을 찾아가 긁어 오는 방식이다. 팬파라이브가 다른 서버(AWS)에 있으면 선택지가 둘이다.

| 방식 | 내용 | 판단 |
| --- | --- | --- |
| 중앙에서 인터넷으로 직접 수집 | 팬파라이브의 Actuator를 공개 주소로 열고 인증을 건다 | 지표 엔드포인트가 인터넷에 열림. 대상 서버의 방화벽도 열어야 함 |
| 대상 서버에 에이전트를 두고 밀어 보냄 | 대상 서버에서 프로메테우스를 에이전트 모드로 띄워 로컬 수집 후 중앙으로 원격 쓰기 | 대상 서버는 나가는 연결만 씀. Actuator는 계속 비공개 |

둘째를 고른다. 에이전트 모드는 저장과 질의 기능 없이 수집과 전달만 하므로 메모리를 적게 쓴다. 중앙 프로메테우스는 원격 쓰기 수신 기능을 켜고, Caddy가 그 경로에 인증을 건다.

팬파라이브 서버는 평소 꺼져 있다. 밀어 보내는 방식은 서버가 켜지면 알아서 다시 보내기 시작한다. 꺼져 있는 동안 중앙에서 수집 실패 경보가 울리지도 않는다.

로컬 개발에서는 전부 같은 도커 네트워크에 있으므로 직접 수집한다. 두 방식의 차이는 compose 파일의 프로필로 나눈다.

## 13.4 직접 만드는 지표

표준 지표(JVM, HTTP, 커넥션 풀)만으로는 파이프라인의 상태를 알 수 없다. 아래 12개를 Micrometer로 직접 만든다.

| 지표 | 종류 | 태그 | 알려 주는 것 |
| --- | --- | --- | --- |
| `errdeck_ingest_requests_total` | 카운터 | result | 수락과 거절(429, 503, 413)의 비율 |
| `errdeck_ingest_envelope_bytes` | 분포 | 없음 | 봉투 크기. 대기열 메모리 계산의 근거 |
| `errdeck_queue_length` | 게이지 | stream | 대기열에 쌓인 건수 |
| `errdeck_queue_oldest_age_seconds` | 게이지 | stream | 가장 오래 기다린 항목의 나이 |
| `errdeck_worker_stage_seconds` | 타이머 | stage | 단계별 처리 시간(해제, 복원, 지문, 쓰기) |
| `errdeck_events_processed_total` | 카운터 | outcome | 저장, 건수만 기록, 중복, 격리의 건수 |
| `errdeck_e2e_latency_seconds` | 히스토그램 | 없음 | 수신부터 저장까지 걸린 시간 |
| `errdeck_clickhouse_batch_rows` | 분포 | table | 묶음 크기 |
| `errdeck_clickhouse_flush_seconds` | 타이머 | table | 묶음 쓰기 시간 |
| `errdeck_sourcemap_cache_total` | 카운터 | result | 적중, 해석, 소스맵 없음 |
| `errdeck_uptime_schedule_lag_seconds` | 히스토그램 | 없음 | 점검 예정 시각과 실제 시각의 차이 |
| `errdeck_notifications_total` | 카운터 | channel, result | 알림 발송 성공과 실패 |

대기열은 길이보다 나이가 더 중요한 신호다. 길이 5,000건은 처리 속도에 따라 1초 분량일 수도 10분 분량일 수도 있다. 나이 30초는 언제나 표시가 30초 늦다는 뜻이다.

태그에는 규칙을 둔다. 프로젝트 ID는 넣을 수 있다(13개). 지문, 사용자, 실제 주소는 넣지 않는다. 태그 값의 종류가 곧 시계열 수이고, 시계열 수가 프로메테우스의 메모리다.

## 13.5 대시보드 5개

| 대시보드 | 첫 줄에 두는 것 | 보는 관점 |
| --- | --- | --- |
| 전체 개요 | 2.2의 목표 대비 현재 값(수집 응답 시간, 표시 지연, 거절 비율) | 지금 목표를 지키고 있는가 |
| 수집 파이프라인 | 초당 수신과 처리 건수, 대기열 나이, 단계별 시간 | 어느 단계가 병목인가 |
| JVM과 스레드 | 힙, GC 멈춤 시간, 스레드 수, 풀의 활성과 대기, 커넥션 풀 | 14장의 풀 크기가 맞는가 |
| 컨테이너 자원 | 컨테이너별 CPU 사용과 제한 횟수, 메모리와 상한 | 14장의 상한이 맞는가 |
| 저장소 | PostgreSQL 연결과 잠금, Redis 메모리, ClickHouse 파트 수와 쿼리 시간 | 저장소가 버티는가 |

JVM과 스레드 대시보드는 서비스 이름을 변수로 받는다. 이 서비스의 프로세스 3개와 팬파라이브, CoPage가 같은 대시보드를 쓴다. 12.4의 링크가 가리키는 것이 이 대시보드다.

지표를 고르는 기준은 두 가지 틀이다. 요청을 처리하는 프로세스는 요청 수, 오류, 시간을 본다. CPU, 메모리, 풀 같은 자원은 사용률, 포화(대기), 오류를 본다. 포화가 특히 중요하다. 사용률 100%는 일을 잘하고 있다는 뜻일 수 있지만, 대기가 생겼다는 것은 부족하다는 뜻이다.

## 13.6 경보 규칙

프로메테우스가 규칙을 평가하고, Alertmanager가 api의 웹훅으로 넘긴다. api는 이것을 16장의 알림 채널로 내보낸다. 에러 알림과 자원 경보가 같은 곳으로 온다.

| 경보 | 조건(처음 값) | 뜻 |
| --- | --- | --- |
| 프로세스 다운 | ingest, worker, api 중 하나의 생존 지표가 1분 동안 0 |  |
| 대기열 지연 | 가장 오래된 항목의 나이가 2분 동안 30초 초과 | worker가 따라가지 못함 |
| 수집 거절 | 503 응답이 1분 동안 계속 발생 | 대기열이 가득 참 |
| CPU 제한 | 컨테이너의 CPU 제한 구간 비율이 5분 동안 25% 초과 | CPU 상한이 너무 낮음 |
| 힙 부족 | 힙 사용률이 5분 동안 90% 초과 |  |
| 커넥션 풀 대기 | 대기 수가 1분 동안 0보다 큼 | 풀이 작거나 쿼리가 느림 |
| 디스크 부족 | 남은 공간이 15% 미만 | ClickHouse 보존 기간 조정 필요 |
| 격리 증가 | 격리 건수가 10분 동안 증가 | SDK와 worker의 형식이 어긋남 |

## 13.7 로그

로그 수집 도구(Loki 등)는 넣지 않는다. 메모리 예산을 관측 도구에 더 쓰기보다 수집 파이프라인에 쓴다. 컨테이너 로그는 파일 크기와 개수를 제한해 회전시키고, 로그 한 줄마다 trace_id를 넣어 추적 화면에서 찾은 요청을 로그에서 바로 검색할 수 있게 한다.
