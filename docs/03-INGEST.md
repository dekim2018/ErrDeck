# 5. 수집 경로

ingest의 목표는 하나다. 어떤 상황에서도 빠르게 응답하고, 받을 수 없으면 분명하게 거절한다. 그래서 ingest는 본문을 해석하지 않고, Redis 왕복 한 번으로 요청을 끝낸다.

## 5.1 고유 문제: 부하가 장애 순간에 몰린다

일반 서비스는 사용자가 많을 때 바쁘다. 이 서비스는 감시 대상이 고장 났을 때 바쁘다. 팬파라이브의 DB 연결이 끊기면 모든 요청이 같은 예외를 던지고, 그 예외가 전부 이쪽으로 온다. 평소 초당 몇 건이던 수신량이 수천 건으로 뛴다.

이때 이 서비스가 같이 쓰러지면 가장 필요한 순간에 쓸모가 없다. 그래서 폭주를 SDK, ingest, worker 세 곳에서 나눠 막는다.

| 막는 곳 | 방법 | 지키는 것 |
| --- | --- | --- |
| SDK | 같은 에러 접기, 메모리 큐 상한, 거절 응답을 받으면 쉬기 | 감시 대상의 메모리와 네트워크 |
| ingest | 프로젝트별 한도, 대기열 길이 상한 | Redis 메모리와 다른 프로젝트의 몫 |
| worker | 이슈별 원본 저장 상한(초과분은 건수만 기록) | ClickHouse 디스크와 처리 시간 |

원칙은 **건수는 정확하게, 원본은 제한해서** 이다. 같은 예외 1만 건의 스택트레이스를 전부 저장할 이유는 없다. 하지만 1만 번 발생했다는 사실은 알아야 한다.

## 5.2 DSN과 엔드포인트

DSN은 `https://{공개키}@{호스트}/{프로젝트ID}` 형식이다. SDK는 이것을 풀어 아래 주소로 보낸다.

```
POST /ingest/{projectId}/envelope
```

| 보내는 쪽 | 키 전달 | 이유 |
| --- | --- | --- |
| Spring SDK | `X-ErrDeck-Key` 헤더 | 서버 간 호출이라 제약이 없음 |
| Vue SDK | 쿼리 문자열 `?key=`, 본문 형식은 `text/plain` | 사용자 정의 헤더나 JSON 형식을 쓰면 브라우저가 사전 요청(OPTIONS)을 먼저 보낸다. 요청 수가 두 배가 되므로 사전 요청이 필요 없는 단순 요청으로 맞춘다 |

DSN 키는 브라우저 코드에 그대로 들어가므로 비밀이 아니다. 키만으로는 이벤트를 보내는 것 말고 아무것도 할 수 없게 하고, 남용은 15장의 출처 검사와 한도로 막는다.

## 5.3 봉투 형식

요청 본문은 여러 항목을 한 번에 담는 봉투다. 줄 단위 JSON을 gzip으로 압축한다.

```
{"sdk":"spring/0.1.0","sent_at":"2026-11-23T10:00:00Z"}
{"type":"event","length":1834}
{...에러 이벤트...}
{"type":"transaction","length":912}
{...트랜잭션과 스팬...}
{"type":"client_report","length":88}
{...SDK가 버린 건수...}
```

| 항목 종류 | 내용 |
| --- | --- |
| event | 에러 1건. 접힌 경우 `count` 로 실제 발생 횟수를 함께 보냄 |
| transaction | 요청 1건의 트랜잭션과 그 안의 스팬 |
| client_report | SDK가 큐 초과나 거절 응답으로 버린 건수. 사유별로 집계 |

봉투 하나의 압축 크기는 200KB까지 받는다. 넘으면 413으로 거절한다.

## 5.4 ingest가 하는 일

요청 하나에서 하는 일은 다섯 단계이고, 네트워크 왕복은 마지막 한 번뿐이다.

1. `Content-Length` 가 200KB를 넘으면 바로 413. 본문을 읽지 않는다.
2. 프로젝트 ID와 키를 로컬 캐시(Caffeine, 30초)에서 확인한다. 없는 키도 30초 동안 기억해 두어, 잘못된 키로 오는 요청이 매번 DB를 치지 않게 한다.
3. 브라우저 키라면 `Origin` 헤더가 프로젝트의 허용 목록에 있는지 본다.
4. Redis에 Lua 스크립트 하나를 실행한다. 스크립트 안에서 프로젝트 한도 차감, 대기열 길이 확인, 적재(XADD)를 한꺼번에 한다.
5. 결과에 따라 202, 429, 503 중 하나를 응답한다.

한도 확인과 적재를 스크립트 하나로 묶은 이유는 두 가지다. 왕복이 한 번으로 줄고, 확인과 적재 사이에 다른 요청이 끼어들지 못한다.

ingest는 본문의 압축을 풀지 않는다. 압축 해제와 JSON 해석은 CPU를 쓰는 일이고, 그 일은 worker의 몫이다. 대신 worker가 압축을 풀 때 출력 크기에 상한(2MB)을 걸어, 작게 압축된 거대한 본문을 걸러낸다.

| 응답 | 뜻 | SDK의 행동 |
| --- | --- | --- |
| 202 | 대기열에 들어감 | 다음 묶음 전송 |
| 413 | 봉투가 너무 큼 | 버리고 건수 기록 |
| 429 + Retry-After | 프로젝트 한도 초과 | 그 시간만큼 전송 중지, 그동안 생긴 것은 버리고 건수 기록 |
| 503 + Retry-After | 대기열이 가득 참 | 429와 같음 |
| 401, 403 | 키나 출처가 틀림 | 전송 중지, 로그 한 번 |

## 5.5 한도 두 가지

- **프로젝트 한도**: 프로젝트마다 분당 받을 건수. 토큰 버킷으로 구현한다. 한 프로젝트의 폭주가 다른 프로젝트의 자리를 빼앗지 못하게 한다.
- **대기열 길이 상한**: 전체 보호 장치. worker가 느려져 대기열이 상한에 닿으면, 한도가 남은 프로젝트도 503을 받는다. Redis 메모리가 차서 전체가 죽는 것보다 낫다.

대기열은 종류별로 두 개를 둔다. `errdeck:stream:events` 는 에러, `errdeck:stream:tx` 는 트랜잭션이다. 트랜잭션은 건수가 훨씬 많다. 하나로 합치면 트랜잭션 뒤에 에러가 줄을 서게 된다. 에러가 늦게 보이는 것이 더 큰 손해이므로 따로 둔다.

| 설정 | 처음 값 | 조정 기준 |
| --- | --- | --- |
| 프로젝트 한도 | 분당 6,000건, 순간 허용 1,000건 | 프로젝트별로 설정 화면에서 변경 |
| events 대기열 상한 | 20,000건 | Redis 메모리 사용량 실측 |
| tx 대기열 상한 | 20,000건 | 위와 같음 |
| Redis 메모리 상한 | 256MB, 초과 시 쓰기 거절(noeviction) | 14장의 메모리 예산 |

처음 값은 설정의 출발점이다. 18장의 실험에서 봉투의 실제 평균 크기를 재고 다시 맞춘다.

## 5.6 건수를 정확하게 유지하는 방법

버려진 것도 세어야 숫자가 맞는다. 버리는 곳마다 건수를 남긴다.

| 버리는 곳 | 건수를 남기는 방법 |
| --- | --- |
| SDK가 같은 에러를 접음 | 대표 이벤트 1건의 `count` 에 접힌 횟수를 담음 |
| SDK 큐가 넘침, 또는 429와 503을 받음 | client_report 항목으로 사유별 건수를 다음 전송 때 보냄 |
| worker가 이슈별 상한을 넘겨 원본을 저장하지 않음 | 분 단위 집계 테이블에는 건수를 그대로 더함 |

한계도 적어 둔다. SDK가 건수를 보내기 전에 감시 대상 프로세스가 죽으면 그 건수는 사라진다. 정확한 건수는 프로세스가 살아 있는 동안에만 보장한다.

## 5.7 버린 대안과 측정할 값

| 대안 | 버린 이유 |
| --- | --- |
| ingest에서 압축을 풀어 내용 검증 | 폭주 때 CPU가 ingest로 몰려 응답이 느려짐 |
| 프로젝트마다 대기열 하나 | 소비 쪽이 프로젝트 수만큼 읽기를 돌려야 함. 공정성은 프로젝트 한도로 이미 확보함 |
| ingest가 로컬 디스크에 쓰고 worker가 읽기 | 서버 1대에서는 빠르지만 프로세스가 볼륨을 공유해야 하고, 서버를 나눌 때 다시 만들어야 함 |

측정할 값은 ingest 응답 시간(p50, p99), 응답 코드별 건수, Lua 스크립트 실행 시간, 대기열 길이, 대기열에서 가장 오래된 항목의 나이다.
