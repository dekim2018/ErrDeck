# 6. 처리 파이프라인과 이슈 그룹핑

worker는 대기열에서 읽은 이벤트를 정규화하고, 지문을 계산해 이슈에 묶고, ClickHouse에 묶음으로 쓴다. 이 장의 핵심은 지문 규칙이다. 지문이 불안정하면 같은 버그가 배포할 때마다 새 이슈로 쪼개지고, 서비스 전체가 쓸모없어진다.

## 6.1 처리 단계

1. 읽기: 소비 그룹으로 대기열에서 묶음 단위로 읽는다.
2. 압축 해제와 해석: 출력 2MB 상한을 걸고 풀어 항목별로 나눈다.
3. 정규화: 필드 길이를 자르고, 스택 프레임을 250개로 제한하고, 민감한 값을 지운다(15장).
4. 중복 확인: SDK가 붙인 event_id를 이미 처리했는지 본다.
5. 소스맵 복원: 브라우저 이벤트만 해당한다(7장).
6. 지문 계산.
7. 이슈 찾기 또는 만들기.
8. 원본 저장 여부 결정: 이슈별 분당 상한을 넘으면 건수만 남긴다.
9. 묶음 쓰기: ClickHouse에 한 번에 넣는다.
10. 확인 처리와 알림 판정.

2번부터 6번까지는 CPU만 쓰는 일이고, 7번과 9번은 I/O다. 이 차이가 14장의 스레드 풀 설계로 이어진다.

## 6.2 고유 문제: 같은 버그가 다르게 보인다

스택트레이스 문자열을 그대로 해시하면 안 되는 이유는 다음과 같다.

| 흔들리는 원인 | 예 | 결과 |
| --- | --- | --- |
| 줄 번호 | 위쪽에 코드 한 줄을 추가하고 배포 | 모든 프레임의 줄 번호가 바뀜 |
| 프록시 클래스 이름 | `FanService$$SpringCGLIB$$0` 의 끝 숫자 | 실행할 때마다 다를 수 있음 |
| 람다 이름 | `lambda$settle$3` 의 끝 숫자 | 람다를 하나 추가하면 번호가 밀림 |
| 프레임워크 내부 프레임 | 스프링, 톰캣 버전 변경 | 내 코드는 그대로인데 스택이 달라짐 |
| 메시지 안의 값 | `User 1024 not found` | 사용자마다 다른 이슈가 됨 |
| 번들 파일 이름 | `index-BxK3a9.js` 의 해시 | 프론트를 빌드할 때마다 바뀜 |

## 6.3 지문 규칙

지문의 재료는 **예외 사슬의 각 예외 타입과, 앱 프레임의 클래스와 메서드 이름**이다. 이것을 이어 붙여 SHA-256으로 해시한다.

앱 프레임은 내 코드에 속한 프레임이다. SDK 설정의 패키지 목록(예: `com.livebroadcast`, `com.copage`)으로 판정한다. 브라우저에서는 `node_modules` 밖의 원본 파일이 앱 프레임이다.

| 규칙 | 처리 |
| --- | --- |
| 줄 번호와 열 번호 | 재료에서 뺀다 |
| 앱 프레임이 아닌 프레임 | 재료에서 뺀다 |
| CGLIB 프록시 | `$$SpringCGLIB$$` 와 뒤 숫자를 떼어 원래 클래스 이름으로 |
| JDK 프록시 | `$Proxy` 뒤 숫자를 뗀다 |
| 람다 | 메서드의 끝 번호, 클래스의 끝 번호와 주소를 뗀다 |
| 리플렉션 접근자 프레임 | 프레임을 뺀다 |
| 연속으로 반복되는 같은 프레임 | 하나로 접는다(무한 재귀 대응) |
| 브라우저 프레임 | 소스맵 복원 뒤의 원본 파일 경로와 함수 이름을 쓴다. 번들 파일 이름은 쓰지 않는다 |
| 앱 프레임이 하나도 없음 | 예외 타입과 값을 지운 메시지로 대신한다 |

값을 지운 메시지는 숫자, UUID, 16진수, 따옴표 안의 문자열을 자리 표시로 바꾼 것이다. `User 1024 not found` 는 `User <num> not found` 가 된다.

SDK를 쓰는 쪽이 직접 지문을 지정할 수도 있다. 예를 들어 결제사 타임아웃은 스택이 달라도 하나로 묶고 싶을 때 쓴다.

## 6.4 지문과 이슈를 분리해 두는 이유

이슈 하나가 지문 여러 개를 가질 수 있게 한다. PostgreSQL의 `issue_fingerprints(project_id, fingerprint, issue_id)` 가 이 대응을 가진다.

ClickHouse의 이벤트에는 issue_id를 넣지 않고 지문만 넣는다. 이 결정으로 얻는 것이 세 가지다.

- **병합과 분리가 싸다**: 이슈 두 개를 합칠 때 지문 행의 issue_id만 바꾼다. ClickHouse의 이벤트 수백만 건은 건드리지 않는다. ClickHouse는 이미 쓴 행의 수정이 비싸다.
- **규칙을 바꿀 수 있다**: 지문 규칙을 고치면 지문에 버전을 붙인다. 전환 기간에는 worker가 옛 규칙의 지문도 함께 계산한다. 옛 지문으로 이슈를 찾으면 새 지문을 그 이슈에 추가로 연결한다. 기존 이슈가 쪼개지지 않는다.
- **조회가 단순하다**: 이슈의 이벤트는 `fingerprint IN (지문 목록)` 으로 읽는다. 대부분 지문은 1개다.

## 6.5 이슈 찾기와 만들기

같은 새 지문의 이벤트가 동시에 여러 건 오면 이슈가 중복 생성될 수 있다. `issue_fingerprints` 의 유일 제약 (project_id, fingerprint) 과 `INSERT ... ON CONFLICT DO NOTHING` 으로 하나만 만들어지게 한다.

이벤트마다 PostgreSQL을 조회하지 않도록 worker는 지문과 이슈의 대응을 로컬 캐시에 둔다. 폭주 때는 거의 모든 이벤트가 같은 지문이므로 캐시 적중률이 높다.

이슈 행의 갱신도 문제다. 이벤트마다 `last_seen` 을 고치면 폭주 때 한 행에 수정이 몰린다. 그래서 다음과 같이 나눈다.

| 값 | 두는 곳 | 갱신 방식 |
| --- | --- | --- |
| 발생 횟수, 영향 사용자 수 | ClickHouse 집계 테이블 | 쓰기와 함께 자동 집계 |
| 최초 발생, 최근 발생, 최근 릴리스 | PostgreSQL 이슈 행 | 묶음 쓰기 한 번에 이슈당 한 번만 갱신 |

이슈 목록 화면은 PostgreSQL에서 최근 발생 순으로 25건을 읽고, 그 25건의 횟수를 ClickHouse 쿼리 한 번으로 가져와 합친다.

## 6.6 이슈 상태

| 지금 상태 | 일어난 일 | 다음 상태 |
| --- | --- | --- |
| 미해결 | 사용자가 해결로 표시(해결한 릴리스를 함께 기록) | 해결 |
| 미해결 | 사용자가 무시로 표시(기한 또는 횟수 조건) | 무시 |
| 해결 | 해결한 릴리스보다 나중 릴리스에서 이벤트 발생 | 재발 |
| 해결 | 해결한 릴리스보다 이전 릴리스에서 이벤트 발생 | 해결 유지 |
| 무시 | 기한이 지났거나 횟수 조건을 넘김 | 미해결 |
| 재발 | 사용자가 다시 해결로 표시 | 해결 |

넷째 줄이 이 서비스 고유의 판단이다. 브라우저는 사용자가 새로고침하기 전까지 옛 번들을 계속 실행한다. 버그를 고쳐 배포해도 옛 번들에서 같은 에러가 한동안 온다. 이것을 재발로 치면 고칠 때마다 거짓 재발 알림이 온다. 그래서 릴리스의 등록 순서를 비교해 나중 릴리스에서 온 것만 재발로 본다.

## 6.7 전달 보장과 중복

대기열은 적어도 한 번 전달이다. worker가 처리 중에 죽으면 확인되지 않은 항목을 다른 worker가 일정 시간 뒤에 가져간다(XAUTOCLAIM).

중복은 두 경로로 생긴다. SDK가 응답을 못 받아 다시 보낸 경우와, worker가 쓰기 뒤 확인 전에 죽은 경우다.

- 처리 전에 Redis에서 대기열 항목 ID를 확인하고, 쓰기에 성공한 뒤에 항목 ID를 10분 동안 기록한다. 같은 항목을 다시 가져간 경우가 이것으로 걸러진다. 묶음 안에서 같은 event_id가 두 번 오면 메모리에서 하나만 남긴다(29 작업에서 바꿈, 이 장 끝).
- worker가 쓰기와 기록 사이에 죽은 경우는 걸러지지 않는다. 이벤트 테이블은 같은 event_id를 병합 때 하나로 합치는 엔진을 써서 원본 중복은 나중에 사라진다. 집계 건수는 그 묶음만큼 많게 잡힐 수 있다.

이 한계는 받아들인다. 정확히 한 번을 보장하려면 쓰기와 확인을 하나의 트랜잭션으로 묶어야 하는데, Redis와 ClickHouse 사이에는 그런 수단이 없다. 18장의 장애 실험에서 worker를 강제로 죽여 실제 중복 건수를 잰다.

세 번 처리에 실패한 항목은 원문 그대로 격리 테이블로 옮기고 확인 처리한다. 해석할 수 없는 이벤트 하나가 대기열 전체를 막지 않게 하기 위해서다. 격리 건수는 화면과 지표에 보인다.

## 6.8 버린 대안과 측정할 값

| 대안 | 버린 이유 |
| --- | --- |
| 스택트레이스 전체 문자열 해시 | 6.2의 여섯 가지 원인에 전부 흔들림 |
| 맨 위 프레임 하나만 사용 | 공통 유틸 메서드에서 던지는 서로 다른 버그가 하나로 뭉침 |
| 메시지 유사도로 묶기 | 계산이 무겁고 결과를 설명하기 어려움. 왜 묶였는지 화면에 보여 줄 수 없음 |
| 이벤트에 issue_id 저장 | 병합할 때 ClickHouse 행을 대량 수정해야 함 |

측정할 값은 단계별 처리 시간, 지문 캐시 적중률, 묶음 크기, 격리 건수다. 지문 규칙은 수치보다 사례로 검증한다. 같은 버그를 줄 번호만 바꿔 다시 던졌을 때 한 이슈로 묶이는지를 규칙마다 테스트로 고정한다.

## 구현하면서 바뀐 점

05 작업에서 지문 규칙을 구현하면서 정한 것이다. 코드는 `core` 의 `com.errdeck.core.fingerprint` 에 있다.

- **지문의 모양**(사용자 확인): SHA-256의 앞 16바이트를 소문자 16진수 32자로 쓴다. 10.2의 `FixedString(32)` 에 그대로 들어가고 trace_id와 모양이 같다. 128비트라 충돌은 걱정하지 않는다.
- **재료의 형식**: 근거(`STACK`, `MESSAGE`, `CUSTOM`)를 첫 줄에 두고, 예외마다 `type:타입`, 그 아래 앱 프레임마다 `frame:클래스#메서드` 를 한 줄씩 붙인다. 근거를 붙여 서로 다른 근거의 재료가 우연히 같아지지 않게 한다. 규칙 버전은 재료에 넣지 않는다. 버전을 올려도 결과가 바뀌지 않는 입력은 같은 지문으로 남아야 전환 기간에 새 지문이 적게 생긴다.
- **반복 프레임 접기는 앱 프레임만 남긴 뒤에 한다**: 프레임워크 프레임을 사이에 두고 반복되는 재귀도 접힌다. CGLIB 프록시 프레임은 원래 클래스 이름이 되어 바로 아래의 같은 프레임과 접히므로, 프록시를 거친 호출과 거치지 않은 호출이 같은 지문이 된다.
- **앱 프레임 판정 순서**: SDK가 정한 `in_app` 이 있으면 따르고, 없으면 자바 프레임은 패키지 목록(하위 패키지 포함), 브라우저 프레임은 경로에 `node_modules/` 가 없는지로 정한다. 리플렉션 접근자 프레임은 `in_app` 과 상관없이 뺀다.
- **브라우저 프레임의 경로**: 주소의 출처(`https://호스트`)와 쿼리, 앞의 `./` 와 `/` 를 뗀다. 같은 원본 파일이 개발 서버와 배포 주소에서 달리 보이지 않게 하기 위해서다. 소스맵 복원과 복원하지 못했을 때의 대체 지문은 15 작업에서 한다.
- **앱 프레임이 없을 때**: 사슬의 모든 예외에 대해 타입과 값을 지운 메시지를 쓴다. 예외 없이 메시지만 보낸 이벤트는 값을 지운 메시지만 쓴다.
- **메시지 지우기의 범위**: 영문자 바로 뒤의 작은따옴표(`can't`)는 따옴표로 보지 않는다. 16진수는 `0x` 로 시작하거나 숫자와 a-f가 섞인 8자 이상만 지워 `deadbeef` 같은 단어는 남긴다. 식별자 안의 숫자(`utf8`, `IPv4`)는 지우지 않는다.
- **하지 않은 것**: 익명 클래스 번호(`Foo$1`)는 6.3의 규칙에 없어 그대로 둔다. 익명 클래스를 하나 더하면 지문이 바뀔 수 있다. 6.1의 정규화 중 필드 길이 자르기, 프레임 250개 제한, 민감한 값 지우기는 worker의 계산 단계를 만드는 07, 08 작업에서 한다.

07 작업에서 worker의 단계 구조를 구현하면서 정한 것이다. 코드는 `worker` 의 `com.errdeck.worker.app.Pipeline` 에 있다.

- **확인 처리 뒤에 지운다**: 쓰기에 성공한 묶음은 Lua 스크립트 하나로 XACK와 XDEL을 한다. ingest가 XLEN으로 대기열 길이를 보기 때문이다(5장 끝).
- **이어받기와 자기 손의 항목**: XAUTOCLAIM은 자기 worker가 아직 처리 중인 항목도 가져올 수 있다(ClickHouse가 멈춰 오래 쌓였을 때). 읽고 확인 처리하지 않은 항목의 ID를 worker 안에 들고 있다가 이어받은 항목이 그 안에 있으면 다시 넣지 않는다.
- **쓰기 큐의 길이는 대기열 항목 수로 센다**: 14.5의 10,000은 행이 아니라 계산을 마친 대기열 항목(봉투) 수다. 봉투 하나에 이벤트가 여러 건일 수 있어 행 수로는 이보다 많다. 묶음은 행 수(5,000)로 자른다.
- **이벤트가 없는 항목도 쓰기 스레드를 거친다**: 트랜잭션 봉투처럼 쓸 행이 없어도 앞선 묶음이 쓰인 뒤에 확인 처리해야 해서다.
- **쓰기에 실패하면**: 같은 묶음을 0.5초부터 두 배씩 늘려 최대 10초 간격으로 다시 쓴다. 다시 쓰는 동안 쓰기 큐를 비우지 않으므로 막힘이 앞 단계로 전해진다.
- **종료**: 스프링의 종료 단계 제한(30초)보다 3초 먼저 포기한다. 포기한 항목은 확인 처리하지 않으므로 대기열에 남아 이어받는다. 웹 서버보다 늦게 멈춰 종료 중에도 상태 확인과 지표를 볼 수 있다.
- **08 작업 전까지의 임시 처리**: 읽을 수 없는 봉투와 이벤트는 버리고 세어 둔다(격리는 08). 트랜잭션 항목은 확인 처리만 하고 저장하지 않는다(19). client_report도 아직 저장하지 않는다(08). 트랜잭션 대기열에 이벤트가 섞여 오면 그 이벤트는 저장한다.
- **사용자 해시**: 사용자 식별자의 SHA-256 앞 8바이트에서 맨 위 비트를 버린 63비트 값이다. ClickHouse의 UInt64 열에 JSON 숫자로 넣으려고 음수가 되지 않게 했다. 사용자가 없으면 0이다.

08 작업에서 이슈, 집계, 중복, 격리를 구현하면서 정한 것이다. 코드는 `worker` 의 `com.errdeck.worker.app.IssueBatchWriter` 에 있다.

- **중복 확인은 쓰기 단계에서 한다**: 6.1은 4번(중복 확인)을 계산 단계 앞에 두었지만 Redis를 묻는 I/O라 계산 스레드에 두지 않았다(14.5). 쓰기 스레드가 묶음마다 파이프라인 한 번으로 묻고, 같은 묶음 안에서 두 번 온 것도 뺀다. 처리했다는 표시는 ClickHouse 쓰기에 성공한 뒤에 남긴다.
- **쓰기 순서와 이어서 쓰기**: 중복 거르기, 이슈 찾기와 만들기, 원본 고르기, `events`, `event_ticks`, 처리 표시, 이슈 시각 갱신, 격리 순서다. 중간에 실패하면 같은 묶음을 다시 부르되 끝난 단계는 건너뛴다. 그래서 다시 써도 건수를 두 번 더하지 않고 분당 상한을 두 번 세지 않는다. 원본을 건수보다 먼저 쓰는 이유는 원본이 다시 쓰여도 같은 event_id로 합쳐지기 때문이다.
- **분당 상한은 worker가 처리한 시각의 분으로 나누고 worker마다 센다**: SDK의 시계가 틀려도 흔들리지 않는다. 10.6의 Redis 키 목록에 상한용 키가 없어 worker 안에서 센다. worker가 여러 대면 상한도 그 배수가 된다.
- **이슈 만들기**: 이슈 행을 넣고 지문 행을 `ON CONFLICT DO NOTHING` 으로 넣는다. 넣지 못하면 다른 worker가 먼저 만든 것이므로 트랜잭션을 되돌려 만든 이슈를 거두고 먼저 만든 이슈를 쓴다. 이슈 제목은 `예외 타입: 메시지`(200자), 발생 위치(culprit)는 맨 위 앱 프레임이다.
- **이슈 시각 갱신**: 최근 발생은 더 나중 시각일 때만, 최초 발생은 더 이를 때만 고친다. 옛 번들의 이벤트가 늦게 와도 되돌아가지 않는다.
- **접힌 이벤트의 횟수**: `event_ticks.count` 에 SDK가 보낸 `count` 를 그대로 넣는다. UInt32 열이라 그보다 크면 상한으로 자른다.
- **격리**: 봉투를 풀지 못하거나 처리 중 예외가 나면 계산 스레드가 그 자리에서 세 번까지 다시 해 보고 원문(압축된 봉투)을 격리한다. 봉투 안의 이벤트 하나만 틀리면 그 이벤트의 JSON만 격리하고 나머지는 처리한다. 격리 테이블의 7일 삭제는 아직 없다.
- **client_report는 아직 저장하지 않는다**: 저장할 테이블이 10장에 없다. 버린 건수를 화면에 보여 주는 작업에서 정한다.

15 작업에서 이슈 상태 전이(6.6)를 worker 에 붙였다. 재발은 릴리스의 등록 순서로 판정하고, 등록되지 않은 릴리스끼리는 이름이 다를 때만 재발로 본다. 무시는 기한이나 무시한 뒤의 발생 횟수로 풀린다. 자세한 규칙은 CHOICES 15-6, 15-7 이다. 재발 알림은 21 작업에서 한다.

29 작업(남은 부하 실험)에서 바꾼 것이다.

- **중복 확인은 대기열 항목 단위로, 10분**(사용자 확인): 처음에는 event_id마다 `errdeck:seen:{eventId}` 를 1시간 남겼다. 키 하나가 Redis에서 약 130바이트라 초당 5,000건이면 약 6.5분 만에 데이터 상한 256MB(14.7)에 닿았고, 초당 500건을 1시간 이어 가도 234MB였다. 조회 간섭 실험에서 실제로 상한을 넘었고, Redis가 쓰기를 거절해 ingest는 모든 프로젝트에 503을 주고 worker는 쓰기를 멈췄다. 두 SDK는 503이나 연결 실패에서 봉투를 다시 보내지 않고 버린 건수만 세므로(11장), 위에 적은 첫 번째 경로(SDK 재전송)는 지금 생기지 않는다. 남은 경로는 worker가 쓰기 뒤 확인 전에 죽어 같은 항목을 다시 가져가는 것뿐이라 항목 ID를 다시 가져가기(60초 유휴, 30초 주기)를 덮는 10분만 기억한다. 봉투 50건씩 초당 5,000건이면 키 6만 개, 약 8MB다.
- **감수하는 것**: 같은 event_id가 다른 봉투로 다시 들어오면 두 번 센다. 원본은 `events` 의 병합 엔진이 나중에 하나로 합친다. 재전송하는 SDK를 만들면 이 결정을 다시 본다.
