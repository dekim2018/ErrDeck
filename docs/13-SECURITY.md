# 15. 인증과 권한

이 서비스에 들어오는 주체는 넷이고 각각 인증 방식이 다르다. 콘솔 사용자는 JWT, SDK는 DSN 키, 빌드 스크립트는 프로젝트 토큰, 내부 도구는 공유 비밀을 쓴다. Spring Security에서는 경로별로 필터 체인을 나눠 이 넷이 섞이지 않게 한다.

## 15.1 주체와 인증 방식

| 주체 | 들어오는 곳 | 인증 | 할 수 있는 일 |
| --- | --- | --- | --- |
| 콘솔 사용자 | api의 `/api/**` | 액세스 토큰(JWT, 15분)과 리프레시 쿠키 | 역할에 따른 조회와 설정 |
| SDK | ingest의 `/ingest/**` | DSN 공개 키 | 이벤트 보내기만 |
| 빌드 스크립트 | api의 `/api/projects/*/releases/**` | 프로젝트 토큰 | 릴리스 등록과 소스맵 업로드만 |
| Alertmanager | api의 `/api/internal/alerts` | 공유 비밀 헤더 | 경보 전달만 |

## 15.2 api의 필터 체인

api에는 `SecurityFilterChain` 을 세 개 두고 `securityMatcher` 로 경로를 나눈다. 좁은 경로가 먼저 평가되도록 순서를 준다.

| 순서 | 경로 | 구성 |
| --- | --- | --- |
| 1 | `/api/internal/**` | 공유 비밀을 확인하는 필터 하나. 세션 없음 |
| 2 | `/api/projects/*/releases/**` 의 쓰기 요청 | 프로젝트 토큰 필터. 토큰의 SHA-256을 DB와 비교하고, 토큰의 프로젝트와 경로의 프로젝트가 같은지 확인 |
| 3 | `/api/**` | JWT 리소스 서버 설정. 세션 없음 |

체인을 하나로 합치고 조건문으로 나누면 한 경로의 설정 실수가 다른 경로에 번진다. 예를 들어 업로드 경로를 열어 주려다 조회 경로까지 열리는 식이다. 체인을 나누면 각 체인은 자기 경로만 책임진다.

콘솔 로그인은 앞의 두 프로젝트와 같은 방식을 쓴다.

- 액세스 토큰은 HS256 서명 JWT, 수명 15분이다. 검증은 Spring Security의 리소스 서버 기능에 맡기고 직접 필터를 만들지 않는다.
- 리프레시 토큰은 HttpOnly 쿠키에 담고 Redis에 저장한다. 쓸 때마다 새것으로 바꾼다. 이미 쓴 토큰이 다시 오면 탈취로 보고 그 사용자의 토큰을 전부 폐기한다.
- 액세스 토큰을 헤더로 보내므로 `/api/**` 는 CSRF 대상이 아니다. 쿠키를 쓰는 재발급 경로만 SameSite 설정과 경로 제한으로 보호한다.
- 비밀번호는 Spring Security의 위임 인코더로 해시한다. 로그인 실패가 반복되면 응답을 늦춘다.

## 15.3 ingest에는 Spring Security를 넣지 않는다

ingest의 인증은 서블릿 필터 하나로 구현한다. 이유는 세 가지다.

- DSN 키는 비밀이 아니라 식별자다. 사용자, 역할, 권한이라는 개념이 없다.
- ingest는 요청당 하는 일을 최소로 줄인 프로세스다(5.4). 쓰지 않는 필터 십여 개를 매 요청이 지나갈 이유가 없다.
- 의존성이 줄면 ingest의 시작 시간과 메모리도 준다.

대신 ingest는 관리 포트 말고는 `/ingest/**` 하나만 연다. 열린 경로가 하나뿐이라 실수로 열릴 것이 없다.

## 15.4 권한

권한은 시스템 단위로 준다. 팬파라이브의 구성원이 되면 그 안의 프로젝트 6개를 모두 본다.

| 역할 | 조회 | 이슈 상태 변경, 댓글 | 알림 규칙, 모니터, 릴리스 | 키와 토큰, 구성원, 한도 |
| --- | --- | --- | --- | --- |
| VIEWER | 가능 | 불가 | 불가 | 불가 |
| MEMBER | 가능 | 가능 | 불가 | 불가 |
| ADMIN | 가능 | 가능 | 가능 | 불가 |
| OWNER | 가능 | 가능 | 가능 | 가능 |

권한 검사는 두 곳에서 한다. 컨트롤러 메서드에는 메서드 보안으로 역할을 확인한다. ClickHouse 쿼리는 쿼리 생성기 한 곳에서 사용자가 볼 수 있는 프로젝트 ID 목록을 조건에 강제로 넣는다. 컨트롤러 하나에서 검사를 빠뜨려도 다른 시스템의 데이터가 나가지 않게 하는 두 번째 방어선이다.

## 15.5 DSN 키 보호

브라우저용 키는 누구나 볼 수 있다. 키를 숨기는 대신 키로 할 수 있는 일을 좁힌다.

- 프로젝트마다 허용 출처 목록을 두고 `Origin` 헤더를 확인한다. 브라우저 밖에서는 헤더를 꾸밀 수 있으므로 이것만으로는 부족하다.
- 프로젝트 한도(5.5)가 실제 방어선이다. 키를 훔쳐 쓰레기를 보내도 그 프로젝트의 한도까지만 들어온다.
- 키는 폐기하고 새로 발급할 수 있다. 교체하는 동안 옛 키와 새 키가 함께 유효한 기간을 둔다.

## 15.6 민감한 정보 지우기

에러 이벤트에는 요청 정보가 따라온다. 팬파라이브는 로그인과 결제를 다루므로 토큰이나 결제 정보가 섞여 들어올 수 있다. 두 번 지운다.

| 단계 | 지우는 것 |
| --- | --- |
| SDK(보내기 전) | `Authorization`, `Cookie`, `Set-Cookie` 헤더. 이름에 password, token, secret, card, key가 들어간 필드. 요청 본문은 기본으로 보내지 않음 |
| worker(저장 전) | 같은 규칙을 한 번 더. 카드 번호 형태의 숫자열. SQL 스팬의 값 |

SDK에서 먼저 지우는 이유는 민감한 값이 네트워크를 건너지 않는 것이 가장 안전하기 때문이다. worker에서 다시 지우는 이유는 옛 버전 SDK나 설정 실수를 믿을 수 없기 때문이다.

접속 IP는 저장하지 않는다. 사용자 식별자는 10.2에 적은 대로 해시를 열로 두고, 원래 값은 이벤트 원본 안에만 둔다.

소스맵에는 원본 코드가 들어 있다. 소스맵을 내려받는 API는 만들지 않고, 화면에는 문제 프레임의 앞뒤 5줄만 보인다.

## 15.7 관측 도구의 접근

| 도구 | 외부 노출 | 인증 |
| --- | --- | --- |
| Prometheus | 원격 쓰기 경로만 Caddy로 노출 | Caddy의 기본 인증 |
| Grafana | `/grafana/` 경로로 노출 | Grafana 자체 로그인 |
| Alertmanager, exporter, 관리 포트 | 노출하지 않음 | 도커 내부 네트워크 |

콘솔 로그인과 그라파나 로그인을 하나로 합치는 것은 이번 범위에서 뺀다. 포트폴리오 4번 후보인 통합 인증 서버를 만들게 되면 그때 연결한다.
