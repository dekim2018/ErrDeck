# 9. 업타임 점검

worker가 등록된 주소를 주기적으로 호출해 살아 있는지 확인하고, 연속 2회 실패하면 다운으로 판정해 장애 기록을 연다. 에러 수집과 달리 감시 대상이 아무것도 보내지 않아도 동작하는 유일한 기능이다. 프로세스가 통째로 죽으면 에러도 오지 않기 때문에 이 기능이 필요하다.

## 9.1 모니터 설정

| 항목 | 값 |
| --- | --- |
| 주소와 메서드 | 예: `GET https://fanpalive.duckdns.org/actuator/health` |
| 주기 | 30초, 1분, 5분 중 선택. 처음 값 1분 |
| 제한 시간 | 5초 |
| 성공 조건 | 상태 코드 범위(처음 값 200에서 299). 선택으로 본문에 포함될 문자열 |
| 일시 중지 | 수동 중지, 또는 점검하지 않을 시간대 |

일시 중지는 실제 운영 사정 때문에 넣는다. 팬파라이브 서버는 비용 때문에 평소 꺼 둔다. 중지 기능이 없으면 장애 기록과 알림이 계속 쌓이고 가동률이 의미를 잃는다. 중지된 구간은 가동률 계산에서 뺀다.

## 9.2 실행 구조

1. 모니터의 다음 실행 시각을 Redis 정렬 집합에 점수로 넣어 둔다.
2. worker가 1초마다 Lua 스크립트로 실행할 때가 된 모니터를 꺼내고, 같은 스크립트 안에서 다음 실행 시각으로 점수를 바꾼다. worker가 여러 대여도 같은 모니터를 두 번 실행하지 않는다.
3. 꺼낸 모니터마다 가상 스레드 하나로 HTTP 호출을 한다. 점검은 대부분 응답을 기다리는 시간이므로 가상 스레드에 맞는다.
4. 동시에 실행하는 점검 수는 세마포어로 50개까지 제한한다.
5. 결과를 ClickHouse에 쓰고, 상태가 바뀌었으면 PostgreSQL의 모니터와 장애 기록을 갱신한다.

모니터마다 첫 실행 시각을 ID의 해시로 흩어 놓는다. 전부 매분 0초에 실행하면 그 순간에만 부하가 몰리고, 점검 응답 시간에 서로 영향을 준다.

## 9.3 판정

| 지금 상태 | 일어난 일 | 결과 |
| --- | --- | --- |
| 정상 | 1회 실패 | 상태 유지. 주기를 기다리지 않고 10초 뒤 다시 점검 |
| 정상 | 연속 2회 실패 | 다운. 장애 기록을 열고 알림 |
| 다운 | 1회 성공 | 상태 유지. 10초 뒤 다시 점검 |
| 다운 | 연속 2회 성공 | 정상. 장애 기록을 닫고 복구 알림 |

1회 실패로 판정하지 않는 이유는 일시적인 네트워크 끊김과 배포 중 재시작 때문이다. 바로 다시 점검하는 이유는 판정이 주기만큼 늦어지지 않게 하기 위해서다. 주기가 1분이어도 다운 판정은 약 10초 뒤에 나온다.

인증서 만료일도 함께 본다. HTTPS 응답의 인증서에서 만료일을 읽어 14일 이내면 알린다. 팬파라이브는 Caddy가 자동 갱신하지만, 갱신이 실패했을 때 알 방법이 필요하다.

## 9.4 고유 문제: 점검기가 공격 도구가 될 수 있다

모니터 주소는 사용자가 입력한다. 누군가 `http://169.254.169.254/` 같은 클라우드 내부 주소나 `http://redis:6379/` 같은 내부망 주소를 넣으면, worker가 대신 호출해 준다. 서버 쪽 요청 위조(SSRF)다.

- 주소의 호스트를 직접 DNS로 해석해 얻은 IP가 사설 대역, 루프백, 링크 로컬이면 거부한다.
- 검사한 IP로 직접 연결한다. 검사할 때와 연결할 때 DNS 응답이 달라지는 수법을 막는다.
- 리다이렉트는 따라가지 않는다.
- 로컬 개발에서는 같은 도커 네트워크의 서비스를 점검해야 하므로, 허용할 내부 호스트 목록을 설정으로 둔다.

## 9.5 한계

| 한계 | 대응 |
| --- | --- |
| 관측 지점이 한 곳이다. 이 서버의 네트워크가 끊기면 모든 대상이 다운으로 보인다 | 모니터의 절반 이상이 같은 시각에 실패하면 개별 알림을 보류하고 점검기 이상 한 건만 알린다 |
| 이 서비스가 죽으면 아무도 알리지 않는다 | Alertmanager가 worker의 생존 지표를 본다(13장). 서버 전체가 죽는 경우는 서버 1대 구성의 한계로 남긴다 |
| 응답 시간이 이 서버와 대상 사이의 거리를 포함한다 | 절대값보다 추세로 본다 |

## 9.6 버린 대안과 측정할 값

| 대안 | 버린 이유 |
| --- | --- |
| 프로메테우스 blackbox exporter | 점검 자체는 잘한다. 다만 장애 기록, 일시 중지, 프로젝트와의 연결을 화면에서 다루려면 결과를 다시 가져와 저장해야 한다 |
| 스프링 `@Scheduled` 로 모니터 전체를 한 번에 순회 | 느린 대상 하나가 뒤의 점검을 전부 늦춘다. worker를 늘리면 중복 실행된다 |
| 1회 실패로 즉시 다운 판정 | 거짓 알림이 많아져 알림을 믿지 않게 된다 |

측정할 값은 예정 시각과 실제 실행 시각의 차이, 동시 실행 수, 점검 응답 시간 분포다.
