# 16. 알림

알림은 믿을 수 있어야 쓸모가 있다. 장애 때 알림이 수백 건 쏟아지면 사람은 채널을 꺼 버린다. 그래서 알림 설계의 대부분은 보내는 방법이 아니라 보내지 않는 방법이다.

## 16.1 규칙 종류

| 규칙 | 조건 | 판정하는 곳 |
| --- | --- | --- |
| 새 이슈 | 처음 보는 지문으로 이슈가 생김 | worker의 쓰기 단계. 이슈를 만든 그 순간 |
| 재발 | 해결한 이슈가 재발 상태로 바뀜(6.6) | 위와 같음 |
| 빈도 초과 | 한 이슈가 N분 동안 M건 이상 | worker가 30초마다 분 단위 집계를 조회 |
| 응답 지연 | 엔드포인트의 p95가 기준 초과 | 프로메테우스 규칙. Alertmanager로 전달 |
| 다운과 복구 | 모니터 상태 변경(9.3) | worker의 점검 결과 처리 |
| 인증서 만료 임박 | 만료까지 14일 이내 | 위와 같음 |
| 자원 경보 | 13.6의 8개 규칙 | 프로메테우스 규칙. Alertmanager로 전달 |

## 16.2 고유 문제: 장애 때 알림도 폭주한다

| 상황 | 억제 방법 |
| --- | --- |
| 같은 이슈가 계속 조건을 넘김 | 규칙과 이슈의 쌍마다 재알림 간격(처음 값 30분) |
| 배포 직후 새 이슈가 한꺼번에 20개 생김 | 같은 프로젝트의 새 이슈는 1분 동안 모아 한 메시지로 요약 |
| worker가 여러 대라 같은 판정을 동시에 함 | 알림 기록 테이블의 유일 제약으로 한 건만 통과 |
| 채널의 수신 한도 초과 | 채널별 분당 상한. 넘는 것은 요약 한 건으로 |
| 점검기 자신의 네트워크 문제 | 모니터 절반 이상이 동시에 실패하면 개별 알림 보류(9.5) |

셋째 줄의 구현은 다음과 같다. 알림을 보내기 전에 `notifications` 테이블에 (규칙 ID, 중복 방지 키)를 넣는다. 중복 방지 키는 이슈 ID와 재알림 간격으로 나눈 시간 구간 번호다. 넣는 데 성공한 worker만 발송한다. 재알림 간격과 다중 worker 중복이 제약 하나로 함께 해결된다.

## 16.3 발송

1. 판정한 곳이 알림을 `errdeck:stream:notify` 에 넣는다. 판정과 발송을 분리해, 외부 채널이 느려도 이벤트 처리가 늦어지지 않게 한다.
2. 발송 담당이 가상 스레드로 꺼내 보낸다. 동시 발송은 10건으로 제한한다.
3. 제한 시간은 5초다. 실패하면 간격을 늘려 가며 3회까지 다시 시도하고, 끝내 실패하면 기록에 남긴다.

| 채널 | 방식 | 비고 |
| --- | --- | --- |
| Slack, Discord | 웹훅 | 주소는 사용자가 입력하므로 9.4의 내부 주소 검사를 똑같이 적용 |
| 이메일 | SMTP | 클라우드에 따라 25번 포트가 막혀 있으므로 587번 포트의 외부 SMTP를 쓴다 |

알림 한 건에는 제목, 발생 횟수, 영향 사용자 수, 맨 위 앱 프레임, 릴리스, 콘솔의 해당 화면 링크를 담는다. 링크를 누르면 바로 그 이슈나 장애 기록이 열린다.
