# 작업 중에 정한 것

사용자에게 묻지 않고 Claude가 추천안으로 정한 것을 모은다. 나중에 한꺼번에 검토하고 리팩토링할 때 이 문서를 본다.

항목마다 고른 것, 다른 선택지, 고른 이유, 바꾸려면 어디를 고치는지를 적는다. 설계 문서의 빈칸을 채운 결정은 해당 장 끝의 "구현하면서 바뀐 점"에도 짧게 남아 있다. 사용자가 직접 고른 것(03의 스트림 구분, 05의 지문 길이, 09의 gateway 등록 등)은 여기에 적지 않는다.

## 09 Starter SDK

### 09-1. WebFlux에서는 필터까지 올라온 예외만 잡는다

- **고른 것**: `WebFilter` 의 `doOnError` 로 처리되지 않고 올라온 예외만 보낸다. `ErrorResponse` 이고 상태가 500 미만이면 보내지 않는다.
- **다른 선택지**: (가) `@ExceptionHandler` 가 처리한 예외까지 잡으려고 `DispatcherHandler` 나 `HandlerResultHandler` 를 감싸기. (나) `ErrorWebExceptionHandler` 를 감싸 최종 상태 코드를 보고 보내기.
- **이유**: 대상인 팬파라이브 gateway는 컨트롤러가 거의 없고 오류 대부분이 경로 처리와 뒤쪽 호출에서 나서 필터까지 올라온다. (가)는 WebFlux 내부 구조에 깊이 기대고, (나)는 Spring Cloud Gateway가 자기 예외 처리기를 두므로 순서가 엇갈리기 쉽다.
- **바꾸려면**: `sdk-spring/.../webflux/ErrDeckWebFilter.java`.

### 09-2. WebFlux에서는 사용자 ID를 보내지 않는다

- **고른 것**: `RequestContext.userId` 를 비운다.
- **다른 선택지**: `exchange.getPrincipal()` 을 오류 흐름에 엮어 비동기로 꺼낸다.
- **이유**: 사용자는 비동기로만 꺼낼 수 있고, 리액터 스레드에서 기다리면 안 된다. 오류 흐름을 바꾸지 않는 쪽을 골랐다. 영향 사용자 수는 gateway 뒤 서비스의 이벤트로 셀 수 있다.
- **바꾸려면**: 같은 파일의 `snapshot`.

### 09-3. 같은 에러 접기의 비교 기준은 요청 스레드에서 만드는 가벼운 열쇠다

- **고른 것**: 예외 사슬(최대 5단계)의 클래스와 각 위쪽 20프레임(`StackTraceElement`, 줄 번호 포함)을 그대로 비교한다. 지문 규칙(6.3)을 쓰지 않는다.
- **다른 선택지**: core의 `Fingerprinter` 로 지문을 계산해 비교하기. 전송 스레드에서 접기.
- **이유**: 접기는 큐에 넣기 전에 해야 폭주 때 큐와 네트워크를 지킨다(5.1). 요청 스레드에서 프레임을 변환하고 해시하는 비용을 피했다. 같은 코드의 같은 줄에서 쏟아지는 경우가 접기의 대상이라 줄 번호까지 같아도 충분하다.
- **바꾸려면**: `sdk-spring/.../Folder.java` 의 `Signature`.

### 09-4. 같은 예외 객체를 여러 경로가 잡으면 한 번만 보낸다

- **고른 것**: 최근에 잡은 예외 객체를 약한 참조로 최대 1,000개 기억하고, 같은 객체는 다시 넣지 않는다.
- **다른 선택지**: 경로마다 "이미 보냄" 표시를 예외에 붙이기(억제된 예외 사용 등). 중복을 허용하고 worker의 지문으로 합치기.
- **이유**: 리졸버, 필터, 로그 어펜더가 같은 예외를 함께 보는 일이 흔하다(전역 처리기가 `log.error(e)` 를 남기는 경우). 예외 객체를 바꾸지 않고 막을 수 있다.
- **바꾸려면**: `ErrDeckClient.capture` 의 `recent`.

### 09-5. Retry-After가 없는 429, 503은 60초 쉰다

- **고른 것**: 기본 60초. 쉬는 동안 생긴 것은 버리고 이유별로 센다.
- **다른 선택지**: 짧게(5초) 쉬기, 늘려 가며 쉬기.
- **이유**: ingest는 항상 Retry-After를 주므로(03) 이 값은 다른 프록시가 끼었을 때만 쓰인다. 넘쳐 있는 서버를 다시 두드리지 않는 쪽을 골랐다.
- **바꾸려면**: `Sender.DEFAULT_PAUSE`.

### 09-6. 401, 403을 받으면 프로세스가 다시 뜰 때까지 보내지 않는다

- **고른 것**: 전송을 멈추고 로그를 1분에 한 번 남긴다. 이후 생긴 것은 `unauthorized` 로 센다.
- **다른 선택지**: 일정 간격으로 다시 시도하기.
- **이유**: 5.4의 "전송 중지, 로그 한 번"을 따랐다. 키가 바뀌면 설정을 고쳐 다시 띄우므로 다시 시도할 이유가 적다.
- **바꾸려면**: `Sender.handle`.

### 09-7. 연결 실패는 바로 한 번 다시 보낸다

- **고른 것**: `IOException` 이면 기다리지 않고 한 번 더 보내고, 그래도 실패하면 버리고 `network_error` 로 센다.
- **다른 선택지**: 잠깐 기다렸다 다시 보내기, 실패한 묶음을 다음 묶음에 다시 싣기.
- **이유**: 11.1의 "재시도 1회"를 가장 단순하게 따랐다. 다음 묶음에 싣는 방식은 큐 밖에 묶음을 쌓아 메모리 상한을 흐린다.
- **바꾸려면**: `Sender.send`.

### 09-8. 스케줄러의 오류 처리기는 덮어쓰고, 비동기 설정은 감시 대상에 없을 때만 넣는다

- **고른 것**: `ThreadPoolTaskScheduler`, `SimpleAsyncTaskScheduler` 빈에 오류 처리기를 넣는다(잡아서 보낸 뒤 기본 동작대로 로그를 남기고 다음 실행을 계속). `AsyncConfigurer` 는 감시 대상에 없을 때만 넣는다.
- **다른 선택지**: 로그 어펜더에만 맡기기(스프링이 두 경우 모두 ERROR 로그를 남긴다).
- **이유**: 11.2가 두 경로를 따로 적었다. 스케줄러에 오류 처리기를 직접 정한 감시 대상은 덮어쓰이는데, 팬파라이브와 CoPage는 정하지 않았다.
- **바꾸려면**: `ErrDeckAutoConfiguration` 의 `errDeckSchedulerErrorHandler`, `errDeckAsyncConfigurer`.

### 09-9. SDK 안에서도 프레임 250개, 사슬 10단계, 메시지 8KB로 자른다

- **고른 것**: 보내기 전에 자른다.
- **다른 선택지**: worker에서만 자르기(6.1).
- **이유**: 봉투 상한 200KB(5.3)를 넘겨 413을 받는 일을 줄이고 네트워크로 보내는 양부터 줄인다. worker의 정규화는 그대로 한다.
- **바꾸려면**: `EventBuilder` 의 상수.

### 09-10. 패키지 목록이 없으면 `in_app` 을 보내지 않는다

- **고른 것**: `in-app-packages` 가 비어 있으면 프레임의 `in_app` 을 비워 worker가 판정하게 한다.
- **다른 선택지**: 비어 있으면 모두 앱 프레임으로 보기.
- **이유**: 모두 앱 프레임으로 보면 프레임워크 프레임까지 지문에 들어가 버전을 올릴 때마다 이슈가 갈라진다(6.2).
- **바꾸려면**: `EventBuilder.inApp`.

### 09-11. SDK 자신의 로그는 JDK의 System.Logger로, 같은 문제는 1분에 한 번 남긴다

- **고른 것**: 로거 이름 `com.errdeck.sdk.internal`. 로그 어펜더는 이 이름만 정확히 건너뛴다.
- **다른 선택지**: SLF4J를 쓰기, 패키지 접두사로 건너뛰기.
- **이유**: SDK가 로깅 라이브러리에 기대지 않게 했다. 처음에는 `com.errdeck.sdk` 로 시작하는 로그를 모두 건너뛰었는데, 그 패키지의 사용자 코드(테스트)까지 걸러져 정확한 이름 비교로 바꿨다.
- **바꾸려면**: `InternalLog`, `ErrDeckAppender`.

### 09-12. client_report의 종류는 항상 event다

- **고른 것**: 버린 건수의 `category` 를 `event` 로 둔다.
- **다른 선택지**: 트랜잭션을 보내기 시작하면(18) `transaction` 을 나눠 세기.
- **이유**: 지금 SDK는 에러만 보낸다. 18 작업에서 트랜잭션을 더할 때 나눈다.
- **바꾸려면**: `Discards.drain`.

### 09-13. SDK는 core를 그대로 의존한다

- **고른 것**: `sdk-spring` 이 `core` 를 `api` 의존성으로 가진다. 감시 대상은 core도 함께 받는다.
- **다른 선택지**: 봉투와 이벤트 모델만 SDK 안에 따로 두기.
- **이유**: SDK와 worker가 같은 코드로 형식을 맞춘다(02). core는 JDK만 쓰므로 감시 대상의 의존성과 부딪치지 않는다. 패키지를 어디에 올릴지는 20장의 미정 사항이다.
- **바꾸려면**: `sdk-spring/build.gradle.kts`.

## 10 데모 앱

### 10-1. 데모 프로젝트의 ID와 키를 9001, 9002로 고정한다

- **고른 것**: `scripts/demo/seed.sql` 이 `OVERRIDING SYSTEM VALUE` 로 프로젝트 ID 9001(demo-api), 9002(demo-web)와 키 `demoapikey`, `demowebkey` 를 넣는다. 여러 번 실행해도 같다.
- **다른 선택지**: 넣을 때 받은 ID로 DSN을 만들어 출력하는 스크립트, api의 프로젝트 관리 API(11)로 만들기.
- **이유**: 데모 앱의 설정 파일에 DSN을 고정해 두면 compose와 테스트가 단순하다. 일반 프로젝트의 ID는 1부터 늘어나므로 9001에 닿기 전까지 겹치지 않는다.
- **바꾸려면**: `scripts/demo/seed.sql`, `demo-api/src/main/resources/application.yml` 의 `errdeck.dsn`.

### 10-2. compose의 데모 앱은 미리 만든 jar를 이미지에 담는다

- **고른 것**: `./gradlew :demo-api:bootJar :loadgen:installDist` 를 먼저 하고, Dockerfile은 그 결과를 `eclipse-temurin:25-jre` 에 복사만 한다.
- **다른 선택지**: Dockerfile 안에서 Gradle로 빌드하는 다단계 빌드.
- **이유**: 이미지 빌드마다 Gradle과 의존성을 내려받지 않아 빠르다. 16 작업에서 ingest, worker, api의 Dockerfile을 만들 때 같은 방식을 쓸지 다시 정한다.
- **바꾸려면**: `demo-api/Dockerfile`, `loadgen/docker/Dockerfile`.

### 10-3. 16 작업 전까지 compose의 데모 앱은 호스트의 ingest로 보낸다

- **고른 것**: `DEMO_ERRDECK_DSN` 의 기본값을 `host.docker.internal:8080` 으로 둔다.
- **다른 선택지**: 이번 작업에서 ingest도 compose에 올리기.
- **이유**: 프로세스의 컨테이너 등록은 16 작업의 범위다. 그때 기본값을 compose 안의 ingest로 바꾼다.
- **바꾸려면**: `docker-compose.yml` 의 `demo-api.environment`.

### 10-4. SDK 부담은 loadgen의 새 시나리오 `http` 로 잰다

- **고른 것**: 임의 주소에 GET을 정해진 속도로 보내는 `http` 시나리오를 더하고, 같은 jar를 SDK 켬과 끔으로 두 개 띄워 번갈아 잰다.
- **다른 선택지**: 앱 안에서 필터 시간을 재는 마이크로 벤치마크(JMH).
- **이유**: 2.2의 목표가 요청 시간의 차이이므로 바깥에서 본 응답 시간으로 잰다. 같은 맥에서는 잡음이 커서 1ms 이하는 가리지 못했다(EXPERIMENTS.md). 17 작업에서 기계를 나눠 다시 잰다.
- **바꾸려면**: `loadgen` 의 `Scenario.HTTP`, `Runner.requests`.

### 10-5. 데모 앱의 스케줄 예외는 켜고 끌 수 있고 기본 60초다

- **고른 것**: `demo.scheduled-failure.enabled`(기본 켬), `interval`(기본 60초).
- **이유**: 화면에서 스케줄 경로의 이슈를 볼 수 있게 켜 두되, 부담 실험에서는 측정에 섞이지 않게 끈다.

## 11 로그인과 권한

### 11-1. 처음 가입한 사용자가 관리자가 되고, 가입은 열어 둔다

- **고른 것**: `users.role` 이 ADMIN 인 사용자만 시스템을 만들 수 있다. 처음 가입한 사용자가 ADMIN 이 된다(동시에 가입해도 잠금으로 한 명). 가입은 `ERRDECK_SIGNUP_ENABLED=false` 로 막을 수 있다.
- **다른 선택지**: 설정의 관리자 이메일 목록, 초대받은 사람만 가입.
- **이유**: 혼자 운영하는 도구라 처음 띄운 사람이 관리자인 것이 가장 단순하다. 배포한 뒤에는 가입을 막는다(25 작업).
- **바꾸려면**: `JdbcUserRepository.create`, `errdeck.auth.signup-enabled`.

### 11-2. 로그아웃해도 액세스 토큰은 만료(15분)까지 쓸 수 있다

- **고른 것**: 로그아웃과 탈취 감지는 리프레시 토큰만 지운다. 이미 내준 액세스 토큰을 막는 목록은 두지 않는다.
- **다른 선택지**: CoPage처럼 Redis에 막은 토큰 ID와 사용자별 무효 시각을 두고 JWT 검증기에서 확인하기.
- **이유**: 10.6의 Redis 키 목록에 리프레시 토큰만 있고, 액세스 토큰이 15분으로 짧다. 요청마다 Redis를 묻지 않아도 된다.
- **바꾸려면**: `SecurityConfig.jwtDecoder` 에 검증기를 더하고 `AuthService.logout`, `refresh` 의 탈취 처리에서 막는다.

### 11-3. 구성원이 아니면 404, 역할이 모자라면 403

- **고른 것**: 다른 시스템의 프로젝트, 이슈, 키에는 404 를 준다.
- **다른 선택지**: 모두 403.
- **이유**: 403 은 그런 것이 있다는 사실을 알려 준다. 다른 시스템의 ID를 차례로 넣어 보는 것으로 무엇이 있는지 알아낼 수 없게 한다.
- **바꾸려면**: `AccessPolicy`.

### 11-4. 권한 표의 "알림 규칙, 모니터, 릴리스" 칸은 테스트용 엔드포인트로 먼저 확인한다

- **고른 것**: 이 칸의 API는 15, 20, 21 작업에서 생긴다. 지금은 같은 `AccessPolicy` 를 거치는 테스트 전용 엔드포인트로 역할 4개를 확인한다.
- **다른 선택지**: 이 작업에서 알림 규칙이나 모니터 API를 미리 만들기.
- **이유**: 뒤 작업의 범위를 미리 만들지 않는다(WORKFLOW 1.5). 그 작업에서 실제 API를 권한 표 테스트에 더한다.
- **바꾸려면**: `PermissionMatrixTest.AdminColumn`.

### 11-5. 로그인 실패는 잠그지 않고 늦추며, api 프로세스 안에서 센다

- **고른 것**: 같은 이메일로 10분 안에 5번 실패하면 이후 시도마다 1초씩 늦춘다. 세는 표는 메모리에 두고 1만 개를 넘으면 비운다.
- **다른 선택지**: 계정 잠금, Redis에 세기.
- **이유**: 잠그면 남이 일부러 틀려 주인을 막을 수 있다. api는 한 대라 메모리로 충분하다.
- **바꾸려면**: `LoginThrottle`, `errdeck.auth.failures-*`.

### 11-6. 프로젝트 만들기와 프로젝트 설정(한도, 허용 출처), 키 보기는 OWNER 만 한다

- **고른 것**: 15.4의 "키와 토큰, 구성원, 한도" 칸에 프로젝트 만들기와 허용 출처 바꾸기, 키 목록 보기를 함께 넣었다.
- **다른 선택지**: 프로젝트 만들기를 ADMIN 에게, 키 보기를 모든 구성원에게.
- **이유**: 프로젝트를 만들면 한도와 키가 함께 생기고, 허용 출처는 키를 지키는 장치(15.5)라 같은 칸에 두었다. DSN 키는 비밀이 아니지만 폐기와 함께 관리하는 것이 자연스럽다.
- **바꾸려면**: `WorkspaceService` 의 `createProject`, `updateProject`, `keys`.

### 11-7. JWT 서명 키와 내부 공유 비밀의 로컬 기본값을 설정 파일에 둔다

- **고른 것**: `application.yml` 에 로컬 개발용 값을 두고, 배포 환경은 `ERRDECK_JWT_SECRET`, `ERRDECK_INTERNAL_SECRET` 으로 바꾼다.
- **다른 선택지**: CoPage처럼 값이 없으면 api 가 뜨지 않게 하고 개발 프로필에만 기본값 두기.
- **이유**: 지금까지의 실행 방법(`bootRun`, 테스트)을 바꾸지 않는다. 25 작업에서 배포 설정에 반드시 넣는다.
- **바꾸려면**: `api/src/main/resources/application.yml` 의 `errdeck.auth`.

### 11-8. DSN 키 폐기의 유예 시간은 요청마다 정하고 기본 0이다

- **고른 것**: `DELETE /api/projects/{id}/keys/{keyId}?graceMinutes=60`. 폐기 시각을 그만큼 미래로 잡는다.
- **이유**: 15.5의 교체 기간을 요청하는 쪽이 정한다. ingest가 키를 30초 기억하므로 0이어도 최대 30초는 더 받는다.

### 11-9. 사용자가 바꿀 수 있는 이슈 상태는 미해결, 해결, 무시뿐이다

- **고른 것**: 재발(regressed)은 worker가 정한다. 해결할 때 해결한 릴리스를, 무시할 때 기한을 함께 받는다.
- **이유**: 6.6의 표에서 재발은 이벤트가 정하는 상태다. 재발 판정과 상태 전이 전체는 15 작업에서 한다.

### 11-10. Alertmanager 경보는 받기만 하고 로그를 남긴다

- **고른 것**: `/api/internal/alerts` 는 202 를 주고 로그를 남긴다.
- **이유**: 경보를 알림으로 보내는 일은 21 작업이다. 이번에는 첫째 필터 체인을 확인할 곳이 필요했다.

### 11-11. ClickHouse 조회의 값은 모두 쿼리 매개변수로 넘긴다

- **고른 것**: `ScopedQuery` 가 프로젝트 목록과 기간을 `{scope_*:타입}` 매개변수로 넣고, 추가 조건의 값도 매개변수로만 받는다. 열 이름과 식은 코드의 상수만 쓴다.
- **다른 선택지**: 쿼리 문자열에 값을 이스케이프해 이어 붙이기.
- **이유**: 값이 SQL 이 될 길을 처음부터 막는다. 범위 매개변수(`scope_` 로 시작)는 덮어쓸 수 없다.
- **바꾸려면**: `api/.../app/query/ScopedQuery.java`.

## 12 콘솔 뼈대와 이슈 화면

### 12-1. 화면 시안은 왼쪽 사이드바와 표 중심의 A안으로 정했다

WORKFLOW 4장은 시안을 2개 이상 만들어 사용자가 고르게 했지만, 사용자가 추천안으로 진행하라고 해서 두 안을 비교하고 골랐다.

| | A안: 사이드바와 표 | B안: 위쪽 막대와 카드 |
| --- | --- | --- |
| 배치 | 왼쪽 어두운 사이드바에 시스템과 그 안의 프로젝트를 접고 펴는 목록, 오른쪽 본문은 거르기 줄과 이슈 표 | 위쪽 막대에서 시스템과 프로젝트를 고르고, 본문은 이슈마다 카드 한 장을 격자로 |
| 정보 밀도 | 높음. 한 화면에 이슈 15건 안팎 | 낮음. 한 화면에 6건 안팎 |
| 프로젝트 옮겨 다니기 | 사이드바에서 한 번 | 막대의 메뉴를 열어 두 번 |
| 좁은 화면 | 사이드바가 위로 접힘 | 카드가 한 줄로 |
| 색 | 상태 배지에만 색(미해결 빨강, 재발 주황, 해결 초록, 무시 회색). 나머지는 무채색. 밝은 모드와 어두운 모드를 시스템 설정에 따름 | 카드 머리에 상태 색 띠 |

- **고른 것**: A안.
- **이유**: 시스템 4개, 프로젝트 13개를 자주 오가고(3.2), 이슈는 훑어보며 고르는 화면이라 밀도가 중요하다. 색을 상태에만 쓰면 눈이 이상한 것으로 바로 간다.
- **바꾸려면**: `web/src/components/AppShell.vue`, `web/src/style.css`.

### 12-2. 이슈 목록의 환경 거르기는 넣지 않았다

- **고른 것**: 상태, 기간, 정렬, 릴리스(최근 릴리스가 같은 이슈)로 거른다. 환경으로는 거르지 않는다.
- **다른 선택지**: 원본(events)의 environment 로 거르기, 집계 테이블에 environment 열을 더하기.
- **이유**: 횟수는 분 단위 집계에서 읽는데(10.3) 집계에 환경이 없다. 원본으로 거르면 상한으로 줄인 원본 때문에 숫자가 틀린다. 환경이 꼭 필요해지면 집계의 정렬 키에 environment 를 더하는 스키마를 새 번호로 만든다.
- **바꾸려면**: `api/src/main/resources/clickhouse` 에 새 스키마, `ClickHouseEventStats`, `IssueQueryService.list`.

### 12-3. 발생 추이는 차트 라이브러리 없이 SVG 막대로 그린다

- **고른 것**: 구간마다 막대 하나. 빈 구간은 서버가 0으로 채운다. 기간이 1시간이면 5분, 24시간이면 1시간, 7일이면 6시간, 14일과 30일이면 하루 구간이다.
- **다른 선택지**: Chart.js, ECharts 같은 라이브러리.
- **이유**: 12.1이 시계열 분석은 그라파나에 맡기기로 했다. 이슈 하나의 발생 모양만 보이면 되므로 의존성을 더하지 않았다.
- **바꾸려면**: `web/src/components/TrendBars.vue`, `IssueQueryService.Period`.

### 12-4. 횟수순과 사용자순은 쪽 넘김 없이 상위 25건만 보인다

- **고른 것**: ClickHouse가 기간 안의 지문을 많은 순으로 200개 고르고, PostgreSQL에서 상태와 릴리스로 거른 뒤 위 25건을 보인다. 최근 발생순만 쪽을 넘긴다.
- **이유**: 많이 난 것을 볼 때는 위쪽만 의미가 있다. 쪽을 넘기려면 두 저장소를 오가는 커서가 필요해 복잡해진다.
- **바꾸려면**: `IssueQueryService.TOP_CANDIDATES`, `list`.

### 12-5. 지문이 여럿인 이슈의 영향 사용자는 지문별 수를 더한다

- **고른 것**: 이슈의 사용자 수 = 지문마다 센 사용자 수의 합. 같은 사람이 두 지문에 걸치면 두 번 센다.
- **다른 선택지**: 지문을 모아 ClickHouse에서 uniqMerge 를 한 번에 하기.
- **이유**: 거의 모든 이슈는 지문이 하나다(6.4). 이슈 병합 기능을 만들 때 쿼리를 이슈 단위로 바꾼다.
- **바꾸려면**: `IssueQueryService.summarize`, `ClickHouseEventStats.counts`.

### 12-6. 그라파나 링크의 대시보드 ID를 errdeck-jvm 으로 미리 정했다

- **고른 것**: `{grafana-url}/d/errdeck-jvm/jvm?var-service={프로젝트 slug}&from&to`.
- **이유**: 대시보드는 16 작업에서 만든다. 그때 이 ID와 `service` 변수로 만든다.
- **바꾸려면**: `IssueQueryService.grafanaLink`, `errdeck.console.grafana-url`.

### 12-7. 영향 사용자에서 사용자 없는 이벤트를 빼는 스키마를 새로 더했다

- **고른 것**: 화면으로 확인하다 사용자 식별자가 없는 이벤트(user_hash 0)가 사용자 한 명으로 세지는 것을 찾았다. 구체화 뷰를 `uniqStateIf(user_hash, user_hash != 0)` 로 다시 만드는 008 을 더했다.
- **다른 선택지**: 006까지의 파일을 고치기. 이미 적용한 저장소에는 다시 돌지 않으므로 고르지 않았다.
- **감수하는 것**: 008 이전에 합쳐진 분은 사용자 수가 1 많을 수 있다. 뷰를 다시 만드는 짧은 사이에 들어온 행은 집계에서 빠질 수 있다.

### 12-8. 화면 테스트는 순수 함수와 api 호출기만 둔다

- **고른 것**: Vitest 로 시각 표기, 프레임 묶기, 재발급 흐름(401 뒤 한 번만 재발급, 동시 요청)을 시험한다. 컴포넌트 렌더링 테스트와 브라우저 테스트는 두지 않고, 이번에는 브라우저 자동화 도구로 직접 확인했다.
- **다른 선택지**: @vue/test-utils, Playwright 화면 테스트를 CI에 두기.
- **이유**: 화면은 22 작업에서 크게 늘어난다. 그때 화면 테스트를 함께 정한다.

## 13 소스맵 해석과 캐시

### 13-1. 소스맵 캐시를 Caffeine 대신 직접 만들었다

- **고른 것**: core 의 `SourceMapCache`. 동시 해석 한 번은 열쇠마다 `CompletableFuture` 하나로, 바이트 상한은 쓴 순서를 기억하는 `LinkedHashMap` 을 잠금 안에서 다뤄 지킨다.
- **다른 선택지**: 7.4가 적은 대로 Caffeine 의 로딩 캐시(무게 함수로 바이트 상한)를 worker 에 두기.
- **이유**: 작업 목록(13)이 캐시를 core 에 두라고 했고, core 는 JDK 만 쓴다(WORKFLOW 2.4). 필요한 기능(동시 해석 한 번, 바이트 상한, 오래 안 쓴 것부터 내보내기)이 작아 직접 만들 만하다.
- **감수하는 것**: 조회마다 잠금 하나를 지난다. worker 의 계산 스레드는 2개라 다툼이 적다.
- **바꾸려면**: worker 에 Caffeine 을 더하고 `Caffeine.newBuilder().maximumWeight(..).weigher((k, v) -> v.estimatedBytes())` 로 바꾼다.

### 13-2. 조회는 압축 줄 1부터, 열 0부터 받는다

- **고른 것**: `SourceMap.lookup(line, column)` 은 source-map 라이브러리와 같이 줄은 1부터, 열은 0부터 센다. 브라우저 스택의 열은 1부터라 부르는 쪽(15 작업의 복원 단계)이 1을 뺀다.
- **이유**: 정답을 만든 라이브러리와 같은 기준이어야 대조 테스트가 그대로 성립한다.

### 13-3. 원본 경로는 소스맵에 적힌 그대로 둔다

- **고른 것**: `sourceRoot` 가 있으면 앞에 붙이기만 하고 `../../src/collab.ts` 같은 상대 경로를 정리하지 않는다. 지문 규칙(6.3)의 경로 정리(`./`, 출처 떼기)는 지문을 만들 때 한다.
- **다른 선택지**: 해석할 때 `../` 를 지워 `src/collab.ts` 로 만들기.
- **이유**: 정답 라이브러리와 같은 값을 돌려주고, 화면에 보일 경로와 지문의 재료를 정하는 일은 복원 단계(15)에 맡긴다.

### 13-4. 원본 코드는 해석 결과에 담지 않는다

- **고른 것**: `SourceContext.around` 가 필요할 때 소스맵 원문을 다시 읽어 그 파일의 앞뒤 5줄만 자른다.
- **감수하는 것**: 원문 JSON 을 다시 읽는 비용. 복원 단계는 이슈마다 대표 이벤트에만 앞뒤 코드를 붙여 이 비용을 줄인다(15).
- **이유**: 7.3. 원본 코드는 해석 결과보다 훨씬 커서 캐시에 넣으면 128MB 안에 든 소스맵 수가 크게 준다.

### 13-5. 정답 자료는 스크립트로 만들어 저장소에 넣는다

- **고른 것**: `scripts/sourcemap-fixture` 에서 `npm run generate` 로 Vite 빌드와 source-map 0.7.4 의 정답을 만들고, 결과(소스맵 583KB, 정답 848KB)를 `core/src/test/resources/sourcemap` 에 넣는다.
- **다른 선택지**: 테스트할 때마다 Node 로 만들기.
- **이유**: core 테스트가 Node 없이 돈다. Vite 나 소스맵 형식이 바뀌면 스크립트로 다시 만든다.

## 14 Vue SDK

### 14-1. 압축 여부는 쿼리가 아니라 본문의 gzip 머리로 가린다

- **고른 것**: SDK 는 압축하면 설계대로 `enc=gzip` 을 붙이지만, ingest 는 본문을 해석하지 않으므로(adr/0003) 대기열에 옮기지 않는다. worker 의 봉투 읽기가 gzip 머리(1f 8b)로 압축 여부를 가린다.
- **다른 선택지**: ingest 가 `enc` 를 대기열 항목의 필드로 옮기기.
- **이유**: 탭을 떠날 때의 `sendBeacon` 은 동기로 보내야 해서 비동기인 CompressionStream 을 거칠 수 없다. 압축하지 않은 봉투가 생기는데, 머리 두 바이트로 확실히 가릴 수 있어 ingest 를 바꾸지 않았다.
- **바꾸려면**: `core` 의 `EnvelopeCodec.decode`.

### 14-2. 요청 정보에는 쿼리와 조각을 넣지 않는다

- **고른 것**: `request.url` 은 `location.origin + location.pathname`. 헤더는 `User-Agent` 만.
- **이유**: 브라우저 주소의 쿼리에는 토큰이나 이메일이 실릴 수 있다(15.6). 서버 SDK 처럼 이름으로 골라 지우기보다 아예 보내지 않는 쪽이 가볍고 안전하다.

### 14-3. 앱 프레임 판정은 브라우저에서 하지 않는다

- **고른 것**: 프레임의 `in_app` 을 비워 둔다. 번들 하나에 내 코드와 라이브러리가 섞여 있어 브라우저에서는 가릴 수 없다. 소스맵으로 복원한 뒤 worker 가 `node_modules` 밖인지로 정한다(6.3, 15 작업).

### 14-4. fetch 만 빵부스러기로 남기고 XMLHttpRequest 는 감싸지 않는다

- **고른 것**: `window.fetch` 를 감싸 주소(쿼리 제외)와 상태 코드를 남긴다. ingest 로 보내는 요청은 남기지 않는다.
- **다른 선택지**: XMLHttpRequest 도 감싸기(axios 의 기본 어댑터).
- **이유**: 팬파라이브 web 과 CoPage web 은 fetch 를 쓴다. 번들 크기를 작게 둔다. axios 를 쓰는 대상이 생기면 더한다.

### 14-5. Retry-After 가 없는 429, 503 은 60초 쉰다

- **고른 것**: 서버 SDK(09-5)와 같다. ingest 는 Retry-After 를 Access-Control-Expose-Headers 로 열어 두므로 보통은 그 값을 쓴다.

### 14-6. SDK 의 큐 상한은 100건, 묶음 간격은 2초다

- **고른 것**: 브라우저 한 탭에서 나는 에러는 서버보다 훨씬 적어 서버 SDK(1,000건)보다 작게 잡았다. 넘으면 버리고 `queue_overflow` 로 센다.
- **바꾸려면**: `createErrDeck({ queueSize, flushIntervalMs })`.

### 14-7. 데모 화면은 SDK 를 로컬 경로로 의존한다

- **고른 것**: `demo-web/package.json` 의 `"@errdeck/sdk-vue": "file:../sdk-vue"`. SDK 를 먼저 빌드해야 한다(CI도 그 순서).
- **이유**: 패키지 저장소에 올릴 곳은 아직 정하지 않았다(20장의 미정 사항). 감시 대상(23 작업)도 같은 방식이나 빌드 결과를 복사해 붙인다.

## 15 릴리스와 소스맵 업로드, 재발 판정

### 15-1. 소스맵 파일의 위치를 (프로젝트, 릴리스, 파일 이름)으로 정한다

- **고른 것**: `{볼륨}/{프로젝트}/{릴리스의 SHA-256}/{파일 이름의 SHA-256}.gz`. api 가 쓰고 worker 가 같은 규칙으로 읽는다. `release_artifacts` 에는 크기, 해시, 위치를 기록만 한다.
- **다른 선택지**: worker 가 `release_artifacts` 를 조회해 위치를 얻기.
- **이유**: 계산 스레드가 DB를 기다리지 않는다(14.5). 해시 경로라 릴리스나 파일 이름에 `../` 가 섞여도 볼륨 밖으로 나가지 못한다.
- **바꾸려면**: `core` 의 `LocalArtifactStore`. S3 어댑터를 만들 때도 같은 열쇠를 쓴다.

### 15-2. 소스맵 이름은 번들 주소에서 출처와 쿼리를 떼고 .map 을 붙인 것이다

- **고른 것**: `https://x/assets/index-a1.js?v=1` 의 소스맵은 `assets/index-a1.js.map`. 업로드 스크립트는 dist 기준 상대 경로로 올린다. 그래서 번들을 dist 와 같은 구조로 배포해야 짝이 맞는다(Vite 기본 그대로).
- **다른 선택지**: 업로드 때 접두사(`~/assets/...`)를 따로 받기.
- **이유**: 팬파라이브 web 과 CoPage web 은 루트에서 그대로 내보낸다. 하위 경로에 배포하는 대상이 생기면 접두사를 더한다.

### 15-3. 복원은 계산 단계에서 하고, 캐시가 비었을 때만 볼륨을 읽는다

- **고른 것**: `EnvelopeProcessor` 가 지문 계산 바로 앞에서 복원한다. 소스맵이 캐시에 없으면 그 자리에서 볼륨을 읽고 해석한다.
- **다른 선택지**: 복원을 쓰기 단계로 옮기기, 복원 전용 스레드를 두기.
- **이유**: 지문의 재료가 복원 결과라 계산 단계에 있어야 한다(6.1). 볼륨은 같은 기계의 디스크이고 같은 소스맵은 한 번만 읽는다(7.4). 14.5 의 "계산 단계에 I/O 없음"을 조금 어기는 것이라 기록해 둔다.

### 15-4. 복원한 프레임의 함수 이름은 소스맵의 이름만 쓴다

- **고른 것**: 그 위치에 소스맵의 이름(names)이 있으면 쓰고, 없으면 비운다. 브라우저 스택의 압축된 이름(`Oo`, `t`)은 남기지 않는다.
- **이유**: 압축된 이름은 빌드마다 바뀌어 같은 버그를 다른 이슈로 가른다. 실제 Vite 번들로 확인하다 찾았다.
- **감수하는 것**: 소스맵의 이름은 그 위치의 식별자라, 감싸는 함수 이름이 아니라 부르는 함수 이름일 때가 있다(`applyRemote (src/App.vue:12:3)`). 이름이 없으면 지문은 원본 경로만으로 만들어 같은 파일의 서로 다른 함수가 하나로 묶일 수 있다.

### 15-5. 복원하지 못한 번들 프레임은 앱 프레임에서 뺀다

- **고른 것**: 소스맵이 없거나 릴리스가 없으면 그 프레임을 `in_app=false` 로 두고 `restored=0` 으로 저장한다. 앱 프레임이 남지 않으면 지문은 예외 타입과 값을 지운 메시지로 만든다(7.5).
- **감수하는 것**: 뒤늦게 소스맵이 올라와도 이미 만든 이슈는 따로 남는다. 화면에서 다시 복원하기와 자동 재처리는 7.5의 후속 과제다.

### 15-6. 재발 판정의 세부 규칙

- **고른 것**: 해결한 이슈에 이벤트가 오면
  - 해결한 릴리스가 없으면(릴리스 없이 해결) 어느 이벤트든 재발이다.
  - 이벤트에 릴리스가 없으면 재발이다.
  - 두 릴리스가 모두 등록되어 있으면 이벤트의 릴리스가 나중에 등록된 경우만 재발이다. 같거나 이전이면 해결을 유지한다.
  - 둘 중 하나라도 등록되지 않았으면(서버 프로젝트처럼 소스맵을 올리지 않는 경우) 릴리스 이름이 다를 때만 재발이다.
- **감수하는 것**: 이슈는 묶음당 한 번 고치며 그 묶음에서 가장 늦은 이벤트의 릴리스로 판정한다. 옛 번들과 새 번들의 이벤트가 한 묶음에 섞이면 늦은 쪽이 정한다.
- **바꾸려면**: `worker` 의 `JdbcIssueRepository.touch`.

### 15-7. 무시의 횟수 조건은 worker 가 이슈 행에서 센다

- **고른 것**: `issues.ignored_count` 에 무시한 뒤의 발생 횟수(접힌 횟수 포함)를 더하고, `ignored_until_count` 에 닿으면 미해결로 돌린다. 상태를 바꿀 때 0으로 되돌린다.
- **다른 선택지**: ClickHouse 집계에서 무시한 시각 이후의 횟수를 세기.
- **이유**: 묶음당 한 번 고치는 UPDATE 에 덧붙이면 조회가 늘지 않는다. 원본 상한과 상관없이 정확하다.

### 15-8. 업로드에서 릴리스가 없으면 만들고, 소스맵인지 해석해 보고 받는다

- **고른 것**: 등록을 빼먹고 업로드만 해도 릴리스를 만든다. 해석에 실패하는 파일은 400 이다. 크기 상한 20MB.
- **이유**: 깨진 파일을 받아 두면 이벤트가 올 때마다 해석에 실패한다.

### 15-9. 원본 코드의 앞뒤 줄은 맨 위 앱 프레임에만 붙이고 따로 기억한다

- **고른 것**: 이벤트마다 맨 위 앱 프레임 하나에만 붙인다. 잘라 낸 줄은 (소스맵, 파일, 줄)마다 최대 1만 개 기억해 같은 위치에서 원문을 다시 읽지 않는다.
- **이유**: 15.6(화면에는 문제 프레임의 앞뒤 5줄만). 원문을 다시 읽고 푸는 비용을 줄인다.

### 15-10. 프로젝트 토큰은 `edt_` 로 시작한다

- **고른 것**: `edt_` + 무작위 32바이트 Base64URL. 저장소에 실수로 올라갔을 때 검색으로 찾기 쉽다.


## 16 지표, 대시보드, 경보

### 16-1. 저장소는 프로필 없이, 세 프로세스는 core 프로필로

- **고른 것**: `docker compose up -d` 는 지금처럼 저장소 3개만 띄운다. ingest, worker, api 컨테이너는 `core`, 관측 도구는 `obs` 프로필이다.
- **다른 선택지**: 저장소까지 `core` 에 넣기.
- **이유**: 호스트에서 `bootRun` 으로 개발하는 흐름과 테스트(저장소 3개만 필요)를 바꾸지 않는다. `--profile core --profile obs` 를 붙이면 끝 기준의 명령과 같다.

### 16-2. 이미지는 컨테이너 안에서 Gradle 로 빌드한다

- **고른 것**: 다단계 Dockerfile. JDK 이미지에서 `bootJar` 를 만들고 JRE 이미지로 옮긴다. Gradle 캐시는 BuildKit 캐시로 두고 `sharing=locked` 로 세 이미지가 차례로 쓴다.
- **다른 선택지**: 호스트에서 만든 jar 를 복사하기(demo-api, loadgen 의 방식).
- **이유**: 끝 기준이 "명령 한 번"이다. 셋을 함께 빌드하면 캐시를 동시에 쓰다 실패해 잠갔다. 첫 빌드는 2분 남짓 걸린다.
- **감수하는 것**: 소스가 바뀌면 `COPY . .` 뒤가 전부 다시 돈다. 25 작업에서 CI 가 이미지를 만들게 되면 레이어를 나눈다.

### 16-3. 지표는 compose 에서만 관리 포트 8091 로 나눈다

- **고른 것**: compose 가 `MANAGEMENT_SERVER_PORT=8091` 을 주고 호스트에 열지 않는다. 호스트에서 띄우는 로컬 개발은 서비스 포트에서 그대로 낸다. api 는 거부 체인에서 `/actuator/prometheus` 를 관리 포트로 온 요청에만 연다(관리 포트가 없으면 연다).
- **이유**: 13.2. 개발 중에는 포트 하나로 보는 편이 편하다.

### 16-4. Alertmanager 는 Authorization 헤더로 공유 비밀을 보낸다

- **고른 것**: 내부 비밀 필터가 `X-ErrDeck-Internal-Secret` 과 `Authorization: Bearer` 를 둘 다 받는다. Alertmanager 설정은 환경 변수를 펼치지 않으므로 compose 가 시작할 때 비밀을 파일로 쓰고 `credentials_file` 로 읽게 한다.
- **다른 선택지**: Alertmanager 의 임의 헤더 설정, 설정 파일에 비밀을 적기.
- **이유**: Authorization 헤더는 Alertmanager 의 모든 판에서 된다. 비밀을 저장소에 적지 않는다.

### 16-5. 대시보드는 파이썬 생성기가 원본이다

- **고른 것**: `deploy/grafana/generate.py` 가 JSON 5개를 만들고, 둘 다 저장소에 둔다.
- **다른 선택지**: 그라파나 화면에서 만든 JSON 을 내보내 손으로 관리하기.
- **이유**: 내보낸 JSON 은 수천 줄이라 리뷰할 수 없다. 패널 하나가 함수 한 줄이다.

### 16-6. 13.4 의 지표 12개 중 둘은 그 기능을 만드는 작업에서 붙인다

- **고른 것**: `errdeck_uptime_schedule_lag_seconds` 는 20 작업(업타임), `errdeck_notifications_total` 은 21 작업(알림)에서 만든다. 이번에는 worker 단계에 `restore` 를 나눠 넣고, api 에 받은 경보를 세는 `errdeck_alerts_received_total{alertname, status}` 를 더했다.
- **이유**: 하는 일이 없는 지표를 미리 만들면 0 인지 고장인지 구별할 수 없다.

### 16-7. 호스트 포트

- **고른 것**: ingest 18080, api 18081, Grafana 13000, Prometheus 19090, Alertmanager 19093. 전부 환경 변수로 바꾼다. worker 는 호스트에 열지 않는다.
- **이유**: 8080~8087 은 팬파라이브와 CoPage 가 쓴다(WORKFLOW 3장). 3000, 9090 도 다른 도구가 흔히 쓴다.

### 16-8. 로컬 Grafana 는 익명 보기를 연다

- **고른 것**: 익명 사용자는 Viewer. 관리자는 admin/admin(환경 변수로 바꿈). 홈은 전체 개요 대시보드.
- **이유**: 12.4 의 콘솔 링크가 로그인 없이 열린다. 배포에서는 25 작업에서 닫는다.

### 16-9. cAdvisor 는 지표를 줄이고 compose 서비스 이름을 붙인다

- **고른 것**: 디스크, 네트워크, CPU 별, 프로세스 지표를 끈다. `com.docker.compose.service` 라벨만 남겨 Prometheus 에서 `service` 라벨로 바꾼다. 대시보드와 CPU 제한 경보가 이 이름을 쓴다.
- **이유**: 메모리 상한 128MB(14.7). 컨테이너 ID 대신 서비스 이름으로 본다.

### 16-10. 컨테이너 상태 확인은 bash 의 /dev/tcp 로 한다

- **고른 것**: JRE 이미지에 curl 이 없어 `bash -c 'exec 3<>/dev/tcp/127.0.0.1/8091 ...'` 로 `/actuator/health` 를 부른다. ingest 와 worker 는 api 가 건강해진 뒤 뜬다(스키마를 api 가 만든다).
- **다른 선택지**: 이미지에 curl 을 설치하기.
- **이유**: 이미지에 도구를 더하지 않는다.

### 16-11. 힙은 최소와 최대를 같게 둔다

- **고른 것**: `-Xms` 와 `-Xmx` 를 같게(ingest 160m, worker 448m, api 256m).
- **이유**: 컨테이너 상한 안에서 힙이 얼마까지 크는지 처음부터 보인다. 실행 중에 힙을 늘리느라 GC 가 도는 일이 없다. 대신 시작 직후의 메모리 사용이 크게 보인다.

### 16-12. ingest 동시 연결 2,000 은 톰캣 설정으로

- **고른 것**: `server.tomcat.max-connections=2000`, `accept-count=100`.
- **이유**: 14.3. 가상 스레드에는 스레드 풀이라는 천장이 없어 연결 수가 곧 힙에 쌓이는 요청 수다. 넘는 연결은 커널 대기열 100개까지 기다리고 그 뒤로는 거절된다.

### 16-13. Docker Desktop 에서 안 되는 설정은 뺀다

- **고른 것**: node-exporter 의 루트 마운트에서 `rslave` 를 뺐다. Docker Desktop(mac)은 루트가 공유 마운트가 아니라 컨테이너가 뜨지 않는다.
- **감수하는 것**: mac 에서 node-exporter 가 보는 것은 Docker Desktop 의 가상 머신이다. 오라클 서버(25 작업)에서는 `rslave` 를 다시 넣는다.

### 16-14. JVM 컨테이너에 MALLOC_ARENA_MAX=2

- **고른 것**: ingest, worker, api 에 `MALLOC_ARENA_MAX=2`.
- **이유**: 처음 띄웠을 때 api 의 작업 집합이 상한 512MB 중 457MB였다(힙 256 + 힙 밖 99). glibc 가 스레드마다 메모리 구역을 만든 몫이다. 넣은 뒤 api 364MB, ingest 315→232MB, worker 429→315MB.

### 16-15. Go 로 만든 관측 도구에 GOMAXPROCS=1

- **고른 것**: Prometheus, Grafana, Alertmanager, exporter 4종에 `GOMAXPROCS=1`.
- **이유**: Go 도 JVM 처럼 서버의 코어 수(10)만큼 스레드를 돌린다. 상한 0.25~0.5 에서 쉬는 중에도 CPU 제한 경보가 울렸다(Grafana 제한 구간 42%, CPU 43%). 넣은 뒤 Grafana CPU 0.6%. 14.2 의 이야기가 JVM 밖에서도 그대로 맞았다.

### 16-16. ClickHouse 는 서버 메모리 상한을 컨테이너의 75% 로

- **고른 것**: `max_server_memory_usage_to_ram_ratio=0.75`(1.5GB), 마크 캐시 256MB, 비압축 캐시 끔. 병합 스레드 수는 기본값을 둔다.
- **이유**: 기본값으로는 추적 메모리가 280MB인데 상주 메모리가 1.63GB였다(할당기가 돌려주지 않은 몫). 상한에 닿기 전에 쿼리가 실패해야 컨테이너가 죽지 않는다. 병합 스레드를 4로 줄이면 변경 실행 기준값(20)보다 작아 서버가 뜨지 않는다. 줄일지는 17 작업의 CPU 제한 지표로 정한다.

### 16-17. cAdvisor 에 docker 와 containerd 소켓을 따로 붙인다

- **고른 것**: `/var/run` 대신 `/var/run/docker.sock` 과 `/run/containerd/containerd.sock` 을 붙인다. compose 프로젝트 이름이 errdeck 인 컨테이너에만 `service` 라벨을 단다.
- **이유**: Docker Desktop 에서는 `/var/run` 을 붙여도 소켓이 보이지 않았고, Docker 29 는 containerd 이미지 저장소를 써서 containerd 에도 물어야 컨테이너를 찾았다. 같은 Docker 에 CoPage 의 `postgres`, `redis` 가 있어 서비스 이름만으로는 섞였다.

### 16-18. 모든 컨테이너에 restart: unless-stopped

- **이유**: Docker 를 다시 켰을 때 저장소만 안 떠서 api 와 worker 가 계속 죽고 다시 뜨는 일이 있었다.

### 16-19. 가상 스레드 붙잡힘 지표는 micrometer-java21 로

- **고른 것**: 가상 스레드를 쓰는 ingest 와 api 에 `micrometer-java21` 을 더한다. Spring Boot 가 알아서 `jvm.threads.virtual.pinned`(JFR 기반)를 등록한다.
- **이유**: 14.4 가 대시보드에 올리라고 한 지표인데 기본 JVM 지표에는 없다.

## 17 자원 실험

### 17-1. 실험은 스크립트 하나에 하위 명령 7개로

- **고른 것**: `scripts/experiments/resources.py <실험>`. 파이썬 표준 라이브러리만 쓴다. 값마다 compose 덮어쓰기 파일(`.run/override.yml`)을 만들어 core 프로필을 다시 띄운다. 결과 JSON 은 `.run/` 에 남기고(저장소에 넣지 않음) 표는 EXPERIMENTS.md 에 옮긴다.
- **다른 선택지**: 실험마다 셸 스크립트.
- **이유**: 지표를 읽어 차이를 내고 히스토그램 분위수를 구하는 일이 셸로는 길다. 실험 사이의 공통 부분(띄우기, 채우기, 비우기 측정)이 대부분이다.

### 17-2. errdeck 컨테이너는 코어 0~3 에, loadgen 은 4~9 에 묶는다

- **이유**: 도커 가상 머신이 10코어라 상한만으로는 "4코어 서버"가 되지 않는다. 부하 도구가 같은 코어를 쓰면 측정 대상과 CPU 를 다툰다. 코어 수 실험은 0~1 로 바꾼다.

### 17-3. worker 처리량은 미리 채운 대기열을 비우는 속도로 잰다

- **고른 것**: worker 를 멈추고 봉투 18,000개(이벤트 36만 건)를 채운 뒤 worker 를 띄운다. 남은 봉투가 90% 에서 10% 로 줄어든 구간의 속도를 처리량으로 본다. 지표는 컨테이너 안의 관리 포트와 cgroup 의 cpu.stat 에서 시작과 끝에 직접 읽는다.
- **다른 선택지**: 지속 부하를 걸고 Prometheus 로 보기.
- **이유**: 지속 부하로는 worker 가 따라가는 한 처리량이 보낸 양과 같아 한계가 보이지 않는다. Prometheus 의 15초 수집은 수십 초짜리 실험에 거칠다.

### 17-4. ingest 의 동시 연결을 2,000 에서 500 으로

- **고른 것**: `server.tomcat.max-connections=500`.
- **이유**: 컨테이너 상한(1코어, 힙 160MB)에서 이벤트 20건짜리 봉투를 초당 400개 보내자 ingest 가 무너졌다(초당 27개만 응답, p50 1.6초). 전체 GC 15번에 33.5초를 멈췄고 Old 영역이 89MB 로 차 있었다. 봉투는 2KB 인데, 연결마다 톰캣이 힙에 잡는 버퍼(읽기, 쓰기, 헤더)가 수십 KB라 2,000 연결이면 힙의 절반을 넘는다. GC 가 멈추는 동안 Redis 호출이 200ms 를 넘겨 503 이 되고, 응답이 늦어 연결이 더 쌓이는 악순환이다. 500 으로 줄이자 같은 부하에서 전부 응답했고 p50 3.4ms, 전체 GC 0번이었다. 14.7 이 "동시 연결 상한이 메모리 설계"라고 해 놓고 연결 하나의 크기를 계산하지 않았던 것이다.
- **감수하는 것**: 연결 500 을 넘으면 커널 대기열(accept-count 100) 뒤로 거절된다. SDK 는 프로세스마다 연결을 재사용하므로 감시 대상 서버의 수가 수백 대가 되기 전에는 닿지 않는다. 브라우저 SDK 는 사용자마다 연결이라 사용자가 많아지면 다시 본다.


### 17-5. worker 의 쓰기 큐는 이벤트 수로 묶는다

- **고른 것**: 쓰기 큐 자체는 길이 제한 없는 큐로 두고, `write-queue-capacity`(10,000) 만큼의 세마포어를 봉투의 이벤트 수만큼 잡는다. 쓰기 스레드가 꺼낼 때 돌려준다.
- **이유**: 14.5 의 10,000 은 이벤트 수였는데 봉투 수로 세고 있었다. 20건짜리 봉투가 밀리자 힙(448MB)이 넘쳤다.

### 17-6. 읽기 제한 시간 뒤의 복구

- **고른 것**: 읽기에 실패하면 다음 바퀴에 자기 미확인 목록(XREADGROUP ID 0)을 끝까지 다시 읽는다. 다른 worker 의 것을 가져오는 이어받기는 XAUTOCLAIM 의 다음 위치를 따라 한 번에 끝까지 넘긴다. worker 의 Redis 제한 시간은 5초.
- **이유**: 시작 직후 GC 가 3.1초 멈추자 읽기가 3초 제한에 걸렸고, Redis 가 넘긴 항목이 이어받기의 최소 대기(60초)까지 멈췄다.

### 17-7. api 의 동시성 상한

- **고른 것**: ClickHouse 조회 동시 8(0.5초 기다려 자리가 없으면 503), 커넥션 획득 제한 2초(넘으면 503), 톰캣 동시 연결 200.
- **이유**: 14.3, 14.6 에 적었지만 만들지 않았던 것이다. 없을 때 초당 300번의 조회에 api 가 죽었다.
- **감수하는 것**: 몰리면 503 이 많다. 콘솔은 사람이 보는 화면이라 초당 수백 번이 올 일은 없다고 보고 넘어간다.

### 17-8. 실험의 처리량은 한 번씩만 쟀다

- **감수하는 것**: 마감 때문에 값마다 한 번씩 돌렸다. 계산 풀과 GC 비교는 흔들림(같은 설정이 5천에서 1만 4천)이 차이보다 커서 결론을 내지 않았다. 흔들림의 원인으로는 GC(실행 시간의 15~20%)와, 이슈별 분당 원본 상한(100)이 실행 중에 분이 바뀌면 원본을 더 쓰게 되는 것을 의심한다.

## 18-19 성능 추적 (SDK, 저장, 화면)

마감 때문에 18 과 19 를 이슈 하나, 브랜치 하나로 묶었다(사용자 요청: 이슈를 크게).

### 18-1. 트랜잭션 JSON 은 스팬 시작을 트랜잭션 시작부터의 밀리초로 담는다

- **고른 것**: `start_timestamp`(ISO), `duration_ms`, 스팬마다 `start_offset_ms`, `duration_ms`, `repeat`. core 의 `Transaction` 이 읽고 쓴다.
- **이유**: 05 작업의 `transactions` 테이블이 스팬을 시작 위치와 길이의 배열로 둔다. 그대로 옮기면 worker 가 바꿀 것이 없다.

### 18-2. 스프링 SDK 의 추적은 에러 클라이언트와 따로 둔다

- **고른 것**: `ErrDeckTracer` 빈이 자기 큐(1,000), 전송 스레드, `?kind=tx` 전송을 갖는다. `Sender` 는 이벤트 대신 봉투 항목을 만드는 함수를 받게 고쳐 둘이 같이 쓴다.
- **이유**: 대기열을 나눈 5.4 와 같은 이유로, 트랜잭션이 에러의 큐와 전송을 밀어내지 않게 한다. `errdeck.tracing.enabled=false` 로 추적만 끌 수 있다.

### 18-3. 계측은 라이브러리 없이 빈 후처리기와 JDK 프록시로

- **고른 것**: DataSource 빈을 `java.lang.reflect.Proxy` 로 감싸 실행을 스팬으로, `RestClient.Builder` 와 `RestTemplate` 빈에 인터셉터를 붙여 나가는 호출을 스팬으로 남기고 `traceparent` 를 붙인다. 들어오는 요청은 서블릿 필터, WebFlux 는 웹 필터.
- **다른 선택지**: datasource-proxy 같은 라이브러리, Micrometer Observation, 스프링 부트의 `RestClientCustomizer`.
- **이유**: SDK 가 감시 대상에 의존성을 더하지 않는다(11.2). 부트 4 에서 RestClient 자동 설정이 별도 모듈로 갈라져, 고객 앱에 그 모듈이 없을 수 있다.
- **감수하는 것**: DataSource 를 인터페이스로 감싸 `HikariDataSource` 타입으로 주입받는 코드는 깨진다. `unwrap` 은 넘겨주므로 부트의 커넥션 풀 지표는 그대로다. WebFlux 는 안쪽 스팬이 없다(요청이 스레드를 옮겨 다녀 스레드 로컬을 못 쓴다).

### 18-4. 표본으로 뽑히지 않은 요청도 스팬을 모으고 끝에서 판단한다

- **고른 것**: 시작할 때 비율(0.1)로 뽑고, 앞 서비스의 `traceparent` 가 있으면 그 결정을 따른다. 뽑히지 않았어도 5xx, 예외, 1초 이상이면 `partial=true` 로 보낸다(8.4). `tail-sampling=false` 면 끝에서 판단하지 않는다.
- **감수하는 것**: 꺼도 스팬은 모은다(보내지만 않는다). 부담이 목표를 넘으면 모으기부터 끄게 바꾼다.

### 18-5. 경로 이름은 처리한 뒤의 핸들러 패턴

- **고른 것**: 시작할 때는 `GET /실제/주소` 로 열고, 끝에서 `HandlerMapping.BEST_MATCHING_PATTERN_ATTRIBUTE` 로 바꾼다. 패턴이 없으면(404, 정적 파일) `(패턴 없음)`.
- **이유**: 8.3. 실제 주소로 두면 엔드포인트가 수만 개가 된다.

### 18-6. SSE 와 WebSocket 은 연결 수립까지만

- **고른 것**: `Accept: text/event-stream` 이나 `Upgrade: websocket` 이면 op 를 `http.server.stream` 으로 두고, 비동기로 넘어가 필터가 돌아오는 때까지를 기록한다.

### 18-7. Vue SDK 는 페이지 이동 하나가 트랜잭션, 조용해지면 끝

- **고른 것**: 처음 열 때 `pageload`, 라우터 이동마다 `navigation`. 이름은 라우트의 경로 패턴. API 호출이 모두 끝나고 0.5초 조용하면 끝내고, 최대 15초. `traceparent` 는 기본으로 같은 출처에만 붙인다(`tracePropagationTargets` 로 넓힘).
- **이유**: 다른 출처에 사용자 정의 헤더를 붙이면 브라우저가 사전 요청을 보내고 그 서버가 헤더를 허용해야 한다. 팬파라이브와 CoPage 의 API 는 같은 출처(프록시) 뒤에 있다.
- **결과**: 번들 gzip 3.8KB → 5.0KB(목표 10KB 이하).

### 18-8. 트랜잭션은 중복을 거르지 않는다

- **고른 것**: worker 는 트랜잭션의 span_id 로 중복을 확인하지 않는다. 묶음을 다시 쓸 때만 같은 행이 두 번 들어갈 수 있다.
- **이유**: 표본이고 7일 뒤 지워진다. 중복 확인 키를 Redis 에 트랜잭션마다 두는 비용이 더 크다.

### 19-1. 엔드포인트 표는 프로메테우스, 없으면 표본으로 계산하고 그렇다고 표시

- **고른 것**: 프로메테우스의 job 라벨을 프로젝트 슬러그와 같게 둔다(데모는 `demo-api`). `http_server_requests_seconds` 로 요청 수, p95, 5xx 비율을 낸다. 2초 안에 못 읽거나 비어 있으면 `transactions` 표본으로 계산한 표를 내고 화면에 "표본" 이라고 적는다.
- **다른 선택지**: 프로젝트마다 job 이름을 설정으로 따로 받기.
- **이유**: 8.1. 설정을 하나 줄인다. 다른 이름이 필요해지면 projects 에 열을 더한다.

### 19-2. 추적 조회는 볼 수 있는 프로젝트 전체에서 trace_id 로

- **고른 것**: `GET /api/traces/{traceId}` 는 사용자가 볼 수 있는 모든 프로젝트에서 최근 7일(보존 기간)을 찾는다. 볼 수 없는 프로젝트의 구간은 빠지고, 그림에서 부모를 못 찾은 트랜잭션은 맨 위에 놓는다.
- **이유**: 한 요청이 여러 프로젝트(팬파라이브의 gateway 와 서비스들)를 지난다. 권한 밖의 것은 ScopedQuery 가 거른다(15.4).

## 20-22 업타임 점검, 알림, 통합 화면

마감 때문에 20, 21, 22 를 이슈 하나, 브랜치 하나로 묶었다.

### 20-1. api 의 운영 기능은 저장소 포트 없이 JdbcClient 를 바로 쓴다

- **고른 것**: `OpsService`(모니터, 알림 규칙), `OverviewService` 가 JdbcClient 와 ClickHouseReader 를 직접 쓴다. worker 의 `uptime`, `alert` 패키지도 판정과 저장을 한 클래스에 둔다.
- **이유**: 마감. 다른 기능은 app 에 포트, out 에 구현으로 나눠 두었으니 리팩토링 때 같은 모양으로 나눈다.

### 20-2. 판정 상태는 PostgreSQL 의 열로, 바뀌는 순간은 조건부 UPDATE 로

- **고른 것**: `monitors` 에 연속 실패와 연속 성공 횟수를 두고 점검마다 고친다. 상태를 바꾸는 UPDATE 에 "지금 그 상태가 아닐 때만" 조건을 달아, 바뀐 행이 1인 worker 만 장애 기록을 열고 알린다. 열린 장애 기록은 부분 유일 색인으로 하나만.
- **다른 선택지**: Redis 에 상태를 두기.
- **이유**: 화면이 읽는 상태와 판정이 같은 곳에 있다. worker 가 여러 대여도 같은 모니터는 일정 스크립트가 한 번만 꺼내므로 경합은 다시 점검(10초 뒤)과 겹칠 때뿐이다.
- **처음 점검**: 확인 전(unknown)에서는 한 번 성공으로 정상, 연속 2회 실패로 다운이다. 처음 켠 모니터가 정상이 되느라 알림을 보내지 않는다.

### 20-3. 내부 주소 차단은 해석한 주소 전부를 보고, 연결할 IP 를 고정하지는 않는다

- **고른 것**: `core` 의 `UrlGuard` 가 호스트를 직접 해석해 나온 주소 중 하나라도 루프백, 사설, 링크 로컬, 공유(100.64/10), 0.0.0.0/8, fc00::/7 이면 거부한다. 만들 때(api)와 부르기 직전(worker)에 두 번 본다. 리다이렉트는 따라가지 않는다. 허용할 내부 호스트는 `ERRDECK_UPTIME_ALLOWED_HOSTS`.
- **감수하는 것**: 9.4 의 "검사한 IP 로 직접 연결"은 하지 않았다. 자바 HttpClient 로 IP 에 연결하면서 Host 와 TLS 의 이름 확인을 유지하기 어렵다. 확인과 연결 사이에 DNS 응답을 바꾸는 공격(DNS rebinding)은 막지 못한다. 막으려면 자체 이름 해석기(`InetAddressResolverProvider`)를 worker 에 넣는다.

### 20-4. 가동률은 점검한 것 중 성공한 비율

- **고른 것**: ClickHouse `uptime_checks` 의 `avg(ok)`. 중지한 동안은 점검하지 않으므로 계산에서 저절로 빠진다(9.1).
- **감수하는 것**: 다운 중에는 10초마다 다시 점검해 실패 행이 주기보다 많이 쌓인다. 가동률이 실제 시간 비율보다 낮게 나온다. 시간 가중으로 바꾸려면 장애 기록의 길이로 계산한다.

### 20-5. 점검 결과는 5초마다 모아 쓴다

- **이유**: ClickHouse 에 한 건씩 쓰면 파트가 늘어난다(10.4). 쓰지 못한 결과는 판정에 이미 반영했으므로 가동률의 행만 잃는다.

### 21-1. 새 이슈와 재발은 PostgreSQL 을 10초마다 보고 판정한다

- **고른 것**: 쓰기 단계에 알림을 끼우지 않고, 알림 판정 스레드가 `issues.created_at` 과 새로 더한 `issues.regressed_at`(트리거가 재발로 바뀌는 순간 적음)을 본다. 새 이슈는 끝난 1분 단위로 모아 프로젝트마다 한 메시지다. 중복 방지 키는 `new:{프로젝트}:{분}`.
- **다른 선택지**: worker 의 쓰기 단계에서 이슈를 만들 때 바로 알리기(16.1 의 "판정하는 곳" 그대로).
- **이유**: 쓰기 단계는 재시도할 수 있게 만든 단계라 여기에 외부 효과를 넣으면 재시도 때 두 번 판정한다. 별도로 보면 worker 가 여러 대여도 같은 분의 같은 키라 유일 제약이 하나만 통과시킨다(16.2 의 둘째와 셋째 줄이 함께 풀린다).
- **감수하는 것**: 새 이슈 알림이 최대 70초 늦다.

### 21-2. 채널은 Slack 과 Discord 를 함께, 이메일은 뒤로

- **고른 것**(WORKFLOW 의 "먼저 정할 것"): 둘 다 웹훅이라 본문 키만 다르다(`text`, `content`). 이메일(SMTP)은 규칙을 만들 때 거부한다.
- **이유**: 팬파라이브는 Discord 를 쓰고 있다. Slack 은 같은 코드로 따라온다.

### 21-3. 채널의 분당 상한은 규칙마다 20건

- **고른 것**: Redis `INCR` 로 규칙별 분 단위 건수를 세고, 넘으면 보내지 않고 실패로 기록한다.
- **감수하는 것**: 16.2 의 "넘는 것은 요약 한 건으로"는 하지 않았다. 새 이슈는 이미 분 단위로 묶이고, 빈도와 재발은 재알림 간격이 막아 상한에 닿기 어렵다.

### 21-4. 자원 경보는 'resource' 규칙으로 받는다

- **고른 것**: `alert_rules.kind` 에 `resource` 를 더했다. Alertmanager 가 api 로 넘긴 경보를 이 규칙마다 알림으로 연다(키는 경보 지문, 상태, 시작 시각). 이 서비스 자신을 감시하는 프로젝트에 단다.
- **감수하는 것**: 16.1 의 "응답 지연"(프로메테우스 규칙의 p95)은 감시 대상별 규칙을 프로메테우스에 쓰는 일이라 하지 않았다. 지금은 성능 화면과 요약 카드로 본다.

### 21-5. 발송이 막혔을 때의 이어받기

- **고른 것**: 발송 대기열도 소비 그룹이다. 60초 넘게 확인하지 않은 항목은 30초마다 이어받는다. 보낸 알림은 `notifications.status` 가 `sent` 라 이어받아도 두 번 보내지 않는다.
- **감수하는 것**: 보내고 상태를 쓰기 전에 죽으면 한 번 더 간다(최소 한 번 전달).

### 22-1. 상태 신호의 기준

- **고른 것**:
  - 장애(빨강): 다운인 모니터가 있거나, 프로메테우스의 `up` 이 0.
  - 주의(노랑): 재발한 이슈가 있거나, 1시간 안에 새 이슈가 났거나, 요약 카드가 12.2 의 기준을 넘음(CPU 80%, 힙 85%, 5xx 1%, 풀 대기 > 0).
  - 정상(초록): 그 밖.
  - 시스템의 신호는 프로젝트 중 가장 나쁜 것. 이유는 줄에 글로 함께 보인다.
- **이유**: 12장에 기준이 없어 정했다. "무엇 때문인지"가 같이 보여야 신호를 믿는다.

### 22-2. 요약 카드는 job 별 질의 6개를 한 번에

- **고른 것**: 프로젝트마다 질의하지 않고 `by (job)` 으로 6개를 질의해 전체를 15초 캐시한다. 2초 안에 답이 없으면 카드만 비운다.
- **이유**: 프로젝트 수와 상관없이 질의가 6개다. job 이름이 프로젝트 슬러그와 같다는 19-1 의 약속을 그대로 쓴다.

### 22-3. 화면 시안

- **고른 것**(WORKFLOW 의 "먼저 정할 것"): 12-1 의 사이드바 + 표를 그대로 쓴다. 전체 보기는 시스템마다 카드 하나, 그 안에 프로젝트 한 줄씩(신호 점, 미해결, 새 이슈, 모니터, 카드 6개, 그라파나 링크). 시스템 보기는 따로 만들지 않고 이 표가 겸한다.

### 22-4. 그라파나 링크의 변수 이름을 job 으로

- **고른 것**: 대시보드 변수가 `job` 이라(16-5) 링크도 `var-job` 이다. 15 작업에서 만든 이슈 상세의 링크(`var-service`)를 고쳤다. 4곳 중 3곳(이슈 상세, 장애 기록, 통합 화면)에 넣었고, 느린 요청 상세는 추적 화면이 대신한다.
