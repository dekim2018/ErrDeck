# 작업 중에 정한 것

사용자에게 묻지 않고 Claude가 추천안으로 정한 것을 모은다. 나중에 한꺼번에 검토하고 리팩토링할 때 이 문서를 본다.

항목마다 고른 것, 다른 선택지, 고른 이유, 바꾸려면 어디를 고치는지를 적는다. 설계 문서의 빈칸을 채운 결정은 해당 장 끝의 "구현하면서 바뀐 점"에도 짧게 남아 있다. 사용자가 직접 고른 것(03의 스트림 구분, 05의 지문 길이, 09의 gateway 등록 등)은 여기에 적지 않는다.

## 09 Starter SDK

### 09-1. WebFlux에서는 필터까지 올라온 예외만 잡는다

- **고른 것**: `WebFilter` 의 `doOnError` 로 처리되지 않고 올라온 예외만 보낸다. `ErrorResponse` 이고 상태가 500 미만이면 보내지 않는다.
- **다른 선택지**: (가) `@ExceptionHandler` 가 처리한 예외까지 잡으려고 `DispatcherHandler` 나 `HandlerResultHandler` 를 감싸기. (나) `ErrorWebExceptionHandler` 를 감싸 최종 상태 코드를 보고 보내기.
- **이유**: 대상인 팬파라이브 gateway는 컨트롤러가 거의 없고 오류 대부분이 경로 처리와 뒤쪽 호출에서 나서 필터까지 올라온다. (가)는 WebFlux 내부 구조에 깊이 기대고, (나)는 Spring Cloud Gateway가 자기 예외 처리기를 두므로 순서가 엇갈리기 쉽다.
- **바꾸려면**: `sdk-spring/.../webflux/ErrDeckWebFilter.java`.

### 09-2. WebFlux에서는 사용자 ID를 보내지 않는다

- **고른 것**: `RequestContext.userId` 를 비운다.
- **다른 선택지**: `exchange.getPrincipal()` 을 오류 흐름에 엮어 비동기로 꺼낸다.
- **이유**: 사용자는 비동기로만 꺼낼 수 있고, 리액터 스레드에서 기다리면 안 된다. 오류 흐름을 바꾸지 않는 쪽을 골랐다. 영향 사용자 수는 gateway 뒤 서비스의 이벤트로 셀 수 있다.
- **바꾸려면**: 같은 파일의 `snapshot`.

### 09-3. 같은 에러 접기의 비교 기준은 요청 스레드에서 만드는 가벼운 열쇠다

- **고른 것**: 예외 사슬(최대 5단계)의 클래스와 각 위쪽 20프레임(`StackTraceElement`, 줄 번호 포함)을 그대로 비교한다. 지문 규칙(6.3)을 쓰지 않는다.
- **다른 선택지**: core의 `Fingerprinter` 로 지문을 계산해 비교하기. 전송 스레드에서 접기.
- **이유**: 접기는 큐에 넣기 전에 해야 폭주 때 큐와 네트워크를 지킨다(5.1). 요청 스레드에서 프레임을 변환하고 해시하는 비용을 피했다. 같은 코드의 같은 줄에서 쏟아지는 경우가 접기의 대상이라 줄 번호까지 같아도 충분하다.
- **바꾸려면**: `sdk-spring/.../Folder.java` 의 `Signature`.

### 09-4. 같은 예외 객체를 여러 경로가 잡으면 한 번만 보낸다

- **고른 것**: 최근에 잡은 예외 객체를 약한 참조로 최대 1,000개 기억하고, 같은 객체는 다시 넣지 않는다.
- **다른 선택지**: 경로마다 "이미 보냄" 표시를 예외에 붙이기(억제된 예외 사용 등). 중복을 허용하고 worker의 지문으로 합치기.
- **이유**: 리졸버, 필터, 로그 어펜더가 같은 예외를 함께 보는 일이 흔하다(전역 처리기가 `log.error(e)` 를 남기는 경우). 예외 객체를 바꾸지 않고 막을 수 있다.
- **바꾸려면**: `ErrDeckClient.capture` 의 `recent`.

### 09-5. Retry-After가 없는 429, 503은 60초 쉰다

- **고른 것**: 기본 60초. 쉬는 동안 생긴 것은 버리고 이유별로 센다.
- **다른 선택지**: 짧게(5초) 쉬기, 늘려 가며 쉬기.
- **이유**: ingest는 항상 Retry-After를 주므로(03) 이 값은 다른 프록시가 끼었을 때만 쓰인다. 넘쳐 있는 서버를 다시 두드리지 않는 쪽을 골랐다.
- **바꾸려면**: `Sender.DEFAULT_PAUSE`.

### 09-6. 401, 403을 받으면 프로세스가 다시 뜰 때까지 보내지 않는다

- **고른 것**: 전송을 멈추고 로그를 1분에 한 번 남긴다. 이후 생긴 것은 `unauthorized` 로 센다.
- **다른 선택지**: 일정 간격으로 다시 시도하기.
- **이유**: 5.4의 "전송 중지, 로그 한 번"을 따랐다. 키가 바뀌면 설정을 고쳐 다시 띄우므로 다시 시도할 이유가 적다.
- **바꾸려면**: `Sender.handle`.

### 09-7. 연결 실패는 바로 한 번 다시 보낸다

- **고른 것**: `IOException` 이면 기다리지 않고 한 번 더 보내고, 그래도 실패하면 버리고 `network_error` 로 센다.
- **다른 선택지**: 잠깐 기다렸다 다시 보내기, 실패한 묶음을 다음 묶음에 다시 싣기.
- **이유**: 11.1의 "재시도 1회"를 가장 단순하게 따랐다. 다음 묶음에 싣는 방식은 큐 밖에 묶음을 쌓아 메모리 상한을 흐린다.
- **바꾸려면**: `Sender.send`.

### 09-8. 스케줄러의 오류 처리기는 덮어쓰고, 비동기 설정은 감시 대상에 없을 때만 넣는다

- **고른 것**: `ThreadPoolTaskScheduler`, `SimpleAsyncTaskScheduler` 빈에 오류 처리기를 넣는다(잡아서 보낸 뒤 기본 동작대로 로그를 남기고 다음 실행을 계속). `AsyncConfigurer` 는 감시 대상에 없을 때만 넣는다.
- **다른 선택지**: 로그 어펜더에만 맡기기(스프링이 두 경우 모두 ERROR 로그를 남긴다).
- **이유**: 11.2가 두 경로를 따로 적었다. 스케줄러에 오류 처리기를 직접 정한 감시 대상은 덮어쓰이는데, 팬파라이브와 CoPage는 정하지 않았다.
- **바꾸려면**: `ErrDeckAutoConfiguration` 의 `errDeckSchedulerErrorHandler`, `errDeckAsyncConfigurer`.

### 09-9. SDK 안에서도 프레임 250개, 사슬 10단계, 메시지 8KB로 자른다

- **고른 것**: 보내기 전에 자른다.
- **다른 선택지**: worker에서만 자르기(6.1).
- **이유**: 봉투 상한 200KB(5.3)를 넘겨 413을 받는 일을 줄이고 네트워크로 보내는 양부터 줄인다. worker의 정규화는 그대로 한다.
- **바꾸려면**: `EventBuilder` 의 상수.

### 09-10. 패키지 목록이 없으면 `in_app` 을 보내지 않는다

- **고른 것**: `in-app-packages` 가 비어 있으면 프레임의 `in_app` 을 비워 worker가 판정하게 한다.
- **다른 선택지**: 비어 있으면 모두 앱 프레임으로 보기.
- **이유**: 모두 앱 프레임으로 보면 프레임워크 프레임까지 지문에 들어가 버전을 올릴 때마다 이슈가 갈라진다(6.2).
- **바꾸려면**: `EventBuilder.inApp`.

### 09-11. SDK 자신의 로그는 JDK의 System.Logger로, 같은 문제는 1분에 한 번 남긴다

- **고른 것**: 로거 이름 `com.errdeck.sdk.internal`. 로그 어펜더는 이 이름만 정확히 건너뛴다.
- **다른 선택지**: SLF4J를 쓰기, 패키지 접두사로 건너뛰기.
- **이유**: SDK가 로깅 라이브러리에 기대지 않게 했다. 처음에는 `com.errdeck.sdk` 로 시작하는 로그를 모두 건너뛰었는데, 그 패키지의 사용자 코드(테스트)까지 걸러져 정확한 이름 비교로 바꿨다.
- **바꾸려면**: `InternalLog`, `ErrDeckAppender`.

### 09-12. client_report의 종류는 항상 event다

- **고른 것**: 버린 건수의 `category` 를 `event` 로 둔다.
- **다른 선택지**: 트랜잭션을 보내기 시작하면(18) `transaction` 을 나눠 세기.
- **이유**: 지금 SDK는 에러만 보낸다. 18 작업에서 트랜잭션을 더할 때 나눈다.
- **바꾸려면**: `Discards.drain`.

### 09-13. SDK는 core를 그대로 의존한다

- **고른 것**: `sdk-spring` 이 `core` 를 `api` 의존성으로 가진다. 감시 대상은 core도 함께 받는다.
- **다른 선택지**: 봉투와 이벤트 모델만 SDK 안에 따로 두기.
- **이유**: SDK와 worker가 같은 코드로 형식을 맞춘다(02). core는 JDK만 쓰므로 감시 대상의 의존성과 부딪치지 않는다. 패키지를 어디에 올릴지는 20장의 미정 사항이다.
- **바꾸려면**: `sdk-spring/build.gradle.kts`.

## 10 데모 앱

### 10-1. 데모 프로젝트의 ID와 키를 9001, 9002로 고정한다

- **고른 것**: `scripts/demo/seed.sql` 이 `OVERRIDING SYSTEM VALUE` 로 프로젝트 ID 9001(demo-api), 9002(demo-web)와 키 `demoapikey`, `demowebkey` 를 넣는다. 여러 번 실행해도 같다.
- **다른 선택지**: 넣을 때 받은 ID로 DSN을 만들어 출력하는 스크립트, api의 프로젝트 관리 API(11)로 만들기.
- **이유**: 데모 앱의 설정 파일에 DSN을 고정해 두면 compose와 테스트가 단순하다. 일반 프로젝트의 ID는 1부터 늘어나므로 9001에 닿기 전까지 겹치지 않는다.
- **바꾸려면**: `scripts/demo/seed.sql`, `demo-api/src/main/resources/application.yml` 의 `errdeck.dsn`.

### 10-2. compose의 데모 앱은 미리 만든 jar를 이미지에 담는다

- **고른 것**: `./gradlew :demo-api:bootJar :loadgen:installDist` 를 먼저 하고, Dockerfile은 그 결과를 `eclipse-temurin:25-jre` 에 복사만 한다.
- **다른 선택지**: Dockerfile 안에서 Gradle로 빌드하는 다단계 빌드.
- **이유**: 이미지 빌드마다 Gradle과 의존성을 내려받지 않아 빠르다. 16 작업에서 ingest, worker, api의 Dockerfile을 만들 때 같은 방식을 쓸지 다시 정한다.
- **바꾸려면**: `demo-api/Dockerfile`, `loadgen/docker/Dockerfile`.

### 10-3. 16 작업 전까지 compose의 데모 앱은 호스트의 ingest로 보낸다

- **고른 것**: `DEMO_ERRDECK_DSN` 의 기본값을 `host.docker.internal:8080` 으로 둔다.
- **다른 선택지**: 이번 작업에서 ingest도 compose에 올리기.
- **이유**: 프로세스의 컨테이너 등록은 16 작업의 범위다. 그때 기본값을 compose 안의 ingest로 바꾼다.
- **바꾸려면**: `docker-compose.yml` 의 `demo-api.environment`.

### 10-4. SDK 부담은 loadgen의 새 시나리오 `http` 로 잰다

- **고른 것**: 임의 주소에 GET을 정해진 속도로 보내는 `http` 시나리오를 더하고, 같은 jar를 SDK 켬과 끔으로 두 개 띄워 번갈아 잰다.
- **다른 선택지**: 앱 안에서 필터 시간을 재는 마이크로 벤치마크(JMH).
- **이유**: 2.2의 목표가 요청 시간의 차이이므로 바깥에서 본 응답 시간으로 잰다. 같은 맥에서는 잡음이 커서 1ms 이하는 가리지 못했다(EXPERIMENTS.md). 17 작업에서 기계를 나눠 다시 잰다.
- **바꾸려면**: `loadgen` 의 `Scenario.HTTP`, `Runner.requests`.

### 10-5. 데모 앱의 스케줄 예외는 켜고 끌 수 있고 기본 60초다

- **고른 것**: `demo.scheduled-failure.enabled`(기본 켬), `interval`(기본 60초).
- **이유**: 화면에서 스케줄 경로의 이슈를 볼 수 있게 켜 두되, 부담 실험에서는 측정에 섞이지 않게 끈다.

## 11 로그인과 권한

### 11-1. 처음 가입한 사용자가 관리자가 되고, 가입은 열어 둔다

- **고른 것**: `users.role` 이 ADMIN 인 사용자만 시스템을 만들 수 있다. 처음 가입한 사용자가 ADMIN 이 된다(동시에 가입해도 잠금으로 한 명). 가입은 `ERRDECK_SIGNUP_ENABLED=false` 로 막을 수 있다.
- **다른 선택지**: 설정의 관리자 이메일 목록, 초대받은 사람만 가입.
- **이유**: 혼자 운영하는 도구라 처음 띄운 사람이 관리자인 것이 가장 단순하다. 배포한 뒤에는 가입을 막는다(25 작업).
- **바꾸려면**: `JdbcUserRepository.create`, `errdeck.auth.signup-enabled`.

### 11-2. 로그아웃해도 액세스 토큰은 만료(15분)까지 쓸 수 있다

- **고른 것**: 로그아웃과 탈취 감지는 리프레시 토큰만 지운다. 이미 내준 액세스 토큰을 막는 목록은 두지 않는다.
- **다른 선택지**: CoPage처럼 Redis에 막은 토큰 ID와 사용자별 무효 시각을 두고 JWT 검증기에서 확인하기.
- **이유**: 10.6의 Redis 키 목록에 리프레시 토큰만 있고, 액세스 토큰이 15분으로 짧다. 요청마다 Redis를 묻지 않아도 된다.
- **바꾸려면**: `SecurityConfig.jwtDecoder` 에 검증기를 더하고 `AuthService.logout`, `refresh` 의 탈취 처리에서 막는다.

### 11-3. 구성원이 아니면 404, 역할이 모자라면 403

- **고른 것**: 다른 시스템의 프로젝트, 이슈, 키에는 404 를 준다.
- **다른 선택지**: 모두 403.
- **이유**: 403 은 그런 것이 있다는 사실을 알려 준다. 다른 시스템의 ID를 차례로 넣어 보는 것으로 무엇이 있는지 알아낼 수 없게 한다.
- **바꾸려면**: `AccessPolicy`.

### 11-4. 권한 표의 "알림 규칙, 모니터, 릴리스" 칸은 테스트용 엔드포인트로 먼저 확인한다

- **고른 것**: 이 칸의 API는 15, 20, 21 작업에서 생긴다. 지금은 같은 `AccessPolicy` 를 거치는 테스트 전용 엔드포인트로 역할 4개를 확인한다.
- **다른 선택지**: 이 작업에서 알림 규칙이나 모니터 API를 미리 만들기.
- **이유**: 뒤 작업의 범위를 미리 만들지 않는다(WORKFLOW 1.5). 그 작업에서 실제 API를 권한 표 테스트에 더한다.
- **바꾸려면**: `PermissionMatrixTest.AdminColumn`.

### 11-5. 로그인 실패는 잠그지 않고 늦추며, api 프로세스 안에서 센다

- **고른 것**: 같은 이메일로 10분 안에 5번 실패하면 이후 시도마다 1초씩 늦춘다. 세는 표는 메모리에 두고 1만 개를 넘으면 비운다.
- **다른 선택지**: 계정 잠금, Redis에 세기.
- **이유**: 잠그면 남이 일부러 틀려 주인을 막을 수 있다. api는 한 대라 메모리로 충분하다.
- **바꾸려면**: `LoginThrottle`, `errdeck.auth.failures-*`.

### 11-6. 프로젝트 만들기와 프로젝트 설정(한도, 허용 출처), 키 보기는 OWNER 만 한다

- **고른 것**: 15.4의 "키와 토큰, 구성원, 한도" 칸에 프로젝트 만들기와 허용 출처 바꾸기, 키 목록 보기를 함께 넣었다.
- **다른 선택지**: 프로젝트 만들기를 ADMIN 에게, 키 보기를 모든 구성원에게.
- **이유**: 프로젝트를 만들면 한도와 키가 함께 생기고, 허용 출처는 키를 지키는 장치(15.5)라 같은 칸에 두었다. DSN 키는 비밀이 아니지만 폐기와 함께 관리하는 것이 자연스럽다.
- **바꾸려면**: `WorkspaceService` 의 `createProject`, `updateProject`, `keys`.

### 11-7. JWT 서명 키와 내부 공유 비밀의 로컬 기본값을 설정 파일에 둔다

- **고른 것**: `application.yml` 에 로컬 개발용 값을 두고, 배포 환경은 `ERRDECK_JWT_SECRET`, `ERRDECK_INTERNAL_SECRET` 으로 바꾼다.
- **다른 선택지**: CoPage처럼 값이 없으면 api 가 뜨지 않게 하고 개발 프로필에만 기본값 두기.
- **이유**: 지금까지의 실행 방법(`bootRun`, 테스트)을 바꾸지 않는다. 25 작업에서 배포 설정에 반드시 넣는다.
- **바꾸려면**: `api/src/main/resources/application.yml` 의 `errdeck.auth`.

### 11-8. DSN 키 폐기의 유예 시간은 요청마다 정하고 기본 0이다

- **고른 것**: `DELETE /api/projects/{id}/keys/{keyId}?graceMinutes=60`. 폐기 시각을 그만큼 미래로 잡는다.
- **이유**: 15.5의 교체 기간을 요청하는 쪽이 정한다. ingest가 키를 30초 기억하므로 0이어도 최대 30초는 더 받는다.

### 11-9. 사용자가 바꿀 수 있는 이슈 상태는 미해결, 해결, 무시뿐이다

- **고른 것**: 재발(regressed)은 worker가 정한다. 해결할 때 해결한 릴리스를, 무시할 때 기한을 함께 받는다.
- **이유**: 6.6의 표에서 재발은 이벤트가 정하는 상태다. 재발 판정과 상태 전이 전체는 15 작업에서 한다.

### 11-10. Alertmanager 경보는 받기만 하고 로그를 남긴다

- **고른 것**: `/api/internal/alerts` 는 202 를 주고 로그를 남긴다.
- **이유**: 경보를 알림으로 보내는 일은 21 작업이다. 이번에는 첫째 필터 체인을 확인할 곳이 필요했다.

### 11-11. ClickHouse 조회의 값은 모두 쿼리 매개변수로 넘긴다

- **고른 것**: `ScopedQuery` 가 프로젝트 목록과 기간을 `{scope_*:타입}` 매개변수로 넣고, 추가 조건의 값도 매개변수로만 받는다. 열 이름과 식은 코드의 상수만 쓴다.
- **다른 선택지**: 쿼리 문자열에 값을 이스케이프해 이어 붙이기.
- **이유**: 값이 SQL 이 될 길을 처음부터 막는다. 범위 매개변수(`scope_` 로 시작)는 덮어쓸 수 없다.
- **바꾸려면**: `api/.../app/query/ScopedQuery.java`.

## 12 콘솔 뼈대와 이슈 화면

### 12-1. 화면 시안은 왼쪽 사이드바와 표 중심의 A안으로 정했다

WORKFLOW 4장은 시안을 2개 이상 만들어 사용자가 고르게 했지만, 사용자가 추천안으로 진행하라고 해서 두 안을 비교하고 골랐다.

| | A안: 사이드바와 표 | B안: 위쪽 막대와 카드 |
| --- | --- | --- |
| 배치 | 왼쪽 어두운 사이드바에 시스템과 그 안의 프로젝트를 접고 펴는 목록, 오른쪽 본문은 거르기 줄과 이슈 표 | 위쪽 막대에서 시스템과 프로젝트를 고르고, 본문은 이슈마다 카드 한 장을 격자로 |
| 정보 밀도 | 높음. 한 화면에 이슈 15건 안팎 | 낮음. 한 화면에 6건 안팎 |
| 프로젝트 옮겨 다니기 | 사이드바에서 한 번 | 막대의 메뉴를 열어 두 번 |
| 좁은 화면 | 사이드바가 위로 접힘 | 카드가 한 줄로 |
| 색 | 상태 배지에만 색(미해결 빨강, 재발 주황, 해결 초록, 무시 회색). 나머지는 무채색. 밝은 모드와 어두운 모드를 시스템 설정에 따름 | 카드 머리에 상태 색 띠 |

- **고른 것**: A안.
- **이유**: 시스템 4개, 프로젝트 13개를 자주 오가고(3.2), 이슈는 훑어보며 고르는 화면이라 밀도가 중요하다. 색을 상태에만 쓰면 눈이 이상한 것으로 바로 간다.
- **바꾸려면**: `web/src/components/AppShell.vue`, `web/src/style.css`.

### 12-2. 이슈 목록의 환경 거르기는 넣지 않았다

- **고른 것**: 상태, 기간, 정렬, 릴리스(최근 릴리스가 같은 이슈)로 거른다. 환경으로는 거르지 않는다.
- **다른 선택지**: 원본(events)의 environment 로 거르기, 집계 테이블에 environment 열을 더하기.
- **이유**: 횟수는 분 단위 집계에서 읽는데(10.3) 집계에 환경이 없다. 원본으로 거르면 상한으로 줄인 원본 때문에 숫자가 틀린다. 환경이 꼭 필요해지면 집계의 정렬 키에 environment 를 더하는 스키마를 새 번호로 만든다.
- **바꾸려면**: `api/src/main/resources/clickhouse` 에 새 스키마, `ClickHouseEventStats`, `IssueQueryService.list`.

### 12-3. 발생 추이는 차트 라이브러리 없이 SVG 막대로 그린다

- **고른 것**: 구간마다 막대 하나. 빈 구간은 서버가 0으로 채운다. 기간이 1시간이면 5분, 24시간이면 1시간, 7일이면 6시간, 14일과 30일이면 하루 구간이다.
- **다른 선택지**: Chart.js, ECharts 같은 라이브러리.
- **이유**: 12.1이 시계열 분석은 그라파나에 맡기기로 했다. 이슈 하나의 발생 모양만 보이면 되므로 의존성을 더하지 않았다.
- **바꾸려면**: `web/src/components/TrendBars.vue`, `IssueQueryService.Period`.

### 12-4. 횟수순과 사용자순은 쪽 넘김 없이 상위 25건만 보인다

- **고른 것**: ClickHouse가 기간 안의 지문을 많은 순으로 200개 고르고, PostgreSQL에서 상태와 릴리스로 거른 뒤 위 25건을 보인다. 최근 발생순만 쪽을 넘긴다.
- **이유**: 많이 난 것을 볼 때는 위쪽만 의미가 있다. 쪽을 넘기려면 두 저장소를 오가는 커서가 필요해 복잡해진다.
- **바꾸려면**: `IssueQueryService.TOP_CANDIDATES`, `list`.

### 12-5. 지문이 여럿인 이슈의 영향 사용자는 지문별 수를 더한다

- **고른 것**: 이슈의 사용자 수 = 지문마다 센 사용자 수의 합. 같은 사람이 두 지문에 걸치면 두 번 센다.
- **다른 선택지**: 지문을 모아 ClickHouse에서 uniqMerge 를 한 번에 하기.
- **이유**: 거의 모든 이슈는 지문이 하나다(6.4). 이슈 병합 기능을 만들 때 쿼리를 이슈 단위로 바꾼다.
- **바꾸려면**: `IssueQueryService.summarize`, `ClickHouseEventStats.counts`.

### 12-6. 그라파나 링크의 대시보드 ID를 errdeck-jvm 으로 미리 정했다

- **고른 것**: `{grafana-url}/d/errdeck-jvm/jvm?var-service={프로젝트 slug}&from&to`.
- **이유**: 대시보드는 16 작업에서 만든다. 그때 이 ID와 `service` 변수로 만든다.
- **바꾸려면**: `IssueQueryService.grafanaLink`, `errdeck.console.grafana-url`.

### 12-7. 영향 사용자에서 사용자 없는 이벤트를 빼는 스키마를 새로 더했다

- **고른 것**: 화면으로 확인하다 사용자 식별자가 없는 이벤트(user_hash 0)가 사용자 한 명으로 세지는 것을 찾았다. 구체화 뷰를 `uniqStateIf(user_hash, user_hash != 0)` 로 다시 만드는 008 을 더했다.
- **다른 선택지**: 006까지의 파일을 고치기. 이미 적용한 저장소에는 다시 돌지 않으므로 고르지 않았다.
- **감수하는 것**: 008 이전에 합쳐진 분은 사용자 수가 1 많을 수 있다. 뷰를 다시 만드는 짧은 사이에 들어온 행은 집계에서 빠질 수 있다.

### 12-8. 화면 테스트는 순수 함수와 api 호출기만 둔다

- **고른 것**: Vitest 로 시각 표기, 프레임 묶기, 재발급 흐름(401 뒤 한 번만 재발급, 동시 요청)을 시험한다. 컴포넌트 렌더링 테스트와 브라우저 테스트는 두지 않고, 이번에는 브라우저 자동화 도구로 직접 확인했다.
- **다른 선택지**: @vue/test-utils, Playwright 화면 테스트를 CI에 두기.
- **이유**: 화면은 22 작업에서 크게 늘어난다. 그때 화면 테스트를 함께 정한다.

## 13 소스맵 해석과 캐시

### 13-1. 소스맵 캐시를 Caffeine 대신 직접 만들었다

- **고른 것**: core 의 `SourceMapCache`. 동시 해석 한 번은 열쇠마다 `CompletableFuture` 하나로, 바이트 상한은 쓴 순서를 기억하는 `LinkedHashMap` 을 잠금 안에서 다뤄 지킨다.
- **다른 선택지**: 7.4가 적은 대로 Caffeine 의 로딩 캐시(무게 함수로 바이트 상한)를 worker 에 두기.
- **이유**: 작업 목록(13)이 캐시를 core 에 두라고 했고, core 는 JDK 만 쓴다(WORKFLOW 2.4). 필요한 기능(동시 해석 한 번, 바이트 상한, 오래 안 쓴 것부터 내보내기)이 작아 직접 만들 만하다.
- **감수하는 것**: 조회마다 잠금 하나를 지난다. worker 의 계산 스레드는 2개라 다툼이 적다.
- **바꾸려면**: worker 에 Caffeine 을 더하고 `Caffeine.newBuilder().maximumWeight(..).weigher((k, v) -> v.estimatedBytes())` 로 바꾼다.

### 13-2. 조회는 압축 줄 1부터, 열 0부터 받는다

- **고른 것**: `SourceMap.lookup(line, column)` 은 source-map 라이브러리와 같이 줄은 1부터, 열은 0부터 센다. 브라우저 스택의 열은 1부터라 부르는 쪽(15 작업의 복원 단계)이 1을 뺀다.
- **이유**: 정답을 만든 라이브러리와 같은 기준이어야 대조 테스트가 그대로 성립한다.

### 13-3. 원본 경로는 소스맵에 적힌 그대로 둔다

- **고른 것**: `sourceRoot` 가 있으면 앞에 붙이기만 하고 `../../src/collab.ts` 같은 상대 경로를 정리하지 않는다. 지문 규칙(6.3)의 경로 정리(`./`, 출처 떼기)는 지문을 만들 때 한다.
- **다른 선택지**: 해석할 때 `../` 를 지워 `src/collab.ts` 로 만들기.
- **이유**: 정답 라이브러리와 같은 값을 돌려주고, 화면에 보일 경로와 지문의 재료를 정하는 일은 복원 단계(15)에 맡긴다.

### 13-4. 원본 코드는 해석 결과에 담지 않는다

- **고른 것**: `SourceContext.around` 가 필요할 때 소스맵 원문을 다시 읽어 그 파일의 앞뒤 5줄만 자른다.
- **감수하는 것**: 원문 JSON 을 다시 읽는 비용. 복원 단계는 이슈마다 대표 이벤트에만 앞뒤 코드를 붙여 이 비용을 줄인다(15).
- **이유**: 7.3. 원본 코드는 해석 결과보다 훨씬 커서 캐시에 넣으면 128MB 안에 든 소스맵 수가 크게 준다.

### 13-5. 정답 자료는 스크립트로 만들어 저장소에 넣는다

- **고른 것**: `scripts/sourcemap-fixture` 에서 `npm run generate` 로 Vite 빌드와 source-map 0.7.4 의 정답을 만들고, 결과(소스맵 583KB, 정답 848KB)를 `core/src/test/resources/sourcemap` 에 넣는다.
- **다른 선택지**: 테스트할 때마다 Node 로 만들기.
- **이유**: core 테스트가 Node 없이 돈다. Vite 나 소스맵 형식이 바뀌면 스크립트로 다시 만든다.

## 14 Vue SDK

### 14-1. 압축 여부는 쿼리가 아니라 본문의 gzip 머리로 가린다

- **고른 것**: SDK 는 압축하면 설계대로 `enc=gzip` 을 붙이지만, ingest 는 본문을 해석하지 않으므로(adr/0003) 대기열에 옮기지 않는다. worker 의 봉투 읽기가 gzip 머리(1f 8b)로 압축 여부를 가린다.
- **다른 선택지**: ingest 가 `enc` 를 대기열 항목의 필드로 옮기기.
- **이유**: 탭을 떠날 때의 `sendBeacon` 은 동기로 보내야 해서 비동기인 CompressionStream 을 거칠 수 없다. 압축하지 않은 봉투가 생기는데, 머리 두 바이트로 확실히 가릴 수 있어 ingest 를 바꾸지 않았다.
- **바꾸려면**: `core` 의 `EnvelopeCodec.decode`.

### 14-2. 요청 정보에는 쿼리와 조각을 넣지 않는다

- **고른 것**: `request.url` 은 `location.origin + location.pathname`. 헤더는 `User-Agent` 만.
- **이유**: 브라우저 주소의 쿼리에는 토큰이나 이메일이 실릴 수 있다(15.6). 서버 SDK 처럼 이름으로 골라 지우기보다 아예 보내지 않는 쪽이 가볍고 안전하다.

### 14-3. 앱 프레임 판정은 브라우저에서 하지 않는다

- **고른 것**: 프레임의 `in_app` 을 비워 둔다. 번들 하나에 내 코드와 라이브러리가 섞여 있어 브라우저에서는 가릴 수 없다. 소스맵으로 복원한 뒤 worker 가 `node_modules` 밖인지로 정한다(6.3, 15 작업).

### 14-4. fetch 만 빵부스러기로 남기고 XMLHttpRequest 는 감싸지 않는다

- **고른 것**: `window.fetch` 를 감싸 주소(쿼리 제외)와 상태 코드를 남긴다. ingest 로 보내는 요청은 남기지 않는다.
- **다른 선택지**: XMLHttpRequest 도 감싸기(axios 의 기본 어댑터).
- **이유**: 팬파라이브 web 과 CoPage web 은 fetch 를 쓴다. 번들 크기를 작게 둔다. axios 를 쓰는 대상이 생기면 더한다.

### 14-5. Retry-After 가 없는 429, 503 은 60초 쉰다

- **고른 것**: 서버 SDK(09-5)와 같다. ingest 는 Retry-After 를 Access-Control-Expose-Headers 로 열어 두므로 보통은 그 값을 쓴다.

### 14-6. SDK 의 큐 상한은 100건, 묶음 간격은 2초다

- **고른 것**: 브라우저 한 탭에서 나는 에러는 서버보다 훨씬 적어 서버 SDK(1,000건)보다 작게 잡았다. 넘으면 버리고 `queue_overflow` 로 센다.
- **바꾸려면**: `createErrDeck({ queueSize, flushIntervalMs })`.

### 14-7. 데모 화면은 SDK 를 로컬 경로로 의존한다

- **고른 것**: `demo-web/package.json` 의 `"@errdeck/sdk-vue": "file:../sdk-vue"`. SDK 를 먼저 빌드해야 한다(CI도 그 순서).
- **이유**: 패키지 저장소에 올릴 곳은 아직 정하지 않았다(20장의 미정 사항). 감시 대상(23 작업)도 같은 방식이나 빌드 결과를 복사해 붙인다.
