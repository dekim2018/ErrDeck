# 8. 성능 추적

성능 추적은 역할을 둘로 나눈다. 엔드포인트가 얼마나 느린지는 프로메테우스가 전체 요청으로 재고, 왜 느린지는 이 서비스가 표본 요청의 스팬으로 보여 준다.

## 8.1 역할을 나누는 이유

모든 요청의 스팬을 저장하면 정확하지만, 저장량이 요청 수에 비례해 늘어난다. 일부만 저장하면 가볍지만, 표본으로 계산한 p95와 처리량은 틀린다.

감시 대상은 이미 Micrometer로 요청 시간 히스토그램(`http_server_requests_seconds`)을 내보낸다. 이것은 모든 요청을 세지만 크기가 요청 수와 무관하다. 그래서 다음과 같이 나눈다.

| 질문 | 답하는 곳 | 근거 데이터 |
| --- | --- | --- |
| 이 엔드포인트의 p95, 처리량, 에러율은? | 프로메테우스 | 전체 요청의 히스토그램 |
| 이 요청은 어디서 시간을 썼나? | 이 서비스(ClickHouse) | 표본 요청의 스팬 |
| 이 에러는 어떤 요청 흐름에서 났나? | 이 서비스 | 이벤트의 trace_id |
| 브라우저에서 페이지와 API 호출이 얼마나 걸렸나? | 이 서비스 | Vue SDK의 트랜잭션 |

콘솔의 성능 화면은 두 출처를 한 화면에 합친다. 위쪽 엔드포인트 표는 api가 프로메테우스에 질의해 채우고, 줄을 누르면 나오는 느린 요청 목록과 스팬 그림은 ClickHouse에서 읽는다.

## 8.2 모델과 전파

| 값 | 형식 | 뜻 |
| --- | --- | --- |
| trace_id | 16진수 32자 | 요청 하나의 전체 흐름 |
| span_id | 16진수 16자 | 작업 하나 |
| parent_span_id | 16진수 16자 | 이 작업을 부른 작업 |

서비스 사이에는 W3C Trace Context 표준의 `traceparent` 헤더로 전달한다. 형식은 `00-{trace_id}-{span_id}-{표본 여부}` 다. 표준 헤더를 쓰면 나중에 다른 도구와 섞어 쓸 수 있다.

팬파라이브의 흐름을 예로 들면 다음과 같다.

1. Vue SDK가 후원 버튼의 API 호출에 `traceparent` 를 붙인다.
2. gateway가 헤더를 읽어 자기 트랜잭션을 만들고, 뒤로 넘길 때 자기 span_id로 바꿔 붙인다.
3. interaction-service가 같은 trace_id로 트랜잭션을 만든다. 그 안에 SQL과 결제사 호출이 스팬으로 들어간다.
4. 세 구간이 trace_id 하나로 묶여 화면에 한 그림으로 보인다.

## 8.3 계측 범위

| 대상 | 방법 | 기록 내용 |
| --- | --- | --- |
| 들어오는 HTTP 요청 | Micrometer Observation 핸들러 | 경로 패턴(`/api/matches/{id}`), 상태 코드, 시간 |
| 나가는 HTTP 호출 | RestClient 인터셉터 | 호스트, 경로, 상태 코드. `traceparent` 추가 |
| SQL | DataSource 감싸기 | 값을 지운 SQL 문, 시간 |
| 사용자 정의 구간 | SDK의 스팬 API | 이름과 시간 |
| 브라우저 | Vue Router 훅, fetch 감싸기 | 페이지 이동, API 호출 |

긴 연결은 트랜잭션에서 뺀다. 팬파라이브의 SSE(댓글, 알림)와 CoPage의 WebSocket은 연결이 몇 분에서 몇 시간 유지된다. 이것을 요청 시간으로 기록하면 통계가 망가진다. 연결 수립까지만 기록한다.

경로는 실제 주소가 아니라 패턴으로 기록한다. `/api/matches/1024` 를 그대로 쓰면 엔드포인트가 수만 개로 보인다.

## 8.4 표본 추출

요청이 시작될 때 프로젝트별 비율(처음 값 10%)로 추적 여부를 정하고, 그 결정을 `traceparent` 에 실어 뒤 서비스가 그대로 따르게 한다. 한 요청의 구간이 전부 있거나 전부 없게 된다.

시작할 때 정하면 느린 요청과 에러 난 요청을 놓칠 수 있다. 그래서 SDK가 요청이 끝날 때 한 번 더 판단한다.

| 경우 | 처리 |
| --- | --- |
| 시작할 때 표본으로 뽑힘 | 전체 구간을 보냄 |
| 뽑히지 않았지만 에러가 남 | 이 서비스의 구간만 보냄. 부분 추적으로 표시 |
| 뽑히지 않았지만 기준(처음 값 1초)보다 느림 | 위와 같음 |
| 그 밖 | 버림 |

이를 위해 SDK는 뽑히지 않은 요청도 스팬을 메모리에 모았다가 끝에서 버린다. 객체 할당 비용이 생기므로 2.2의 SDK 부담 목표에 이 비용을 포함해 잰다. 부담이 목표를 넘으면 이 기능을 설정으로 끌 수 있게 한다.

## 8.5 스팬 수 제한과 반복 접기

반복문 안에서 쿼리를 날리는 코드는 요청 하나에 스팬 수천 개를 만든다. 트랜잭션당 스팬은 500개로 제한한다.

같은 내용의 스팬이 연속으로 반복되면 하나로 접고 횟수와 합계 시간을 남긴다. 접힌 횟수가 10 이상이면 화면에 반복 쿼리로 표시한다. 저장량을 줄이는 장치가 그대로 N+1 쿼리를 찾는 기능이 된다.

## 8.6 버린 대안과 측정할 값

| 대안 | 버린 이유 |
| --- | --- |
| 전체 요청의 스팬 저장 | 저장량과 수집 부하가 요청 수에 비례. 서버 1대 예산을 넘음 |
| 표본으로 p95 계산 | 표본 비율에 따라 값이 흔들리고, 드문 엔드포인트는 표본이 없음 |
| 서버에서 추적 전체를 받은 뒤 고르기 | 고르려면 일단 전부 받아야 하므로 수집 부하가 줄지 않음 |
| OpenTelemetry 에이전트 사용 | 자체 SDK를 만드는 것이 이 프로젝트의 목적. 헤더 형식만 표준을 따름 |

측정할 값은 추적을 켠 것과 끈 것의 요청 시간 차이(p50, p99), 트랜잭션당 평균 스팬 수, 접힌 스팬의 비율이다.
