#### 열린 문제: 한 클라이언트가 초당 봉투 5,000개를 보내면 연결이 끊긴다

봉투당 1건으로 초당 5,000개를 보낸 실험에서 실패의 대부분은 `SocketException: Connection reset by peer (connect failed)` 였다. 같은 부하를 30초로 다시 돌려 원인을 좁혔다.

| 확인한 것 | 결과 |
| --- | --- |
| 실패가 나는 단계 | TCP 연결 단계. ingest의 요청 수 지표에는 잡히지 않았다 |
| CPU | ingest 1.1코어 안팎, loadgen 2코어, Redis 0.2코어. 10코어 중 어느 쪽도 포화가 아니다 |
| TCP 상태 | 실행 직후 TIME_WAIT 약 11,000개. loadgen이 연결을 계속 새로 연다 |
| Tomcat의 연결당 요청 상한 해제(`max-keep-alive-requests=-1`) | 나아지지 않았다(연결 실패 87,029건) |
| 맥의 연결 대기열 | `kern.ipc.somaxconn` 128, Tomcat `accept-count` 기본 100 |

연결 대기열이 넘친다는 것까지는 확인했고, 연결이 왜 그만큼 새로 열리는지는 아직 모른다. 05 작업 중 같은 현상을 ingest의 동시성 테스트에서 다시 보았다. 연결 200개를 한꺼번에 열면 가끔 같은 예외로 실패했고, 동시 연결을 32개로 줄이자 다섯 번 연속 통과했다. 한꺼번에 여는 연결 수가 연결 대기열(100)을 넘으면 끊긴다는 쪽에 무게가 실린다. 실제 SDK는 프로세스마다 전송 스레드 하나로 묶어서 보내므로(11.2) 이 모양의 부하는 나오지 않는다. 묶어서 보낸 같은 초당 5,000건은 실패 0건이었다. 17 작업(자원 실험)에서 ingest를 컨테이너로 올리고 서버 쪽 지표로 다시 본다. 14.3의 "동시 연결 2,000"은 03 작업에서 설정하지 않아 Tomcat 기본값(8,192)이다.

#### 열린 문제: Redis 제한 시간을 넘긴 요청도 실제로는 적재된다

위 실험에서 ingest가 503(`unavailable`)으로 응답한 98건과 474건이 모두 ClickHouse에 저장되어 있었다. 원인은 Redis 호출이 200ms를 넘겨 ingest가 기다리기를 포기했지만 Lua 스크립트는 Redis에서 이미 실행된 것이다. 제한 시간이 지나면 적재되었는지 알 수 없다.

| 확인한 것 | 결과 |
| --- | --- |
| 타임아웃이 난 시각 | 부하를 시작한 직후 1~3초, worker를 다시 띄운 순간에 몰렸다 |
| Redis 쪽 지연 | 지연 감시(20ms)와 느린 명령 기록(10ms)을 켜고 같은 부하를 다시 걸었을 때 기록 없음, 타임아웃도 0건 |
| Redis 의 fork | 1.9ms |
| ingest 의 GC 멈춤 | 최대 75ms |

Redis 자체는 빠르고, 부하 도구, worker, 도커 포트 전달이 같은 맥에서 순간적으로 CPU를 다툴 때 생긴 것으로 본다. 결과는 잃는 것이 아니라 더 받는 쪽이다. SDK가 다시 보내면 08 작업의 event_id 중복 확인이 걸러 내고, 다시 보내지 않으면 SDK의 버린 건수가 실제보다 많게 잡힌다. 17 작업에서 컨테이너 상한을 걸고 다시 잰다.

## 실행 방법

자원 실험과 장애 실험(17, 24 작업):

```bash
./gradlew :loadgen:installDist && docker compose --profile core --profile obs --profile demo build
python3 scripts/experiments/resources.py compute-threads   # gc, batch-rows, ingest-inflight, api-pool, compact-headers, cores
python3 scripts/chaos/chaos.py worker-kill                  # clickhouse-stop, redis-restart, postgres-stop, all-down, two-workers
```

03~07 작업의 호스트 실행 방법:

```bash
./gradlew :ingest:bootJar :loadgen:installDist
java -jar ingest/build/libs/ingest-0.1.0-SNAPSHOT.jar
loadgen/build/install/loadgen/bin/loadgen sustained --dsn=http://<키>@localhost:8080/<프로젝트ID> --rate=500 --duration=30s --fingerprints=1000
loadgen/build/install/loadgen/bin/loadgen burst --dsn=http://<키>@localhost:8080/<프로젝트ID> --rate=5000 --duration=5m --batch=50
docker compose exec redis redis-cli XLEN errdeck:stream:events
```

worker가 대기열을 비우기 전(07 작업 전)에는 실험 사이에 `docker compose exec redis redis-cli DEL errdeck:stream:events` 로 대기열을 비운다.
