# 17. 배포

로컬 docker compose를 기준 환경으로 삼고, 같은 compose 파일에 덮어쓰기 파일 하나를 더해 오라클 무료 서버에 올린다. 쿠버네티스는 8단계의 선택 과제로 두고, 한다면 로컬에서만 한다.

## 17.1 세 가지 선택지 비교

| 기준 | 로컬 docker compose | 오라클 무료 서버 | 쿠버네티스(k3s) |
| --- | --- | --- | --- |
| 비용 | 없음 | 없음(무료 한도 안) | 없음(로컬 또는 같은 서버) |
| 자원 | 내 PC. 도커에 4코어, 8GB 할당 | 2코어, 12GB | 같은 서버에서 k3s 자체가 자원을 더 씀 |
| 외부에서 접속 | 불가 | 가능. 팬파라이브가 실제로 이벤트를 보낼 수 있음 | 서버에 올릴 때만 가능 |
| 이 문서의 고민을 보여 주는가 | 보여 줌. 상한과 풀 설정이 그대로 드러남 | 보여 줌. 코어가 절반일 때의 조정까지 | 일부만. 상한이 requests와 limits로 옮겨질 뿐 |
| 추가 작업 | 없음 | 서버 설정 하루 | 매니페스트, 인그레스, 볼륨, 프로브 |
| 제안 | 기준 환경 | 공개 시연용 | 선택 과제 |

## 17.2 쿠버네티스를 기본으로 하지 않는 이유

쿠버네티스가 주는 것은 여러 서버에 걸친 배치, 자동 복구, 수평 확장이다. 서버가 한 대면 배치할 곳이 없고, 자동 복구는 도커의 재시작 정책으로 충분하다. 수평 확장은 코어 2개에서 시연할 여유가 없다.

쿠버네티스 없이도 확인할 수 있는 것이 많다.

| 확인하고 싶은 것 | compose에서 하는 방법 |
| --- | --- |
| worker 여러 대의 안전성(중복 처리, 중복 점검, 중복 알림) | `docker compose up --scale worker=2` |
| 프로세스가 죽었을 때의 복구 | `docker kill` 과 재시작 정책 |
| 자원 상한의 효과 | compose의 CPU와 메모리 상한 |
| 준비 상태 확인 | compose의 healthcheck와 Actuator의 상태 그룹 |

그래도 쿠버네티스를 경험으로 넣고 싶다면 마지막 단계에서 로컬 k3d로 다음 범위만 한다. 매니페스트 작성, 준비 상태와 생존 상태 프로브, 무중단 교체 배포, 대기열 나이를 기준으로 한 worker 자동 확장이다. 이 경우에도 설계는 바뀌지 않는다. 14장의 상한이 그대로 매니페스트의 값이 된다.

## 17.3 compose 구성

| 프로필 | 포함하는 것 | 용도 |
| --- | --- | --- |
| core | Caddy, ingest, worker, api, web, PostgreSQL, Redis, ClickHouse | 기능 개발 |
| obs | Prometheus, Grafana, Alertmanager, exporter 4종 | 관측과 자원 실험 |
| demo | 데모 앱, loadgen | 에러와 부하 만들기 |

파일은 셋으로 나눈다.

- `docker-compose.yml`: 전체 정의와 4코어 기준 상한(14.1, 14.7).
- `docker-compose.oci.yml`: 오라클 서버용 덮어쓰기. CPU 상한과 풀 크기만 바꾼다.
- `docker-compose.agent.yml`: 감시 대상 서버에 두는 프로메테우스 에이전트(13.3).

맥의 도커는 리눅스 가상 머신 안에서 돈다. 로컬에서 node exporter와 cAdvisor가 보여 주는 값은 맥이 아니라 그 가상 머신의 값이다. CPU 제한 현상 같은 실험은 로컬에서도 재현되지만, 디스크 성능 수치는 서버에서 다시 잰다.

## 17.4 오라클 무료 서버의 조건

오라클 클라우드에는 기간 제한 없이 무료인 자원이 있다. 2026년 11월 기준 조건은 다음과 같다([오라클 문서](https://docs.oracle.com/iaas/Content/FreeTier/resourceref.htm)).

| 항목 | 내용 |
| --- | --- |
| Arm 서버(Ampere A1) | 합계 2코어(OCPU), 메모리 12GB. 한 대로 써도 되고 두 대로 나눠도 됨 |
| 디스크 | 부트 볼륨과 블록 볼륨 합계 200GB |
| 지역 | 가입할 때 고른 홈 리전에서만 무료 |
| 유휴 회수 | 7일 동안 CPU 사용률(95 백분위) 20% 미만, 네트워크 20% 미만, 메모리 20% 미만이면 유휴로 보고 회수할 수 있음 |
| 메일 | 나가는 25번 포트가 기본으로 막혀 있음 |

주의할 점이 있다. 이 서버의 무료 한도는 2026년 6월 15일에 4코어 24GB에서 2코어 12GB로 절반이 되었다([InfoQ 기사](https://www.infoq.com/news/2026/07/oracle-cloud-free-tier-limits/)). 인터넷의 설치 글 대부분은 예전 한도 기준이다. 한도가 또 바뀔 수 있으므로 서버를 만들기 직전에 문서를 다시 확인한다.

메모리 12GB는 14.7의 예산 5,632MB를 담고도 남는다. 부족한 것은 코어다. 4코어 기준으로 잡은 상한을 다음과 같이 줄인다.

| 컨테이너 | 4코어 기준 | 오라클(2코어) | 함께 바꾸는 것 |
| --- | --- | --- | --- |
| worker | 2.0 | 1.0 | 계산 풀을 2개에서 1개로 |
| ClickHouse | 2.0 | 1.0 | 쿼리당 스레드 수를 1로 |
| ingest | 1.0 | 0.5 |  |
| api | 1.0 | 0.5 |  |
| PostgreSQL | 1.0 | 0.5 |  |
| Redis | 1.0 | 0.5 |  |

2.2의 처리량 목표는 4코어 기준이다. 오라클 서버에서는 같은 실험을 다시 돌려 2코어에서의 값을 따로 기록한다. 코어가 절반일 때 처리량이 절반인지, 그보다 더 떨어지는지가 그 자체로 의미 있는 측정이다.

## 17.5 오라클 서버에 올리는 순서

1. 계정을 만든다. 홈 리전은 나중에 바꿀 수 없으므로 가까운 곳(서울 또는 춘천)을 고른다. 본인 확인에 카드가 필요하다.
2. 인스턴스를 만든다. 모양은 VM.Standard.A1.Flex, 2코어, 12GB, 이미지는 Ubuntu, 부트 볼륨은 100GB로 한다. SSH 공개 키를 등록한다.
3. 용량 부족 오류가 나면 다른 가용 도메인을 고르거나 시간을 두고 다시 시도한다. 오라클 문서는 종량제 계정으로 올리는 방법도 안내한다. 무료 한도 안의 자원에는 요금이 붙지 않는다고 되어 있지만, 한도를 넘으면 과금되므로 신중하게 정한다.
4. 가상 네트워크의 보안 목록에서 들어오는 80, 443 포트를 연다. 22번은 내 IP에만 연다.
5. 인스턴스 안의 방화벽에서도 80, 443을 연다. 보안 목록만 열고 접속이 안 되면 대부분 이 단계가 빠진 것이다.
6. 도커를 설치하고 저장소를 내려받는다.
7. `.env` 에 비밀번호, JWT 비밀 키, 도메인을 넣는다.
8. DuckDNS에 도메인을 만들어 서버 IP를 연결한다. 팬파라이브와 같은 방식이고 Caddy가 인증서를 자동으로 받는다.
9. `docker compose -f docker-compose.yml -f docker-compose.oci.yml --profile core --profile obs up -d --build` 로 올린다.
10. 팬파라이브의 SDK 설정에 이 서버의 DSN을 넣고, 팬파라이브 서버에 프로메테우스 에이전트를 띄운다.

서버가 Arm이라는 점은 문제가 되지 않는다. 자체 이미지는 팬파라이브 때처럼 서버에서 직접 빌드하므로 아키텍처가 자동으로 맞는다. 받아 쓰는 이미지(PostgreSQL, Redis, ClickHouse, Prometheus, Grafana)는 Arm용을 함께 제공한다.

유휴 회수는 세 조건이 모두 참일 때 해당한다. 이 서비스는 메모리를 5GB 넘게 쓰므로 메모리 조건에는 걸리지 않을 것으로 본다. 실제 사용률은 올린 뒤 오라클 콘솔에서 확인한다.

## 17.6 운영 설정

| 항목 | 설정 |
| --- | --- |
| 재시작 | 모든 컨테이너에 자동 재시작 정책 |
| 시작 순서 | 저장소의 healthcheck가 통과한 뒤 ingest, worker, api 시작 |
| 종료 | worker는 종료 신호를 받으면 읽기를 멈추고, 처리 중인 묶음을 쓰고 확인 처리한 뒤 끝낸다. 제한 30초 |
| 스키마 | PostgreSQL은 Flyway. ClickHouse는 번호 붙인 SQL 파일을 순서대로 적용하는 작은 실행기 |
| 백업 | PostgreSQL만 매일 덤프. ClickHouse는 보존 기간이 짧은 기록이라 백업하지 않음 |
| 로그 | 컨테이너당 10MB 파일 3개로 회전 |
| CI | GitHub Actions에서 빌드와 테스트. 배포는 서버에서 수동 |
