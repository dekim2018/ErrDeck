# ErrDeck 기획서

에러 모니터링 서비스의 목표, 범위, 용어를 정리한다. 설계 문서는 02번부터 이어진다.

## 1. 개요와 핵심 결정

이 서비스는 여러 서비스를 프로젝트로 등록해 에러, 요청 성능, 가동 상태를 한곳에서 수집하고 확인하는 셀프 호스팅 모니터링 플랫폼이다. 포트폴리오 3번 프로젝트이며, 1번 팬파라이브와 2번 CoPage가 첫 번째 고객이 된다.

이 문서의 무게 중심은 화면 기능보다 서버와 인프라 설계에 둔다. 모니터링 서비스는 감시 대상이 고장 났을 때 가장 많은 요청을 받는다. 평소 부하가 아니라 장애 순간의 부하를 견디는 것이 이 서비스 고유의 문제이고, 4장부터 14장까지의 설계가 모두 여기서 출발한다.

### 1.1 이번에 정한 것

| 항목 | 결정 | 자세한 내용 |
| --- | --- | --- |
| 수집 범위 | 에러, 요청 성능 추적, 업타임 점검 세 가지 | 2장, 8장, 9장 |
| 기술 | Java 25, Spring Boot 4.1.x, Spring Security 7.1.x, Vue 3, PostgreSQL 17, ClickHouse, Redis 7 | 4장, 10장 |
| SDK | 자체 Spring Boot Starter SDK와 Vue SDK | 11장 |
| 수집 대상 | 팬파라이브, CoPage, 이 서비스 자신, 에러 실험용 데모 앱 | 3장 |

### 1.2 제안 두 가지

**배포 규모: 서버 1대와 docker compose를 기준으로 설계하고, 쿠버네티스는 마지막 단계의 선택 과제로 둔다.**

이유는 세 가지다.

1. 이 문서에서 말하려는 고민은 CPU 배분, 스레드 풀 크기, 메모리 예산, 프로세스 간 장애 격리다. 이 고민은 자원이 고정된 서버 1대에서 가장 선명하게 드러난다. 코어 4개를 누구에게 얼마나 줄지 정해야 하기 때문이다.
2. 쿠버네티스를 먼저 도입하면 매니페스트, 인그레스, 볼륨 같은 운영 작업이 늘어난다. 그 시간은 백엔드 설계의 깊이로 이어지지 않는다.
3. 수집, 처리, 조회를 처음부터 별도 컨테이너로 나누고 컨테이너마다 CPU와 메모리 상한을 적어 두면, 그 숫자가 쿠버네티스의 requests와 limits로 그대로 옮겨진다. 나중에 옮기는 비용이 작다.

실행 환경은 로컬과 오라클 무료 서버 두 곳을 같은 compose 파일로 지원한다. 방법은 17장에 적는다.

**한눈에 보기: 3번(에러는 화면, 지표는 그라파나)을 기본으로 하고, 2번에서 요약 카드만 가져온다.**

- 화면에 직접 그리는 것: 에러, 성능, 업타임, 그리고 서비스별 상태 요약 카드(지표 6개).
- 그라파나로 넘기는 것: CPU, 메모리, 스레드, GC 같은 상세 시계열. 화면에서 보던 서비스와 시간 범위를 그대로 가진 링크로 연결한다.

이유는 12장에 정리한다. 요약하면, 그라파나가 이미 잘하는 시계열 차트를 다시 만드는 것은 이 프로젝트의 차별점이 아니다. 반대로 링크만 걸면 한눈에 본다는 목표가 깨진다. 그래서 판단에 필요한 숫자 6개만 화면에 올리고 나머지는 넘긴다.

### 1.3 이 문서의 원칙

- 설계마다 서비스 고유의 문제, 고른 방법, 버린 대안, 측정할 값을 함께 적는다.
- 성능 숫자는 전부 목표값이다. 실측 전에는 결과 숫자를 적지 않는다.
- 서비스 이름은 ErrDeck이다(2026-11-23 확정). 저장소는 dekim2018/ErrDeck, 기본 패키지는 com.errdeck이다. 문서에서는 프로세스 이름을 ingest, worker, api, web 으로 부른다.

### 2.2 비기능 목표

아래 값은 전부 목표다. 18장의 부하 실험으로 실측한 뒤 달성 여부를 적는다.

| 항목 | 목표 | 재는 곳 |
| --- | --- | --- |
| 수집 응답 시간 | 정상 부하에서 p99 50ms 이하 | ingest의 HTTP 히스토그램 |
| 표시까지 걸리는 시간 | 수신부터 조회 가능까지 p95 5초 이하 | 수신 시각과 저장 시각의 차이 |
| 지속 처리량 | 초당 500건을 30분 동안 지연 누적 없이 처리 | 대기열 길이와 가장 오래된 항목의 나이 |
| 폭주 내성 | 초당 5,000건 수신에서 ingest가 응답하고 발생 건수가 정확함 | 보낸 건수와 집계 건수 비교 |
| SDK 부담 | 추적을 켠 요청의 추가 지연 p99 1ms 이하 | SDK 켠 것과 끈 것의 비교 실험 |
| 격리 | 이 서비스가 멈춰도 감시 대상의 요청은 실패하지 않음 | 장애 실험 |
| 자원 | 4코어, 메모리 예산 5,632MB 안에서 전체 동작 | 컨테이너 지표 |

### 2.3 보존 기간

| 데이터 | 보존 | 이유 |
| --- | --- | --- |
| 에러 이벤트 원본 | 30일 | 이슈 조사에 필요한 기간. 용량의 대부분을 차지함 |
| 스팬 | 7일 | 건수가 가장 많고 최근 것만 의미가 있음 |
| 업타임 점검 결과 | 90일 | 분기 가동률 계산 |
| 분 단위 집계 | 1년 | 추세 그래프. 행이 작아 오래 둘 수 있음 |
| 이슈, 릴리스, 장애 기록 | 삭제하지 않음 | PostgreSQL에 두는 메타데이터 |

### 2.4 하지 않는 것

- 로그 수집과 검색. 에러와 추적에 집중한다. 컨테이너 로그는 파일 회전만 설정한다.
- 세션 리플레이, 프로파일링, 모바일 SDK.
- 요금제와 결제. 대신 프로젝트별 수집 한도는 구현한다. 폭주 방어에 필요하기 때문이다.
- 여러 리전 배포.
- OpenTelemetry 프로토콜 수신. 자체 SDK를 먼저 완성하고, 여유가 있으면 마지막 단계에서 검토한다.

## 3. 용어와 도메인 모델

### 3.1 용어

| 용어 | 뜻 |
| --- | --- |
| 시스템 | 하나의 제품을 이루는 프로젝트 묶음. 팬파라이브, CoPage가 각각 시스템이다. 한눈에 보기 화면의 단위다 |
| 프로젝트 | 배포 단위 하나. 스프링 서비스 하나, 프론트 앱 하나가 각각 프로젝트다. DSN 키와 수집 한도를 가진다 |
| 환경 | local, staging, production 같은 실행 환경. 이벤트의 속성이며 조회 필터로 쓴다 |
| DSN 키 | SDK가 이벤트를 보낼 때 쓰는 프로젝트 식별 키. 브라우저에 노출되는 공개 키다 |
| 릴리스 | 프로젝트의 배포 버전. 보통 git 커밋 해시. 소스맵과 재발 판정의 기준이다 |
| 이벤트 | SDK가 보낸 에러 1건. 수정되지 않는 기록이다 |
| 지문 | 같은 원인의 이벤트를 묶기 위해 스택트레이스에서 계산한 해시 |
| 이슈 | 같은 지문을 가진 이벤트의 묶음. 상태와 담당자를 가진 작업 단위다 |
| 추적 | 요청 하나가 여러 서비스를 지나간 전체 경로. trace_id 하나로 묶인다 |
| 트랜잭션 | 추적 중 서비스 하나가 처리한 구간. 예: POST /api/donations |
| 스팬 | 트랜잭션 안의 작업 하나. 예: SQL 한 번, 외부 호출 한 번 |
| 모니터 | 업타임 점검 대상 하나. 주소, 주기, 기대 응답을 가진다 |
| 장애 기록 | 모니터가 다운으로 판정된 때부터 복구될 때까지의 구간 |

### 3.2 시스템과 프로젝트 구성

시스템 4개, 프로젝트 13개로 시작한다.

| 시스템 | 프로젝트 | 종류 | 개수 |
| --- | --- | --- | --- |
| 팬파라이브 | gateway, auth-service, broadcast-service, interaction-service, fandom-service | Spring | 5 |
| 팬파라이브 | web | Vue | 1 |
| CoPage | app | Spring | 1 |
| CoPage | web | Vue | 1 |
| 이 서비스 | api, worker | Spring | 2 |
| 이 서비스 | web | Vue | 1 |
| 데모 앱 | demo-api | Spring | 1 |
| 데모 앱 | demo-web | Vue | 1 |

확인이 필요한 점이 하나 있다. 이전 정리에서는 팬파라이브를 서비스 4개와 Vue로 적었다. 이 문서에서는 gateway를 더해 5개로 잡았다. 서비스 간 추적이 gateway에서 시작하기 때문에 gateway가 빠지면 추적의 첫 구간이 비기 때문이다.

이 서비스의 ingest는 프로젝트로 등록하지 않는다. ingest가 자기 에러를 자기에게 보내면 장애 때 요청이 스스로 불어나는 고리가 생긴다. ingest는 프로메테우스 지표와 컨테이너 로그로만 본다.

### 3.3 이벤트와 이슈를 나눠 저장하는 이유

이벤트와 이슈는 성격이 정반대다.

- 이벤트는 건수가 많고, 한 번 쓰면 바뀌지 않으며, 기간과 조건으로 집계해서 읽는다. ClickHouse에 둔다.
- 이슈는 건수가 적고, 상태와 담당자가 자주 바뀌며, 한 건씩 정확하게 읽고 쓴다. PostgreSQL에 둔다.

둘을 한 저장소에 두면 어느 쪽이든 손해를 본다. PostgreSQL에 이벤트를 쌓으면 30일 치를 지우는 작업과 집계 쿼리가 부담이 된다. ClickHouse에 이슈를 두면 행 단위 수정과 트랜잭션이 맞지 않는다. 스키마는 10장에 적는다.
